# LocalMind 页面加载缓慢故障分析：文档权限轮询放大与日志写入争用

首次记录：2026-10-30。代码分析与方案：2026-10-31（GPT 起草）。复核与现场复测：2026-11-01。时区：America/Los_Angeles（下称 PT），现场时间同时给出 UTC。

状态：第 2—10 节是 10 月 30—31 日的现场记录和方案原文，保留供追溯；第 11 节是 2026-11-01 的复核结论，与前文冲突时以第 11 节为准。线上于 2026-10-31 23:20 PT 重启恢复，仍运行原实现，故障条件没有消除。“日志堆内存 OOM 排查”会话已在本地源码实施部分止血改动，尚未提交、发布或部署。

结论摘要（2026-11-01）：

- 本问题与[日志积压与堆内存耗尽](localmind-logging-heap-oom-investigation.zh-CN.md)是**同一次故障、同一个进程、同一条因果链**：页面慢是前半段，OOM 是后半段。但页面慢不以 OOM 为前提。重启约 3 小时后，spool 为 0，内存也正常，权限轮询、日志随机读和连接池占满仍然存在，页面仍然慢。只修 OOM 后半段，页面不会变快。
- 首要流量源已经可以确定，不再是“待复现”。提交 `f4a00b882a`（2026-10-25）把原本只服务单个文档范围的 5 秒权限轮询，扩展到所有被订阅的文档；同时让资源列表、侧栏、搜索把全部候选文档纳入订阅。每到一个周期，全部文档的请求在约 100 ms 内同时发出；后台标签页被浏览器节流成每分钟一次，但仍然整批发出。每个请求在服务端要加载三遍权限上下文，执行约 15 条业务 SQL，还附带两条逐条提交事务的完成日志。
- GPT 方案的诊断方向基本正确，机制细节经逐条核对大多属实。不足有三类：
  - 优先级偏重验证和通用框架，止血不足；
  - 普通运行日志的持久化设计过重；
  - 遗漏了同周期突发发起、服务端单次成本、debug 日志入库，以及“等待时显示为空”等问题。

  推荐顺序见第 11.6 节。

### 2.2 当前数据库读取主要来自运行日志

现场 `vmstat` 与 `iostat` 观测到：

- 多次采样的 CPU I/O wait 为约 60%—80%；另一次采样为 36%—65%，存在波动。
- 磁盘 `sda` 读平均等待约 79—80 ms，写平均等待约 36—38 ms，平均队列深度约 30。
- 多个 PostgreSQL 进程处于磁盘等待状态；一次数据库快照有 16 个连接等待 `DataFileRead`，另有 1 个等待 `BufferIO`。

随后连续采样 8 次数据库连接状态，共获得 144 个连接状态样本，其中 94 个是运行日志 SQL 等待 `DataFileRead`。另有 WAL 提交等待、短暂事务和少量 advisory lock 等待，不能表述为“完全没有锁等待”。

| ---------------------------- | ---------: | ---------: |
| `localmind_log_events_2026`  |      1,220 |        449 |
| `localmind_log_event_ids`    |        444 |        449 |
| `ai_context_project_members` |          3 |          0 |
| 其余采集表                   |          0 |          — |
| 合计                         |      1,667 |          — |

## 3. 代码机制与证据强度

### 3.1 已核对线上产物的日志写入路径

从线上运行镜像的 `main.js.map` 读取了对应源码，并与本地文件比较 SHA-256。以下四个文件一致，因此此处不是仅凭本地较新源码推断线上行为：

- `packages/backend/server/src/server.ts`
- `packages/backend/server/src/base/logger/localmind-log-service.ts`
- `packages/backend/server/src/base/prisma/factory.ts`
- `packages/backend/server/src/base/prisma/index.ts`

机制如下：

1. `server.ts:64` 注册日志 sink，每次事件都调用 `localMindLogs.write(input)`。
2. 普通运行日志的 `write()` 进入 `persist()`，每条事件单独开启 Prisma transaction，调用 `persistRuntimeBatch(tx, [record])`。
3. 单条事务执行 advisory lock、跨日志与归档表的 event ID 去重、日志插入；数据库触发器还会插入全局 event ID 表，并维护相关索引。
4. 虽然存在 `writeBatch()`，上述通用 sink 没有使用它，也没有在该入口限制在途写入并发。
5. 日志服务注入的 PrismaClient 与业务服务来自同一个全局 `PrismaFactory` 实例，共用数据库连接池。

代码入口：

- [日志 sink](../packages/backend/server/src/server.ts)
- [日志持久化与补写](../packages/backend/server/src/base/logger/localmind-log-service.ts)
- [全局 Prisma 实例](../packages/backend/server/src/base/prisma/factory.ts)
- [HTTP 完成日志](../packages/backend/server/src/middleware/timing.ts)
- [GraphQL 完成日志](../packages/backend/server/src/base/graphql/logger-plugin.ts)
- [日志全局 ID 触发器与分区](../packages/backend/server/migrations/20260913013000_localmind_log_partitions/migration.sql)

HTTP 和 GraphQL 两层分别产生完成日志，一次正常 GraphQL 请求通常对应两条运行日志。日志调用虽然没有被业务代码直接 `await`，仍会争用同一个连接池、数据库缓存和磁盘。因此，“异步记录日志”并不等于“日志开销与业务隔离”。

**结论强度：已确认实现机制和现场资源竞争。** 尚未通过关闭日志、隔离连接池等对照实验量化其对单个请求延迟的贡献；本轮不会为实验修改云端。

### 3.2 权限轮询是需要优先复现的请求放大路径

当前本地源码中的 [GuardService](../packages/frontend/core/src/modules/permissions/services/guard.ts) 存在以下行为：

- `guard.ts:41` 对被订阅的文档逐一刷新权限；已确认管理员角色时提前返回。
- `guard.ts:56` 每 5 秒触发一次；窗口重新聚焦或网络恢复也会触发。
- `guard.ts:268` 按 docId 分组。同一文档通过 `exhaustMap` 避免这一通路自身重叠，但不同文档之间没有统一并发上限。
- `can()` 会直接加载权限，不完全等价于经过上述分组通路，因此初次加载、列表和其他消费者之间的合并程度也需要测量。

这些机制与现场大量 `getDocRolePermissions` 请求相符，但线上前端 bundle 尚未核对，用户当时打开的页面、角色、文档数量、标签页数量也未完成关联。因此不能把“某个页面每 5 秒轮询全部文档”写成已确认的现场事实。

### 3.3 列表权限结果等待可能放大用户感知延迟

当前本地 `guard.ts:186` 的 `readableDocIds$()` 先以最多 4 路并发检查全部候选文档，等待 `Promise.all` 完成后，才转入权限结果订阅；初始值为空集合。

[WorkspaceResourceExplorer](../packages/frontend/core/src/components/native-files/resource-explorer.tsx) 把当前文档组中的候选文档交给这一方法；侧栏节点和搜索也有调用入口。

当每次权限请求已经耗时数秒时，列表可能需要等待多轮检查，而不是第一批文档返回就逐批展示。此机制能够解释“单个请求十几秒，整个列表却更久才出现”的可能性，但尚未在本轮实际卡住的浏览器页面上确认。需要分别记录首个可见结果、全部结果可用和 UI 可交互时间。

## 6. 现有代码为什么会放大延迟

本节基于 2026-10-31 的本地工作树。除第 3.1 节已核对的文件外，不把本地行为自动等同于线上版本。下面说明设计原意、实际执行成本和需要修正的边界，而不是否定权限校验或可靠日志本身。

### 6.1 一次读取判断被扩展成完整权限计算

调用链为：

```text
资源列表、搜索结果、侧栏节点
  → GuardService.readableDocIds$(ids)
  → can('Doc_Read', id)
  → loadDocPermission(id)
  → GuardStore.getDocPermissions(id)
  → getDocRolePermissions GraphQL
  → workspace → doc → permissions 三层 resolver
  → PermissionService → PermissionContextLoader → 数据库与权限计算
```

[GraphQL operation](../packages/common/graphql/src/graphql/doc-role-permissions.gql) 请求读取、更新、删除、发布、成员管理、评论等 17 个权限字段。服务端 [builder.ts 的 `permissions()`](../packages/backend/server/src/core/permission/builder.ts) 传入的是整个 `DOC_ACTIONS`，不会因为调用方只想知道 `Doc_Read` 就只计算读取权限。

在正常存在的文档路径上，[WorkspaceResolver.workspace](../packages/backend/server/src/core/workspaces/resolvers/workspace.ts) 先检查 `Workspace.Read` 并加载 Workspace，[DocResolver.doc](../packages/backend/server/src/core/workspaces/resolvers/doc.ts) 再读取文档信息并检查 `Doc.Read`，`permissions()` 随后再加载权限上下文。`PermissionContextLoader` 已缓存请求内的 quota runtime，但没有对所有成员、目录策略和文档授权查询统一做请求内合并。一次 HTTP 请求不等于一次 SQL。

还有一个不直观的成本：[PermissionService.evaluateLoaded](../packages/backend/server/src/core/permission/service.ts) 发现所求 actions 包含受运行状态限制的写动作时，会调用 `WorkspacePolicyService.getWorkspaceState()`，再失效 quota runtime 缓存。完整权限查询包含这些写动作，即使最初消费者只需要读取判断，也会走这条检查路径。[policy.ts](../packages/backend/server/src/core/permission/policy.ts) 在 quota 已知且新鲜时只读当前状态；未知、陈旧或到期时才进入 reconcile，**不能描述成每次权限查询都重算或写配额**。

原意是复用一个完整权限结果支撑菜单和按钮，避免各动作规则分叉。问题是列表可见性属于高频、窄需求，却支付了完整交互权限的成本。应把“候选文档是否可读”和“当前文档有哪些操作权限”区分为同一领域服务上的两种查询形态。

已有可复用实现是 [PermissionService.batchDocPermissions / filterReadableDocs](../packages/backend/server/src/core/permission/service.ts) 和 [PermissionAccess.docs](../packages/backend/server/src/core/permission/builder.ts)。`PermissionContextLoader.load()` 已能接收多个 docs，文档策略与授权使用集合查询。优先接通这条路径，不另写一套较弱的 SQL 鉴权逻辑。

### 6.2 局部并发上限不能控制整个页面

`readableDocIds$()` 内部最多 4 路，但上限只属于**这一次方法调用**。[侧栏文档节点](../packages/frontend/core/src/desktop/components/navigation-panel/nodes/doc/index.tsx) 每个节点调用 `readableDocIds$([docId])`；资源列表和搜索还会独立调用。因此多个消费者的 4 路上限可以叠加，不能视为整个 Workspace 的全局上限。

`GuardService` 的周期刷新每 5 秒遍历所有已订阅文档，`groupBy(docId) + exhaustMap` 只抑制同一分组内重叠，不限制不同文档并发，也不覆盖 `can()` 直接调用的请求。当前 `observedDocs` 表示有订阅，未必等于屏幕视口内可见；列表级订阅可能覆盖尚未滚动到的所有结果。已确认管理员角色时跳过刷新，这个例外必须保留在分析中。

作为容量模型，假设非管理员、每次请求在 5 秒内完成、每个标签订阅 N 个不同文档、K 个标签同时运行，仅周期检查就约为 `K × N / 5` 次请求/秒。例如 N=100、K=2 时约 40 次/秒；按两个完成日志估算，又产生约 80 条运行日志/秒。这是说明规模关系的模型，**不是对现场文档数或标签页数的反推**。请求变慢后，`exhaustMap` 会跳过部分触发，实际速率还受排队、其他通路与重试影响。

原意是及时反映权限撤销、避免相同文档重复请求。缺少的是跨入口的请求合并、统一预算和生命周期管理，而不是把 5 秒机械改成 60 秒。

### 6.3 全量等待把单次慢请求放大成列表长时间空白

`readableDocIds$()` 执行全部检查后才返回 `checked`，再订阅 `can$()`，此前只发出空集合。它保障新搜索不先暴露旧缓存中的可读内容，但把“未验证的条目不可展示”扩大成了“所有条目都验证完才展示结果”。

假设单次检查耗时都为 t、不重试且持续使用 4 路，N 个候选的这一阶段约需 `ceil(N / 4) × t`。例如 N=100、t=1 秒，约需 25 秒才结束该阶段；这仍是说明机制的模型，不是实测耗时。

不能简单删除权限等待。可安全改成：每一批结果只有在服务端授权成功且身份与版本仍有效时才发布；未验证条目保持不可见，拒绝条目移除，首屏不等待后台候选。不同请求快照发生漂移时要丢弃或重读，不能把分批展示实现成旧授权与新目录的混合。

另外，`checked.add(id)` 不等于授权成功：代码随后以 `can$()` 的结果为 true 才显示，因此不能把“false 结果也加入 checked”误报成直接越权。

### 6.4 取消、重试和状态传播还没有形成统一边界

[fromPromise](../packages/common/infra/src/livedata/ops.ts) 在取消订阅时触发 AbortSignal；`readableDocIds$()` 只用它停止后续循环，已经启动的 `can()` → `GuardStore.getDocPermissions()` 没有接收并传给 GraphQL 的 signal。因此停止订阅不代表已经发出的 HTTP 请求立即停止，也没有在这条写入 `docPermissions$` 的路径上看到目录 store 那样的 generation 校验。旧结果是否会覆盖新的撤销结果，需要专门的乱序返回测试。

`revalidateDocPermission` 对剩余错误使用无限次 `backoffRetry`。该工具按 200 ms 起始、指数增长、15 秒封顶重试，没有 jitter；401/403/404 已在 `loadDocPermission` 中转换为拒绝，但其他错误仍可能长期占用重试通路。当前代码不具备按隐藏页面暂停、共享 Retry-After 或统一重试预算的机制。

每个权限结果还会展开复制整个 `docPermissions$` 对象，再通知订阅者。大量文档同时返回时会重复复制和计算；`can$` 的前后值比较可以减少向外发射，却不能消除前面的所有工作。这是需要 profile 的次要 CPU 成本，不是已证明的云端 I/O 主因。

### 6.5 已有目录快照很好用，但不能无条件当作全部文档权限

[DirectoryAccessStore](../packages/frontend/core/src/modules/organize/stores/directory-access.ts) 已有几项可复用机制：

- 监听资源、Workspace access 和 directory policy 变化；权限相关事件先清空旧数据再刷新。
- 用 account generation、请求 generation 和 AbortController 防止旧请求污染新身份状态。
- 合并多个订阅的 ready/reconnect 信号，避免同一初始化重复刷新。
- 跨页比较 `revision`、`authorizationRevision`、`fullSyncAllowed` 和 root rights，拒绝混合快照。
- 对 429 尊重 Retry-After 或退避，并限制页面数和总条目数。

这比再引入一套通用数据访问层更接近当前项目。但有两个边界：第一，目录 `rights.canWrite/canOrganize` 不是完整的 `Doc_Update/Doc_Publish` 等权限；只能复用已经检查的可见性和目录能力，不能直接映射成正文写入许可。第二，[workspaceDirectory resolver](../packages/backend/server/src/core/doc/directory-resolver.ts) 每次请求都读取和授权完整候选集，按最多 500 篇调用现有文档批量鉴权，最后才截取 100 条返回。分页限制了响应大小，尚未使全部计算变成按页的成本。

[readDirectory](../packages/backend/server/src/core/doc/workspace-organization.ts) 还会遍历路径、检查原生资源，在相应页面树分支逐个校验页面祖先。重复页请求可能重复这些工作。客户端则拉完所有分页后才发布集合，这又是一处全量等待。

这些做法保护了祖先可见性、实时 ACL 和跨页一致性。优化需要保留这些语义，分别研究按需授权投影、请求内批量祖先检查和带版本的分页；不能把原始 Yjs 表直接交给客户端过滤，或直接把 slice 提到授权前而改变分页可见性和游标契约。

### 6.6 日志的异步写法没有限制资源占用

核心代码仍是：

```ts
LocalMindLogService.registerSink(input => {
  void localMindLogs.write(input).catch(() => undefined);
});
```

`void` 只让调用方不等待，不限制任务数量。每条日志仍构造记录、申请同一个 PrismaClient 的事务、去重、插入和提交。处理速度下降后，在途 Promise、记录和上下文的存活时间变长；等待者也消耗内存。只在最后套一个并发信号量，而让前面无限创建等待 Promise，仍然不能限制总量。

每个 GraphQL 请求通常生成 HTTP 和 GraphQL 两条完成事件；两者提供的信息不同，不是简单重复错误。但它们都进入高成本持久化路径，使“读取权限”附带了持续写入压力。

已有 `writeBatch()` 可以减少事务往返，但不能直接把全部输入丢给它：它用 `inputs.slice(0, 100)` 取前 100 条，调用者必须分块并正确处理每条结果；批量大小也不等于全局排队上限。若未来允许合并，必须覆盖所有日志入口和补写，而不只优化一个调用点。

在约 50 条/秒的假定流量下，若按实验参数“最多 100 条或等待 200 ms”合批，通常每批约 10 条、每秒约 5 批，并不会自动得到 100 倍收益。批量主要降低事务与 SQL 往返，仍有每条记录的索引维护成本。

### 6.7 故障缓冲和清理也会反向增加负担

`spoolRuntime()` 对成功进入缓冲的普通失败事件，再尝试追加一条 `log.ingestion.degraded`；同名降级事件被排除，因此不是无限递归。[spool.bytes()](../packages/backend/server/src/base/logger/spool.ts) 每次列出并排序全部 JSON 路径，再逐文件 stat。一次追加前后可能多次检查容量，N 个文件、C 个并发检查会放大枚举工作和路径数组保留量。`append()` 的容量检查与写入之间也没有原子预留，不能把磁盘字节上限当作在途内存上限。

`flushSpool()` 每轮最多读 100 个文件，逐条事务补写，定时周期 15 秒。在每轮都能于周期内完成且全成功的理想条件下，定时路径最多约 6.7 个文件/秒；慢库、失败退出或附加降级文件会进一步降低有效净排空能力。实际吞吐还可能受其他调用入口影响，不把此数值当作现场实测。

`cleanupRetention()` 在同一事务中先 count 全部过期行，再 deleteMany，没有分批提交；锁能避免清理并发，却不会缩小事务工作量。年分区与 30 天运行日志保留期也不匹配。小数据量时逻辑直接，大数据量时删除、触发器、索引和 WAL 成本会集中出现。

相关的 [OOM 专题第 2—5 节](localmind-logging-heap-oom-investigation.zh-CN.md)记录了后续证据：V8 OOM、七次事务过期的清理失败，以及 8,305 个合成文件上对真实 `bytes()` 的独立本地实验。该实验在 64 并发时，运行中 GC 后堆达到约 206.6 MiB，结束后回落至约 20 MiB。它证明容量检查的并发内存放大，不证明存在永久泄漏，也不能直接解释线上全部 4 GB 堆。这些结果来自已有专题，本轮没有重跑或连接云端。

因此需要区分两个阶段：10 月 30 日早期记录的是业务请求慢、日志 I/O 竞争；后续专题记录的是进程因 OOM 失去响应。不能用早期首页 200 的结论描述后续不可用状态。

## 7. 适合 LocalMind 的优化设计

> 2026-11-01 复核：本节方向保留，优先级和普通运行日志的持久化要求已由第 11.5、11.6 节修订。

以下是建议设计，未修改代码、产品权限契约或运行参数。优先扩展现有 service、store、领域方法和日志持久化设施。

### 7.1 用两条有界链路取代分散发起

```text
页面可见性需求
  → 同一身份与作用域的请求协调器
  → 合并重复 docId，限制总候选与在途批次
  → 现有 batchDocPermissions，只求需要的动作
  → 版本和 generation 校验
  → 分批发布已授权的首屏结果
  → 变更事件失效，重连补读，有限的兜底校验

普通运行日志
  → 脱敏与总字节限制
  → 有界准入与持久化接收点
  → 数量、字节、时间三重约束的批次
  → 有限写入并发和数据库资源预算
  → 幂等提交，确认后推进 checkpoint

业务审计
  → 保留所属业务事务或可靠 outbox 的既有契约
  → 不进入普通日志采样或可丢弃队列
```

### 7.2 权限查询统一调度，服务端批量判定

在 `GuardService` 或同模块新增职责明确的协调器，让直接 `can()`、周期刷新、列表初始化走同一条读取调度路径。至少包含：

| 维度     | 设计要求                                                                                                               |
| -------- | ---------------------------------------------------------------------------------------------------------------------- |
| 作用域   | server、账号 generation、workspace、显式 project scope、docScope 和所需 actions 都影响结果身份；禁止跨账号、跨项目复用 |
| 请求合并 | 相同作用域与 docId 的在途读取共用结果；短窗口合并不同 docId，单批数量有上限                                            |
| 总预算   | 同时限制排队候选、等待者、在途批次和字节，不能只有每批上限                                                             |
| 优先级   | 当前文档与视口可见结果优先；背景候选不阻塞首屏，避免低优先级永远饥饿                                                   |
| 取消     | 贯穿 coordinator、store、GraphQL 的 AbortSignal；共享请求只有无消费者后才能取消                                        |
| 结果提交 | 校验身份、generation 和授权失效状态；旧请求即使成功也不得恢复已经撤销的结果                                            |
| 重试     | 401/403/404 保持拒绝；429 遵守 Retry-After；瞬态错误有 jitter、预算和可见错误状态                                      |

服务端优先复用 `batchDocPermissions`。对外 batch operation 还需定义候选数量、actions、输入大小、整体成本和无权限文档的非枚举式结果；缺失与拒绝不能泄露额外存在性信息。批量 HTTP 不等于数据库批量，内部必须共享 Workspace 上下文并使用集合查询。

只求 `Doc.Read` 的列表与当前文档的完整操作权限分开。写操作提交时仍由领域服务执行实时 ACL、版本和编辑租约检查，不接受客户端缓存作为写入授权。

### 7.3 复用事件与快照，减少周期性全量查询

复用 DirectoryAccessStore 的权限变化清空、重连补读、generation 和跨页校验机制。先盘点每一种文档授权变更是否已经产生可接收的失效事件；不能假设 Workspace access 或 directory policy 事件涵盖全部 Doc grant。

有事件覆盖的可见集合采用“读取快照 → 订阅失效 → 合并补读”；通知只负责使数据失效，不携带可长期信任的授权。事件可能丢失或跨重连存在缺口，所以保留有界兜底校验，并明确撤销收敛的时间目标。隐藏标签暂停可选刷新，恢复可见时先校验再展示受保护缓存；后台写行为仍服务端检查。

现有 `authorizationRevision` 是由可见授权快照计算的 hash，不能当作单调递增序号比较大小，也不能凭空用它判定事件序列完整。若需要版本增量协议，必须另行定义版本语义和断档恢复；第一阶段可直接复用重新读取与相等性校验。

目录分页的优化分两步：先批量加载祖先与候选权限，减少单次快照内的重复 I/O；再评估有界、带授权依赖版本的分页投影。保留原来按请求读取存储和实时检查 ACL 的保证，不能直接把 actor rights 放进 30 秒无条件缓存。只缓存不含授权结论的解析结果是现有实现的合理边界。

### 7.4 首屏分批可用，并区分空、未知和失败

将列表状态拆成首批加载、部分结果可用、后台加载、明确失败。已经由当前有效快照授权的行可以先显示；未确认行不得先展示标题、摘要再事后隐藏。空结果只表示检查完成且没有可见结果，不能同时代表未检查或失败。

搜索条件变化、账号切换、目录版本漂移或权限撤销时取消旧批次并使旧结果失效。跨页快照一致性的策略先定义清楚：已发布页面所属快照失效后，移除或重新验证，不能为了“渐进展示”混合快照。

现有实现等待完整集合提供了简单的一致性边界；如果第一阶段还不能安全实现分批快照，可以先通过服务端批量鉴权减少整个集合的等待，随后再做渐进 UI。

### 7.5 普通日志建立持久化的批量消费者

详细机制与 [OOM 专题第 7 节](localmind-logging-heap-oom-investigation.zh-CN.md)保持一致。本篇只列出对页面性能直接相关的设计决定：

1. **先准入，再创建异步工作。** 预算覆盖等待、在途、文件操作、回执和镜像缓冲。队列满时不能继续保留无限 Promise；普通日志按明确策略处理，审计不静默丢弃。
2. **明确持久化确认点。** 不以进程内数组或 worker 消息队列作为已接收日志的最终保障。复用并修正 spool，使用持久卷、稳定 node identity、可恢复批次和 checkpoint；区分原子 rename、进程崩溃恢复与掉电落盘保证。
3. **按记录数、字节和最大等待时间合批。** 通过受限的 `writeBatch` 路径落库，超出 100 条时分块；成功、重放已存在、进入待补写、未接收等结果不能混成一个“成功”。
4. **为实时写入与补写分配总预算。** 补写不应抢占全部业务连接，也不能长期饥饿。采用有限消费者、退避和熔断；日志自身失败只按状态转换或时间窗口汇总，避免逐事件再制造文件。
5. **普通日志与审计分开处理。** 成功请求的运行日志可按明确策略采样或合并 HTTP/GraphQL 摘要，并以不含正文的计数说明采样；错误、安全拒绝、审批与副作用证据按对应保留契约处理。不能把现有审计改成 fire-and-forget。
6. **资源隔离作为补强。** 若限流与合批后仍有明显池竞争，可为普通运行日志配置小型专用池或独立 writer。审计继续参与业务事务；各副本总连接数受数据库预算约束。单独连接池并不隔离同一磁盘和 WAL。

不主张为这次问题强制部署 Kafka、ELK 或外部 Collector，也不把 stdout 改成真相源。成熟系统的机制可以内置到 LocalMind 现有部署边界中。

### 7.6 保留幂等，调整维护粒度

日志去重同时涉及在线分区、全局 ID 登记、归档记录和审计不可变约束。改成批量后先保留现有幂等语义和锁顺序，测量收益；后续如需收敛到一个权威 event ID 接收登记，应把在线、已归档、保留期删除和重放规则一起设计。**只删除 UNION 查询、全局 ID 表或 advisory lock 都没有充分依据。**

清理先改为有数量与时间预算的小批推进，避免正式删除前依赖全量 count；预览可独立计算，删除回执使用已提交数量。每批重新检查 freeze/legal hold，记录持久进度与失败原因，给业务留出 I/O 余量。

日/月分区属于下一阶段方案。当前表混合不同保留期，且存在 ID 删除触发器；直接 DROP 分区既可能删掉未到期数据，也不会自动执行逐行删除触发器完成登记维护。必须先验证归档、登记生命周期和审计约束，再决定分区策略。[PostgreSQL 16 分区说明](https://www.postgresql.org/docs/16/ddl-partitioning.html)

VACUUM、索引统计与缓存调优用于处理剩余的存储成本；普通 VACUUM 的空间复用不等于文件立即缩小，VACUUM FULL 还需要重写和强锁，不是本次只读排查的操作。[PostgreSQL 16 维护说明](https://www.postgresql.org/docs/16/routine-vacuuming.html)

## 8. 成熟项目中值得借鉴的做法

资料核对日期为 2026-10-31，仅采用项目维护者和官方文档。下面“借鉴”是基于 LocalMind 代码的设计判断，不表示这些项目已验证了 LocalMind 的故障或保证相同性能。无需为借鉴机制迁移整套技术栈。

| 来源                                                                                                                           | 原项目的做法                                                                 | LocalMind 的应用与边界                                                                                                                                    |
| ------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [GraphQL DataLoader](https://github.com/graphql/dataloader#batching)                                                           | 合并同一调度窗口的 key，批量加载；缓存通常按请求创建，结果必须与输入顺序对应 | 扩展现有 PermissionContextLoader 与 batchDocPermissions，复用同一请求中的公共上下文；它不能自动合并浏览器发出的独立 HTTP 请求，也不允许跨用户共享授权缓存 |
| [TanStack Query 生命周期](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults)                    | 将 stale、挂载、重新聚焦、重连和轮询分开配置                                 | 在现有 RxJS service 中显式定义刷新原因和预算；不能把通用缓存的 staleTime 直接当作安全权限的有效期                                                         |
| [TanStack Query 取消](https://tanstack.com/query/latest/docs/framework/react/guides/query-cancellation)                        | 为查询提供 AbortSignal，传到底层请求后才能实际取消网络工作                   | 补全 GuardStore 的 signal 与 generation 链路；取消客户端等待不保证已经提交到数据库的查询也被取消                                                          |
| [Kubernetes list/watch](https://kubernetes.io/docs/reference/using-api/api-concepts/#efficient-detection-of-changes)           | 先取带版本的集合，再观察变化；历史版本不可用时重新 list                      | 借鉴“快照、失效、重连补读”的完整协议，复用现有 realtime；不需要引入 Kubernetes，也不能把当前 hash 版本当作可排序游标                                      |
| [OpenTelemetry 批处理](https://github.com/open-telemetry/opentelemetry-collector/blob/main/processor/batchprocessor/README.md) | 数量和时间触发发送，另设批次硬上限                                           | 普通日志采用数量、字节、时间阈值；批次阈值与硬上限、全局队列预算分别定义，不复制 Collector 默认值                                                         |
| [OpenTelemetry 持久队列](https://opentelemetry.io/docs/collector/resiliency/)                                                  | 有界队列、退避、持久化 WAL 和恢复机制；满载与耗尽仍可能丢数据                | 借鉴明确接收与恢复状态；普通 telemetry 的丢弃规则不能用于 LocalMind 业务审计，默认不向外部发送                                                            |
| [Pino transports](https://github.com/pinojs/pino/blob/main/docs/transports.md)                                                 | 把日志传输与变换放到独立线程或进程                                           | 需要时隔离序列化与 I/O；worker thread 不会自动解决数据库竞争或无界消息队列，不能单靠更换 logger 完成修复                                                  |
| [Node Streams 背压](https://nodejs.org/learn/modules/backpressuring-in-streams)                                                | 消费端用容量信号让生产端暂停，并在可继续时恢复                               | 预算必须从日志入口一直覆盖到写入与 stdout 镜像；如果在 Stream 外无限创建任务，仍会积压                                                                    |
| [PostgreSQL 分区约束](https://www.postgresql.org/docs/16/ddl-partitioning.html#DDL-PARTITIONING-DECLARATIVE-LIMITATIONS)       | 分区表唯一约束需要覆盖分区键，不能天然保证任意跨时间 event ID 唯一           | 当前全局 ID 登记有存在理由；优化应调整批次与登记生命周期，不能凭局部分区唯一键删掉全局幂等                                                                |

这些实现共同值得借鉴的是：工作有明确所有者、输入有上限、结果有版本或确认点、失效和故障有恢复规则。减少“每个调用点各自发起异步工作”，通常比在原有扇出之上增加机器或超时更容易验证和维护。

## 9. 本地验证设计与验收标准

### 9.1 先建立可比较的基线

复用本机 Linux 容器，新增合成数据时使用独立测试数据库或专用 fixture，不覆盖现有热启动数据，不拉取云端数据库。测试过程阻止误发外部通知、provider 和工具调用。生产构建与开发 HMR 分开测量；本地和云端 Node、架构、存储、源码不同，只能用本地同条件前后对照证明改进。

使用管理员、普通成员和文档受限访问角色；文档规模 1/20/100/250，单标签与多标签；覆盖首次进入、刷新、搜索、切换 Workspace、重新聚焦和隐藏页面。每组记录冷/热缓存、日志规模、spool 文件数、后台任务和固定版本。共享开发机上的其他任务需要记录，不能只挑最快一次。

保留完整故障链与单因素实验：先量化纯权限请求，再量化附带日志；改变一个变量后与同一基准对比。测试 harness 中隔离普通运行日志写入可作为因果实验，但不关闭真实审计或把这种配置直接作为交付方案。

### 9.2 同时测端到端体验与内部成本

| 层次         | 必须采集的指标                                                                 | 防止误判                                            |
| ------------ | ------------------------------------------------------------------------------ | --------------------------------------------------- |
| 页面         | 首个已授权结果、列表可交互、全部必要结果完成、加载/错误状态持续时间            | HTML 200、骨架出现或基础 GraphQL 成功不等于页面可用 |
| 请求         | 每次导航与每分钟 operation 数、唯一 docId 数、峰值并发、取消、重试、响应体大小 | HTTP 请求少不代表内部 SQL 少                        |
| 领域与数据库 | 每批 SQL 数、事务数、池排队时间、在途连接用途、读块与 WAL 增量                 | 区分 SQL 执行慢与申请连接慢                         |
| 日志         | 事件生成率、准入/采样计数、队列与在途字节、批次大小、确认延迟、最老积压年龄    | 只观察写入吞吐会漏掉不断增大的等待队列              |
| 进程与主机   | heap、GC 后保留量、RSS、事件循环延迟、I/O wait、磁盘延迟                       | RSS、日志表大小与 spool 正文字节不是同一指标        |

### 9.3 必须覆盖的实验

| 编号 | 实验                                       | 判断标准                                                                        |
| ---- | ------------------------------------------ | ------------------------------------------------------------------------------- |
| T01  | 单文档与 100/250 文档列表                  | 前台请求由批次预算控制，不随组件数量突破并发上限；记录端到端 P50/P95            |
| T02  | 侧栏、列表和搜索同时读取同一组文档         | 在途同 key 合并；不能每个消费者各自形成一套 4 路并发                            |
| T03  | 某一批权限响应延迟                         | 已验证的首屏结果不等待无关批次；未知或拒绝内容始终不可见                        |
| T04  | 切页、切账号、权限撤销后旧响应晚到         | 旧响应不恢复旧身份或旧授权结果；取消不误伤仍有消费者的共享请求                  |
| T05  | 事件丢失、断线重连、授权 hash 变化         | 清空或校验失效结果并补读；不混合分页快照，撤销收敛时间可测                      |
| T06  | 目录多页与深祖先链                         | 记录每页的完整计算成本，批量祖先鉴权与原语义等价；目录权利不能扩展成正文权利    |
| T07  | 约 30 次权限请求/秒及附带日志              | 对比逐条与批量写入的事务数、池等待与页面 P95；吞吐提高同时检查积压是否持续增长  |
| T08  | 数据库慢、不可用、恢复                     | 内存和等待者有硬上限，持久回执正确，补写恢复不抢占全部业务容量                  |
| T09  | 8,305 及更多合成 spool 文件                | 追加成本不再依赖每条全目录扫描；覆盖并发追加、删除与容量预留，复用 OOM 专题实验 |
| T10  | 日志提交前后崩溃、重复批次、已归档事件重放 | 无静默漏记、重复生效或首条证据被覆盖；恢复 checkpoint 正确                      |
| T11  | 千万行合成历史日志及清理                   | 小批事务持续提交；冻结可及时停止；不能用清空测试库伪造改善                      |
| T12  | 日志优化下的权限和审计回归                 | Workspace/Project 隔离、实时写 ACL、拒绝路径、审计不可变、legal hold 全部保留   |

已有 [GuardService 测试](../packages/frontend/core/src/modules/permissions/services/guard.spec.ts)覆盖单次调用的四路上限、拒绝与撤销；已有 [日志集成测试](../packages/backend/server/src/base/logger/__tests__/localmind-log-ingestion.spec.ts)覆盖重放与归档幂等。这些应保留，但不能替代多消费者、长时间慢库和高积压测试。

验收先看结构性约束：请求数与总并发可预测、积压与内存有界、失效与重放正确；再确定用户体验目标。基线未完整建立前，不承诺“优化后必定 200 ms”或固定百分比。短时稳定后，还需要覆盖原始约 8 小时生命周期的持续运行，观察退化是否重现。

### 11.2 是不是同一个问题

**是同一次故障、同一个进程、同一条因果链的两个阶段。** 页面慢是持续存在的前半段；OOM 是负载叠加到日志降级后的后半段。

| 证据     | 本文                                | OOM 专题                                       |
| -------- | ----------------------------------- | ---------------------------------------------- |
| 进程     | 现场“运行约 7—8 小时、重启 0”       | 故障进程 03:24:32Z 启动，11:21:12Z OOM         |
| 采样时间 | 第 2.1 节窗口为 10:49:11Z—10:52:42Z | 10:44Z 起日志持续降级落盘，10:46Z 堆约 870 MiB |
| 首要请求 | `getDocRolePermissions` 占 96.4%    | 同一 operation 占全进程 93.6%                  |
| 数据库   | 日志两表占读取块增量 99.8%          | 直接引用本文第 2.2 节样本                      |

因此，第 2.1 节的中位 6,870 ms 取自 OOM 前约 30 分钟的故障末段，不能代表常态。同一进程全程的权限查询中位耗时为 1,792 ms（OOM 专题第 2.3 节）。

**重启后，后半段消失，前半段仍在**（第 11.3 节）：spool 为 0，RSS 约 0.9 GiB，没有 OOM 迹象；但权限轮询、日志随机读、连接池被日志占满、保留清理每小时失败都依旧存在。

```text
① 前端权限轮询扇出：全部被订阅文档每周期同时发出
② 每个请求：约 16 条业务 SQL + 2 条逐条事务的完成日志，共用约 17 个连接
③ 日志随机读占满磁盘与连接池；保留清理每小时失败并制造尖峰
   → 页面加载慢（本文）                                  ← 重启后仍在
④ 日志事务超时转入 spool，扫描按“并发 × 文件数”放大
   → V8 堆耗尽 → 进程不退出（OOM 专题）                   ← 重启后暂未出现
```

修好 ④（spool 计数、入口准入、stdout 上限、`init`）能防止再次宕机，但页面不会因此变快。页面要变快，必须削减 ①②，并缓解 ③。

两篇文档的分工：OOM 专题负责 ②③④ 的日志写入、降级与进程恢复；本文负责 ① 与 ② 中权限请求的部分，以及页面体验。同一修复项只在一处设计，另一处只引用。

| ----------- | ------------------------------------ | ------------------------------------------------------------------------------------------- |
| 07:20—07:24 | 每 60 秒一次 173 个，偶有 24 个      | 隐藏超过 5 分钟的后台标签页：5 秒定时器被 Chrome 深度节流为每分钟一次，但每次仍发出全部文档 |
| 08:40       | 每 5 秒 54 个，外加每分钟一次 173 个 | 一个前台标签页（54 篇）加上述后台标签页；54 × 12 + 173 = 821，与每分钟计数吻合              |
| 09:05       | 每 5 秒 85 个；09:05:34 一次 258 个  | 前台标签页增至 85 篇；258 = 173 + 85，两者同时触发                                          |

同一批请求在约 100 ms 内全部发出，耗时呈阶梯式上升：

- 08:40:02 的 54 个请求，耗时从 15 ms 逐级升至 192 ms，最慢 639 ms。
- 07:24:24 的 173 个请求，前 45 个的耗时就从 27 ms 升至 376 ms。

这说明延迟主要来自“同一时刻的并发请求互相排队”，而不是单个请求本身慢。数据库同时被日志读占用时，阶梯更陡。

规模对照：最大的 Workspace 约有 250 个 snapshot（含系统文档）。OOM 专题从峰值 42.8 次/秒反推“单标签约 214 篇”，二者同一量级。

### 11.4 现有代码是怎么写的，为什么会慢

#### 11.4.1 轮询从“一篇文档”被扩展成“全部候选文档”

| 版本                       | 行为                                                                                                                                                                                                   |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| AFFiNE `upstream/canary`   | `GuardService` 没有定时器，也没有 `observedDocs` 和 `readableDocIds$`。权限在打开文档或调用时按需加载，访问授权完全由服务端每次检查                                                                    |
| `bcf0018da9`（2026-09-04） | 只在 `docScopeId` 存在（单文档范围访问）时，每 5 秒刷新这一篇文档的权限                                                                                                                                |
| `f4a00b882a`（2026-10-25） | 改为每 5 秒刷新**所有被 `can$` 订阅的文档**，并新增 `readableDocIds$`。资源列表、侧栏文档节点、文档搜索（两处）、快速搜索最近文档、链接搜索 6 个入口把候选文档逐篇交给它，检查后再逐篇建立 `can$` 订阅 |

这里的设计错误是：把单文档场景的刷新机制原样套到列表上，没有改变它的成本模型。列表有多少篇文档，就有多少个 5 秒周期请求。管理员或 Owner 角色会被提前放行，所以请求全部来自普通成员的标签页。

#### 11.4.2 为什么会形成突发

`refreshObservedPermissions` 在同一个定时回调里同步遍历全部文档，逐个调用 `revalidateDocPermission`。`groupBy(docId) + exhaustMap` 只阻止同一篇文档的请求重叠，不同文档之间没有全局并发上限。所以每个周期就是 N 个请求同时发出。

后台标签页被浏览器节流后，频率降到每分钟一次，但每次仍是同时发出 N 个；它节省的是 CPU，并没有降低服务端的瞬时并发。HEAD 中的 `can()` 直接调用 `loadDocPermission`，也不与轮询合并。

#### 11.4.3 为什么列表会长时间为空

`readableDocIds$()` 先以 4 路并发检查全部候选文档，`Promise.all` 结束后才发布结果，此前持续发出空集合。

[resource-explorer.tsx](../packages/frontend/core/src/components/native-files/resource-explorer.tsx) 用这个集合过滤分组。而“加载中”的判断只看 catalog、查询和文档列表是否就绪，并不看权限检查是否完成。所以权限检查进行期间，页面显示的是“暂无资源”，而不是“加载中”。这是本文第 3.3 节“可能放大体感延迟”的具体表现。

按 `ceil(N / 4) × t` 估算，N = 214 时：

- t = 0.2 s：约 11 秒；
- 故障期中位数 t = 1.8 s：约 96 秒。

两者都是机制估算，不是浏览器实测。

#### 11.4.4 服务端每个请求的成本

一次 `getDocRolePermissions` 在 quota 状态新鲜时，大约执行 16 条业务 SQL（不含会话认证）：

| 解析层                                                 | SQL                                                                                                           |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| `workspace()`：`Workspace.Read` 检查，再加载 Workspace | 成员、Workspace 策略、运行状态，加 1 次读取，共 4 条                                                          |
| `doc()`：读取文档信息，再检查 `Doc.Read`               | 文档信息，加成员、Workspace 策略、文档策略、文档授权（运行状态命中请求内缓存），共 5 条                       |
| `permissions()`：全部 17 个 `DOC_ACTIONS`              | Workspace 存在性、quota 状态；随后作废运行状态缓存，重新加载成员、策略、运行状态、文档策略、文档授权，共 7 条 |

也就是说，同一个请求把权限上下文加载了三遍，最后一遍还计算了列表根本不需要的 16 个写入、发布、管理类动作。

`PermissionContextLoader.load()` 用 `Promise.all` 并行发出查询，一个请求可以同时占用最多 5 个连接。一个 54 篇文档的周期约产生 860 条业务 SQL 和 108 条日志事务，它们共同争抢约 17 个连接。这就是第 11.3 节阶梯式排队的服务端原因。

服务端其实已有正确的批量路径：`PermissionAccess.docs(docs, 'Doc.Read')` 与 `PermissionService.filterReadableDocs()`。`workspaceDirectory` 就是用它按每批 500 篇授权全部候选（本文第 6.5 节写的“最多 500 篇”应理解为每批 500 篇），只是资源列表没有用它。

#### 11.4.5 日志使请求成本翻倍，并与业务互相拖慢

每个成功的 GraphQL 请求写两条完成日志（HTTP 层与 GraphQL 层），每条是一个独立的交互事务：advisory lock、跨分区与归档表查重、插入，再由触发器写全局 ID 登记，并与业务共用连接池。日志表与索引远大于 128 MiB 的 `shared_buffers`，随机读要等约 70 ms 的磁盘。

`debug` 日志不受日志级别控制，同样入库（OOM 专题第 3.2 节；3 小时内约 2.2 万条）。保留清理每小时先做一次大范围 `count()`，再失败，什么也没删，表只增不减。这几项在 OOM 专题第 3.2—3.3 节有完整分析，本文不重复。

#### 11.5.2 遗漏

1. **同一周期的突发与后台节流。** 这是阶梯式延迟的直接机制。只设“每批上限”而不消除同时触发，问题仍会存在。
2. **服务端单次成本。** 三遍上下文加载、约 16 条 SQL、每次最多 5 个并发连接，对约 17 个连接的默认池。
3. **日志放大的另外两处。** `debug` 日志入库；`/api/logs/batch` 上传请求本身又产生 HTTP 完成日志。OOM 专题已覆盖。
4. **列表等待期显示“暂无资源”。** 用户感知是“没有内容”，而不是“加载慢”。
5. **线上仍处于故障条件。** 没有考虑这一点，因此没有给出可以立即上线的止血项。

#### 11.5.3 取舍上的问题

1. **优先级偏重。** 第 10 节把“固定隔离基线”放在 P0，止血排在建立完整实验之后。而线上目前只是靠重启维持，第 11.3 节表明故障条件全部还在。应先发布低成本、可回滚的削减项，再做基线对照。
2. **反对“把 5 秒改成 60 秒”只对一半。** 单独改间隔确实不够。但“打开的文档保持 5 秒、列表行 60 秒、页面隐藏时暂停、全局并发上限、同文档合并”这一组合，是合理的止血。服务端对每次读写都实时检查 ACL，前端刷新只影响界面提示，并不削弱授权。
3. **普通运行日志的持久化要求过重。** 第 7.5 节要求“明确持久化确认点”、持久卷、可恢复批次与 checkpoint。这适用于审计，不适用于可按策略采样的运行日志。它与[日志系统设计](localmind-logging-system-design.zh-CN.md)的采样策略不一致，OOM 专题第 5.6 节也已否定“正常路径先落盘”：磁盘正是瓶颈，先落盘等于再写一遍。运行日志只需要有界内存批次，数据库熔断时再转入 spool；审计保持原有契约。
4. **通用请求协调器、版本化增量协议、渐进式分批展示排得太前。** 这些方向本身合理，但成本高。接通批量接口后，N 篇文档只需 `ceil(N / 100)` 个请求，单次几十毫秒，渐进展示的收益会大幅下降。应先做批量，再按实测决定是否需要渐进展示。

### 11.6 推荐方案

#### 11.6.1 P0 止血（应尽快合入发布）

下表“本地已改”指 OOM 排查会话在工作树中的未提交实现，需要合入、聚焦测试并发布才对线上生效。

| #   | 修改                                                                                                                                                                      | 状态                                |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| 1   | 列表候选按排序后的 ID 集合判断变化，数组重建不再触发全量重查                                                                                                              | 本地已改（`resource-explorer.tsx`） |
| 2   | 列表、侧栏、搜索的订阅进入 60 秒刷新池，打开的文档保持 5 秒；页面隐藏时不刷新，恢复可见时刷新一次                                                                         | 本地已改（`guard.ts`）              |
| 3   | 全部文档权限请求共享 4 路全局并发上限，同一文档的在途请求合并；重试改为有限次数                                                                                           | 本地已改（`guard.ts`）              |
| 4   | 成功的 `/graphql` 与 `/api/logs/batch` 不再写 HTTP 完成日志；成功且不慢的 GraphQL 完成日志按 operation 汇总；`debug` 默认不入库；入口准入与熔断；spool 计数与 stdout 上限 | 本地已改，见 OOM 专题第 5.2 节      |

P0 发布后，第 11.3 节的指标会有以下变化：

- 后台标签页的请求降为 0；
- 前台每个周期的同时请求数不超过 4；
- 列表行请求频率降为原来的 1/12；
- 日志入库行数大致减半以上。

服务端单次成本仍然不变，所以 P0 之后仍需 P1。

#### 11.6.2 P1 根治扇出：批量 `Doc.Read` 查询

1. **服务端新增只读批量查询**，例如 `workspace(id).readableDocIds(docIds: [String!]!): [String!]!`：
   - 单次最多 100 个去重后的 ID，超限直接报错；
   - 内部一次调用 `ac.user(...).workspace(...).projectScope(null).docs(docs, 'Doc.Read')`，与 `workspaceDirectory` 同一授权路径；
   - 不带 `projectId`，即只用个人与 Workspace ACL，遵守 Workspace 直接访问的权限规则；
   - 只返回可读 ID，拒绝与不存在不可区分，不泄露存在性；
   - 一次请求约 6 条 SQL，与 N 无关。
2. **前端 `GuardService` 内做 DataLoader 式合并**：
   - 同一微任务或短窗口内的 `Doc_Read` 检查合并为批次，每批最多 100，全局最多 1—2 个批次在途；
   - 结果只写 `Doc_Read`，不伪造其他动作；
   - `readableDocIds$`、列表刷新池和侧栏都走批量；
   - 打开的文档和菜单仍取完整的 17 项权限；写操作提交时仍由服务端实时检查 ACL、版本和编辑租约。
3. **AbortSignal 从 `readableDocIds$` 传到 `GuardStore.gql`**；批次的所有等待者都取消后，才中止共享请求。
4. **日志写入路径**按 OOM 专题第 5.3 节执行：有界内存批量写入、服务端自生成 ID 跳过查重、日志使用 1—2 个连接的独立小池、保留清理改为小批提交。其中清理是重启后每小时仍在制造尖峰的直接来源，应与批量接口同批完成。

效果估算（机制推算，需按第 9 节实测）：

| 指标         | 现在        | 批量化后   |
| ------------ | ----------- | ---------- |
| HTTP 请求    | 214 个      | 3 个       |
| 业务 SQL     | 约 3,400 条 | 约 18 条   |
| 完成日志事务 | 428 条      | 每分钟汇总 |

#### 11.6.3 P2 事件失效取代轮询

- 盘点文档授权变更（文档授权、文档策略、Workspace 成员与策略、目录策略）是否都有实时事件。已覆盖的类型改为“快照 → 事件失效 → 合并补读”。列表刷新池降为“重新聚焦、重连时补读，加长周期兜底”，打开的文档保留短周期兜底。
- 资源列表评估直接复用 `DirectoryAccessStore` 中已经由服务端按 `Doc.Read` 授权的目录集合，前提是候选集与目录集合一致，并保留第 6.5 节的边界。
- 在批量查询的实测结果上，再决定是否需要渐进展示与跨页快照校验。

#### 11.6.4 P3 数据库与部署

`shared_buffers`、日志索引审查、按月按保留等级分区、spool 持久卷、`init: true`、存活检查和内存上限，按 OOM 专题第 5.4、5.5 节执行，本文不另设方案。

#### 11.6.5 不采用

| 做法                         | 原因                           |
| ---------------------------- | ------------------------------ |
| 取消权限刷新                 | 撤权后界面会长期显示旧权限     |
| 永久缓存 ACL                 | 违反实时 ACL 契约              |
| 只调大连接池或超时           | 磁盘读是瓶颈，长事务会更多     |
| 只加 Node 堆                 | 只能推迟 OOM，不能让页面变快   |

| 运行日志改为先落盘           | 磁盘本身就是瓶颈，等于再写一遍 |

### 11.8 验收补充

在第 9.3 节 T01—T12 之外，增加以下指标：

1. **同周期并发**：每个刷新周期内同时在途的权限请求数不超过全局上限；没有“一百毫秒内发出几十至数百个请求”的批次。
2. **后台标签页**：隐藏状态下权限请求为 0；恢复可见时只补读一次。
3. **列表首屏**：214 篇文档的列表在权限检查期间显示“加载中”；完成时间按批量请求数估算；不出现先显示“暂无资源”再出现内容。
4. **请求成本**：一次列表加载的权限 HTTP 请求数不超过 `ceil(N / 100)`；单个批量请求的业务 SQL 数与 N 无关。
