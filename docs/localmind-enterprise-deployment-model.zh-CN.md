# LocalMind 企业私有部署与客户端形态设计

## 1. 文档定位

本文描述 LocalMind 面向企业私有部署时的目标组织模型、使用场景和客户端形态。
它回答两个问题：

1. 一家公司应部署多少套 LocalMind；
2. 员工应通过浏览器访问，还是在每台电脑上运行独立客户端。

本文是产品与部署设计文档。具体的数据库、权限和 Project 行为仍分别以以下文档为准：

- [LocalMind 部署指南](localmind-deployment.zh-CN.md)
- [Project 原生资源](ai-modernization/tracks/project-native-resources.md)
- [Project 工作台重构](ai-modernization/tracks/project-workbench-redesign.md)
- [LocalMind 用户使用指南](localmind-user-guide.zh-CN.md)

## 2. 核心结论

一家公司部署**一个逻辑上的 LocalMind 实例**。这个实例可以由多台服务器、多个容器或高可用组件组成，但对员工表现为一个统一的内网地址，例如：

```text
https://localmind.company.internal
```

员工默认通过浏览器使用 LocalMind。桌面端和移动端作为可选入口，连接到同一个公司实例，不各自运行一套独立的 LocalMind 服务。

组织数据、Workspace、Project、AI 任务、审批、审计、模型配置和备份以公司实例为中心。客户端可以拥有本地缓存和离线能力，但不能形成另一套组织级真相源。

## 3. 企业组织模型

LocalMind 的对象层级如下：

| 层级      | 主要职责                                     | 示例                    |
| --------- | -------------------------------------------- | ----------------------- |
| 公司实例  | 统一身份、策略、AI 配置、审计、备份和集成    | 某集团的 LocalMind      |
| Workspace | 部门或稳定团队的知识与日常协作边界           | 研发部、销售部、人事部  |
| Project   | 有明确目标、周期或交付物的协作空间，可跨部门 | 客户 A 交付、年度预算   |
| 用户      | 通过成员关系获得 Workspace 或 Project 权限   | 研发成员参与客户 A 项目 |

Workspace 适合长期积累部门知识和流程，Project 适合围绕具体目标组织人员、文件、任务和 AI 工作。Project 与 Workspace 是平级对象，Project 拥有自己的文件树和资源。

Project 内部资源默认只属于 Project。只有用户明确要求时，才将资源发布或复制到指定 Workspace；项目内容不会因为来源关系自动回写部门文档，外部副本也不会自动回流到 Project。

## 4. 典型使用场景

### 4.1 部门日常工作

研发部在研发 Workspace 中维护技术规范、版本计划和架构决策；销售部在销售 Workspace 中维护客户资料、报价模板和商机记录。部门成员按照 Workspace 成员关系访问资料，AI 只检索其有权限读取的内容。

### 4.2 跨部门项目

“客户 A 交付项目”邀请销售、研发和交付成员加入 Project。项目成员在 Project 文件树中创建计划、会议纪要、风险清单和交付材料，AI 在项目范围内总结、生成任务或提出修改预览。

项目完成后，成员可以明确将最终方案发布到研发 Workspace，或将客户交付文档复制到销售 Workspace。发布操作使用目标 Workspace 的实际权限，并留下操作记录。

### 4.3 管理与审计

实例管理员在 Admin 中配置全局 Project BYOK、模型 Provider、任务路由和企业集成。管理员查看运行状态、审批记录、失败原因、执行回执和审计日志，但不能通过管理身份绕过资源权限或代替用户批准高风险操作。

### 4.4 临时或外部协作

需要外部人员参与时，应创建受控账号或受控 Project 成员关系，并按目标资源授权。外部协作者不应获得整家公司 Workspace 的默认访问权。是否开放公网访问由部署方决定，公网入口必须经过 HTTPS 反向代理，数据库和 Redis 等内部端口不得暴露。

## 5. 推荐部署拓扑

```text
员工浏览器 / Electron 桌面端 / 移动端
                    │
              HTTPS / WSS
                    │
        公司内网反向代理或统一入口
                    │
     LocalMind Web、Admin 与后端服务
                    │
   PostgreSQL、Redis、文件存储、任务 Worker
                    │
     企业内部模型或获准的 AI Provider
```

部署可以从单机 Docker Compose 开始，后续再拆分 Web、Worker、数据库、Redis 和文件存储，但这些组件共同组成一个逻辑实例。生产环境应备份数据库、上传文件、配置和企业连接器数据。

## 6. Web 与桌面端的分工

### 6.1 Web 是默认入口

浏览器入口应承担标准企业使用场景：

- 统一登录、SSO 和会话管理；
- Workspace 与 Project 访问；
- 文档、白板、原生 Office 资源和 AI Chat；
- 审批、任务、通知和审计相关界面；
- 管理员配置与运维；
- 集中升级和跨平台访问。

Web 入口的优势是部署一次即可让全体用户获得相同版本，适合内网、VDI、共享办公设备和临时协作者。

### 6.2 桌面端是可选增强入口

Electron 桌面端应是连接公司实例的客户端外壳，而不是员工电脑上的独立服务器。它适合：

- 高频使用 LocalMind 的员工；
- 桌面通知、快捷键和深链接；
- 更方便的本地文件导入；
- 更好的窗口、标签页和系统集成；
- 将来支持更完整的本地缓存或离线编辑。

私有部署桌面端可以在构建时指向公司的实例地址，例如使用 `LOCALMIND_CLOUD_URL`，但登录、权限、同步、Project 状态和审计仍由服务器处理。

### 6.3 移动端

移动端适合审批、通知、快速查看、评论和轻量编辑。它同样连接公司的 LocalMind 实例，不维护独立的组织数据副本。

## 7. 为什么不为每名员工部署一套 LocalMind

每台电脑运行独立实例会产生多个互不一致的数据源，带来以下问题：

- 部门与 Project 无法自然共享同一份实时状态；
- 权限、审批和审计难以统一；
- 模型密钥、MCP 凭据和企业集成需要重复配置；
- 员工离职、设备损坏或重装会增加数据恢复风险；
- AI 队列、租约、重试和取消无法形成统一的服务端状态机；
- 公司无法对知识、文件和运行证据执行一致的备份与保留策略。

客户端本地缓存可以提升编辑体验，但缓存失效、设备更换和离线恢复都必须有服务器同步与权限校验作为边界。

## 8. 身份、权限与数据边界

企业部署应围绕公司身份系统建立账号和成员关系。建议支持统一登录，并将以下边界保持清晰：

1. 实例管理员负责系统级配置和运维；
2. Workspace 管理员负责部门成员、资料和部门级设置；
3. Project 成员默认管理 Project 内部文件树和资源；
4. 对外发布或复制时，重新检查操作者对目标 Workspace 和目标位置的实际权限；
5. AI 工具不能因为用户加入 Project 就获得额外的 Workspace 或企业系统权限；
6. 所有写入、审批、取消、重试和外部副作用都保留可恢复状态与审计证据。

## 9. 推荐产品路线

### 第一阶段：企业 Web 基础

- 完成单实例内网部署；
- 支持 SSO、Workspace、Project 和成员权限；
- 提供文档、白板、Office/PDF 原生资源和 AI Chat；
- 完成任务、审批、审计、备份和管理员配置；
- 通过浏览器覆盖绝大多数员工场景。

### 第二阶段：桌面与移动增强

- 提供指向企业实例的 Electron 安装包；
- 增加桌面通知、快捷键、深链接和本地文件导入；
- 提供移动端审批、通知和快速访问；
- 统一版本策略，避免客户端长期落后于服务器协议。

### 第三阶段：受控离线能力

- 明确哪些资源允许离线缓存；
- 处理离线编辑、冲突、租约过期和设备撤销；
- 允许管理员配置离线数据保留时间和远程清除策略；
- 保证离线状态不会绕过实时权限、审批和审计规则。

## 10. 验收标准

该设计落地后，应能证明：

- 一家公司可以通过一个内网地址访问同一 LocalMind 实例；
- 不安装桌面端的员工也能完成主要工作；
- 安装桌面端的员工连接的是同一实例，而不是独立数据库；
- 不同部门可以使用不同 Workspace；
- 一个 Project 可以安全地组织跨部门成员和内部资源；
- Project 内容只有在明确操作后才发布到 Workspace；
- 管理员能够统一配置 AI、备份和审计；
- 客户端缓存或短暂离线不会造成权限扩大或审计记录丢失。
