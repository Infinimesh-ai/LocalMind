## 1 摘要

**影响。** 2026-10-30 起，LocalMind 自托管实例的页面加载明显变慢：

- 资源列表长时间显示“暂无资源”；
- 文档权限请求中位耗时 1.8 s，最慢 18 s。

同日 11:21:12 UTC（04:21 PT），后端进程 V8 堆耗尽，进程停在异常退出路径上，既不退出也不响应。直到 11-01 06:20:37 UTC（10-31 23:20 PT）人工重启，服务完全不可用约 **43 小时**。

**根因。** 同一个进程上叠加了两个独立缺陷。

**缺陷 A：前端权限请求扇出，服务端单次成本高。**

- 提交 `f4a00b882a`（2026-10-25）把只服务单文档范围的 5 秒权限刷新，扩展到所有被订阅的文档。
- 同一提交让资源列表、侧栏、搜索等 6 个入口，把全部候选文档逐篇纳入订阅。
- 每个刷新周期，全部文档的请求在约 100 ms 内同时发出：
  - 前台标签页每 5 秒 54—85 个；
  - 被浏览器节流的后台标签页每分钟 173 个。
- 服务端每次 `getDocRolePermissions` 要执行 19 条 SQL（本地实测），最多同时占用 5 个连接。

**缺陷 B：日志管道无上限，进程不退出。**

- 每个请求写两条运行日志，每条是一个独立的交互事务，与业务共用连接池。
- 日志表已有约 1,090 万行、约 9.8 GiB；`shared_buffers` 只有 128 MiB，磁盘读等待约 70—80 ms，日志 SQL 占数据库读取块的 99.8%。
- 保留清理每小时扫描大范围后失败，表只增不减。
- 写库超时后，降级路径对每条日志做 3 次全目录扫描。扫描在 4 线程的 libuv 线程池中排队，内存占用随“并发数 × 文件数”增长，直到堆耗尽。
- 进程 OOM 后没有退出，而容器重启策略只在进程退出时才生效。

A 是这次 B 爆发的放大器，但 B 不依赖 A：任何原因让数据库变慢，都可能触发 B。反过来，修好 B 也不会让页面变快。

**修复。**

| 缺陷 | 修复                                                                                                                                                                                                     | 状态                          |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| A    | 打开的文档 5 秒刷新，列表、侧栏、搜索 60 秒刷新，隐藏页面暂停；全局并发上限与在途合并；候选集合不变不重查                                                                                                | 已合入 `main` 并部署（11-02） |
| A    | 新增 `workspace.readableDocIds`：一次最多 100 篇，SQL 数与篇数无关；前端以 16 ms 窗口合并所有调用方，最多 2 个请求在途，取消信号传到请求层；列表在检查中显示“加载中”，失败可重试；列表行不再订阅编辑权限 | 已合入 `main` 并部署（11-02） |
| B    | 削减日志量；有界准入、熔断、批量写入；spool 内存计数；独立小连接池；保留清理分批提交并持久化进度；`init`、存活检查、致命错误诊断报告、看门狗脚本                                                         | 已合入 `main` 并部署（11-02） |

**效果。**

已在本地实测：

- 单篇权限查询 19 条 SQL；
- 批量只读查询 11 条 SQL，1、10、100 篇都一样。

按此推算（未经线上验证），一个挂着 214 篇文档的前台标签页：

| 指标         |        修复前 |         修复后 |
| ------------ | ------------: | -------------: |
| 权限请求     | 约 42.8 次/秒 |  约每分钟 3 次 |
| 权限相关 SQL |  约 813 条/秒 | 约每分钟 33 条 |

线上部署后 3 小时实测（第 8.3 节）：

- 日志写入从 26.5 行/秒降到 0.58 行/秒；
- 全库事务从约 543 次/秒降到约 58 次/秒；
- 磁盘读等待从约 70 ms 降到约 7 ms；
- 仍来自旧前端的权限请求，P95 从 0.5—3 秒降到约 50 ms。

## 2 背景

### 2.1 LocalMind 与部署形态

LocalMind 是基于 AFFiNE（开源文档与白板应用）的自托管 AI 办公工作区。本次事故的实例形态如下：

| 部分                                   | 说明                                                                                                                                                                       |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 主机                                   | 单台 Linux 主机（8 vCPU，磁盘设备 `sda`，剩余约 1.2 TB），Docker Compose 部署                                                                                              |
| 后端容器 `localmind_affine_server`     | Node.js 22（v22.22.3）运行 NestJS 服务。同时提供 GraphQL API 和 Web 前端静态文件。镜像以 `CMD ["node", "./dist/main.js"]` 启动，没有 init 进程，所以 node 是容器内的 PID 1 |
| 数据库容器 `localmind_affine_postgres` | PostgreSQL 16（pgvector 镜像），参数为默认值，`shared_buffers` 128 MiB                                                                                                     |
| 其他依赖                               | Redis 与若干辅助容器，与本次事故无关                                                                                                                                       |
| 客户端                                 | 浏览器中的 React 单页应用；业务状态由 RxJS 驱动的 service 管理（`LiveData`、`effect`）                                                                                     |

### 2.2 与本次事故有关的组件

```text
浏览器标签页
  资源列表 / 侧栏文档节点 / 文档搜索 / 快速搜索 / 链接搜索
    └─ GuardService（前端权限服务）：can$ 订阅、readableDocIds$、周期刷新
         └─ GuardStore → GraphQL getDocRolePermissions（每篇一个请求）
                         ↓ HTTP
后端 NestJS 进程（单进程、单事件循环）
  HTTP 中间件 timing.ts ──────────┐ 每个响应写 http.request.completed
  Apollo GraphQL logger-plugin ───┤ 每个请求写 graphql.request.completed
  WorkspaceResolver → DocResolver → permissions()（PermissionService 计算 17 项权限）
  LocalMindLogService：sink → write() → Prisma 交互事务 → 失败则进 spool（本地文件）
  定时任务：spool 补写（15 秒）、保留清理（1 小时）、签名归档（1 天）、MonitorService（1 分钟内存采样）
         ↓ Prisma（单个全局 PrismaClient，默认连接池约 17）
PostgreSQL：业务表 + 日志分区表 localmind_log_events_2026 + 全局事件 ID 登记 localmind_log_event_ids
```

几个下文反复出现的概念：

- **权限查询的两种用途。**
  - 列表只需要知道某篇文档“能不能读”，用来决定显示与否。
  - 打开的文档需要完整的 17 项权限，用于菜单与按钮：编辑、删除、发布、评论等。
  - 无论哪种，服务端都会在每次真实读写时实时检查 ACL；前端拿到的权限只是界面提示，不是授权凭据。
- **日志系统。** [日志系统设计](localmind-logging-system-design.zh-CN.md)规定：
  - PostgreSQL 是日志真相源，stdout 是兼容镜像；
  - spool 是数据库不可用时的本地待补写缓冲；
  - 运行日志可以按策略采样或丢弃，业务审计（`writeAudit()`）不得静默丢弃。
- **保留策略。** 运行日志 30 天、错误日志 90 天、审计 365 天。日志表按年分区：2026、2027、2028 加默认分区。全局 ID 登记表由触发器维护，用于跨分区幂等。

## 4 排查过程

本节按实际顺序记录推理路径：每一步看了什么数据、得出什么结论、排除了哪些假设。证据强度分三级：

- **已确认**：有直接观测或实验；
- **强推断**：多项独立证据一致，但缺少直接测量；
- **未确认**：只有机制或单项证据。

### 4.1 页面慢，但服务活着：先判断“慢在哪里”

**数据**（10-30 03:50—03:57 PT 现场只读检查）：

- 公网首页约 166 ms，回环首页约 68 ms；
- GraphQL `__typename` 约 67 ms，HTTP 200；
- PostgreSQL 与 Redis 健康检查正常；
- 磁盘使用 35%，剩余约 1.2 TB；可用内存约 7.9 GiB；
- Swap 已用约 4 GiB，但短时采样 si/so 为 0。

**结论**：进程、入口和依赖都活着，慢的是业务请求。

**排除**：

- **磁盘耗尽**：使用率 35%；
- **持续换页**：si/so 为 0；
- **入口层故障**：`__typename` 很快。

**注意**：`__typename` 只验证 GraphQL 入口，不经过数据库，所以不能当作就绪证据。这也是后来存活检查只用 `/info`、而就绪要单独设计的原因（第 10.4 节）。

### 4.2 哪些请求慢：按 operation 聚合

**工具**：对 `docker logs` 做流式 JSON 解析，只输出聚合值，按 GraphQL operation 统计。

**故障末段窗口**（10:49:11—10:52:42 UTC，211 秒，取自页面加载记录）：

| operation                          |  次数 |       P50 |       P95 |      最大 |
| ---------------------------------- | ----: | --------: | --------: | --------: |
| `getDocRolePermissions`            | 5,426 |  6,870 ms | 12,024 ms | 14,597 ms |
| `workspaceDirectory`               |   111 |  2,716 ms |  6,753 ms |  9,678 ms |
| `copilotWorkbenchConversationsGet` |    42 |  4,441 ms | 10,040 ms | 10,045 ms |
| `getWorkspaces`                    |     3 | 11,722 ms |         — | 15,170 ms |

权限查询占该窗口 GraphQL 完成记录的 96.4%，约 25.7 次/秒。

**故障进程全程**（03:24:36—11:21:12 UTC）：

- 容器日志约 392.8 MB、962,324 行；
- GraphQL 完成记录 211,280 条，其中 `getDocRolePermissions` 197,718 条（93.58%）；
- 权限查询耗时中位 1,792 ms、P95 10,036 ms、最大 18,209 ms；
- 按 `requestId` 关联出 193,522 对 HTTP/GraphQL 完成日志，即至少 391,240 条（约 90.3%）完成日志由权限查询产生。

**结论（已确认）**：权限查询是压倒性的流量。故障末段的 6.9 s 中位数只代表 OOM 前约 30 分钟，全程中位数是 1.8 s。

### 4.3 数据库为什么慢：看等待事件与读取块

**数据**（10-30 10:50—10:57 UTC 现场，取自页面加载记录）：

- **主机**：
  - `iowait` 60%—80%；
  - `sda` 读等待约 79—80 ms、写约 36—38 ms，队列深度约 30。
- **连接**：
  - 一次快照中，16 个连接等待 `DataFileRead`、1 个等待 `BufferIO`；
  - 连续 8 次采样共 144 个连接状态，其中 94 个是日志 SQL 在等 `DataFileRead`。
- **读取块**：8.85 秒内 `pg_statio_user_tables` 新增读取块 1,667 个，其中：
  - `localmind_log_events_2026` 1,220 个；
  - `localmind_log_event_ids` 444 个；
  - 日志表合计占 **99.8%**；同期约 51 条/秒日志插入。
- **规模**：
  - 日志分区约 1,092 万行、7,898 MB；
  - 全局 ID 登记约 1,089 万行、2,119 MB；
  - 最大的几个索引：主键约 969 MB、事件名与时间约 834 MB、全局 ID 主键约 819 MB、event ID 约 814 MB。

**结论（已确认）**：数据库的读 I/O 几乎全部花在日志写入路径上。业务查询与日志 SQL 共用连接池与磁盘，所以一起变慢。

**排除**：

- **缺索引**：`EXPLAIN` 显示 event ID 查重走索引，不是全表扫描。查重查询不带分区时间条件，会探查多个分区与归档表；每条日志要在多个大索引里定位随机页，这才是成本所在。
- **只是 `shared_buffers` 太小**：调大它能提高缓存命中，但三个问题都还在：
  - 每个请求 19 条 SQL；
  - 每个请求附带 2 个日志事务；
  - 每小时一次大范围清理扫描。

  而且 OS 页缓存同样受限于约 10 GB 的随机访问工作集。所以它是缓解项，不是根因（第 9 节）。

- **同机另一套 AFFiNE**：其 PostgreSQL 累计读取约 0.57 GB，`localmind_affine_postgres` 约 271 GB，可忽略（11-01 复测）。

**未排除**：虚拟化底层存储本身的问题。guest 内看到的 70—80 ms 读等待无法区分宿主机原因。本次结论不依赖于此：即使磁盘更快，请求扇出与日志放大依然存在。

### 4.4 进程为什么失去响应：V8 OOM，而不是被杀

**数据**（11-01 首轮检查，进程仍是故障进程）：

- 容器运行中，重启计数 0，`OOMKilled=false`；
- RSS 约 5,145,584 KiB，持续占用约一个核心；
- 回环 HTTP 能建立连接，但 8 秒内无数据；
- 最后两次 Mark-Compact：4037.2 → 4030.2 MB（3,638 ms）、4045.9 → 4038.8 MB（3,439 ms），随后出现 `FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory`；
- 短时 GDB attach，主线程栈为 `abort` ← `node::OOMErrorHandler` ← `V8::FatalProcessOutOfMemory` ← `Heap::CollectGarbage`。

**结论（已确认）**：V8 堆达到上限；进程停在 `abort` 路径，没有退出。`OOMKilled=false` 与此不矛盾：这是 V8 自身的堆上限，不是容器内存上限触发的内核 OOM。

- 强推断：降级路径（spool）是堆积的主体。

### 4.8 进程为什么不退出：验证 PID 1 假设

**假设**：node 是容器内的 PID 1。内核会忽略 PID 1 发给自己的默认处置信号，包括 `abort()` 的 SIGABRT，导致进程卡在退出路径上。

**实验**（本地 arm64 Docker，附录 B.3）：

| 条件                                         | 结果                  |
| -------------------------------------------- | --------------------- |
| node 为 PID 1，纯 JS OOM                     | 退出码 133（SIGTRAP） |
| `--init`，纯 JS OOM                          | 退出码 134（SIGABRT） |
| PID 1，加载 Prisma 与 native addon 后 OOM    | 133                   |
| `--init`，加载 Prisma 与 native addon 后 OOM | 134                   |

**结论（未确认根因）**：PID 1 确实改变了退出路径（SIGABRT 被忽略后，由 glibc 的兜底指令终止），但四种情况都正常退出，没有复现卡死。

剩余假设：

- 线上 x64 的 glibc 兜底行为不同；
- core 路由到 Apport 管道时，约 5 GB 进程的转储阻塞了退出。

这两点需要在 x64、相同内核配置下复现。修复不依赖查明根因：`init: true` 加外部看门狗（第 7.5 节）。

```text
① 前端扇出（缺陷 A）
   N 篇候选文档 × 每 5 秒 × 每个前台标签页；后台标签页每分钟整批 N 个
   放大：1 次页面挂载 → 每分钟 12N + 若干 N 个请求（N=214 时约 42.8 次/秒）   ← 重启后仍在
        │
② 服务端单次成本（缺陷 A）
   每个请求 3 层 resolver、3 次加载权限上下文、19 条 SQL，最多同时占 5 个连接
   放大：1 次“能否读”判断 → 19 条 SQL（批量只读查询分摊后 < 0.2 条/篇）        ← 重启后仍在
        │
③ 日志放大（缺陷 B）
   每个请求 HTTP + GraphQL 两条完成日志，每条一个交互事务（至少 5 次往返）、
   多个随机 UUID 索引写入与查重；debug 与日志上传请求本身也入库
   放大：1 个业务请求 → 2 个日志事务，约 10 次数据库往返                         ← 重启后仍在
        │
④ 存储与连接（缺陷 B）
   约 9.8 GiB 日志表与索引 vs 128 MiB shared_buffers；随机读等约 70—80 ms；
   日志 SQL 与业务共用约 17 个连接；清理每小时扫描后失败，表只增不减
   放大：权限请求在无竞争时 15—30 ms，排队后 P50 1.8 s、P95 10 s                 ← 重启后仍在
        │ 数据库变慢到让日志事务超时（10:44 起）
⑤ 降级路径（缺陷 B）
   每条失败日志做 3 次全目录扫描（readdir + 逐文件 stat），写 2 个文件；
   扫描挤在 4 线程 libuv 线程池中，单次耗时 ∝ 并发数 × 文件数
   放大：1 条日志 → 3 × F 次 stat（F≈8,000 时为 24,000 次）；
        故障末期约 930 个扫描同时在途，GC 后保留约 2.6 GiB                      ← 重启后暂未出现
        │
⑥ V8 堆耗尽，进程停在 abort 路径，不退出；无健康检查与告警 → 约 43 小时不可用  ← 修复前随时可复发
```

各级的关系：

- ①②决定页面慢不慢。
- ③④决定数据库会不会被拖垮，同时也让①②更慢。
- ⑤⑥决定数据库变慢时进程会不会死、死了能不能恢复。

修复必须覆盖每一级：

- 只修 ⑤⑥，进程不再死，但页面仍慢；
- 只修 ①②，这次的流量没了，但任何其他原因让数据库变慢，⑤⑥仍会复发。

### 6.3 出现的问题与机制

#### 6.3.1 请求数：从“1 篇”变成“列表里的每一篇”

刷新回调 `refreshObservedPermissions` 在同一个定时器回调里同步遍历全部被观察文档，逐个调用 `revalidateDocPermission`。

- 一个前台标签页挂着 N 篇文档时，每 5 秒发出 N 个请求，即 N/5 次/秒。
- K 个前台标签页时，为 K × N / 5 次/秒。
- 管理员和 Owner 被提前放行（`isAdmin$` 为 true 时直接返回），所以请求全部来自普通成员。

故障日峰值 42.8 次/秒，对应单个前台标签页约 214 篇。

#### 6.3.2 突发：RxJS 的 `groupBy` + `exhaustMap` 只管“同一篇”

```ts
private readonly revalidateDocPermission = effect(
  groupBy((docId: string) => docId),
  mergeMap(doc$ => doc$.pipe(exhaustMap(docId => fromPromise(...)))),
);
```

- `groupBy` 按 docId 拆成 N 个子流；`exhaustMap` 只让同一子流在上一个请求返回前丢弃新的触发。
- `mergeMap` 把 N 个子流并行展开，没有任何上限。
- 结果：每个周期 N 个请求在同一个事件循环轮次里全部发出。11-01 复测看到“约 100 ms 内发出 54 个、耗时阶梯上升”，就是这个机制。

`readableDocIds$` 内部的 4 路并发，是**这一次调用**的局部上限：

- 侧栏的每个文档节点各自调用一次 `readableDocIds$([docId])`；
- 列表和搜索也各自调用；
- `can()` 直接调用 `loadDocPermission`，不经过上面的 `exhaustMap` 通路。

局部上限叠加起来，没有全局上限。

#### 6.3.3 浏览器定时器节流：省 CPU，不省服务端

Chrome 88 起，页面隐藏超过 5 分钟后，链式定时器每分钟最多唤醒一次（[Chrome 定时器节流](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)）。

5 秒周期因此被压成每分钟一次，但每次唤醒仍同步发出全部 N 个请求。它节省的是客户端 CPU，没有降低服务端的瞬时并发，反而让请求更集中。这就是 07:20—07:24 每分钟一批 173 个的来源。

节流是浏览器约束，不能当作修复。正确做法是隐藏时完全不发（`visibilitychange`）。

#### 6.3.4 服务端单次成本：19 条 SQL、最多 5 个连接

一次 `getDocRolePermissions` 依次经过三层 resolver：

1. `workspace(id)` 检查 `Workspace.Read` 并加载 Workspace；
2. `doc(docId)` 读取文档信息并检查 `Doc.Read`；
3. `permissions` 计算全部 17 个 `DOC_ACTIONS`。

后一层不知道前一层已经算过，所以同一请求加载了三遍权限上下文：成员、Workspace 策略、运行状态、文档策略、文档授权。17 个动作里包含写类动作，会触发 quota 运行状态检查并作废请求内缓存。

本地实测（附录 B.4，PostgreSQL 语句日志，5 次取最小值）：

| 请求                            | SQL 条数 |        其中认证 | 同时用到的后端连接 |
| ------------------------------- | -------: | --------------: | -----------------: |
| `getDocRolePermissions`（1 篇） |       19 | 2（会话、用户） |                  5 |
| `readableDocIds`（1 篇）        |       11 |               2 |                  5 |
| `readableDocIds`（10 篇）       |       11 |               2 |                4—5 |
| `readableDocIds`（100 篇）      |       11 |               2 |                  5 |

- 另一会话通过代码阅读估算为“约 16 条业务 SQL”；实测扣除认证后是 17 条，二者一致。
- “最多 5 个连接”来自 `PermissionContextLoader.load()` 用 `Promise.all` 并行发出 5 类查询。Prisma 为每条并行查询各取一个连接。

#### 6.3.5 Little 定律：为什么 42.8 次/秒能占满 17 个连接

Little 定律：系统中平均在途数 L = 到达率 λ × 平均停留时间 W。套用到连接池上，平均被占用的连接数 = 每秒 SQL 数 × 每条 SQL 平均持有连接的时间。以下是机制推算，不是线上实测。

- **权限请求**：42.8 次/秒 × 19 条 ≈ 813 条/秒。缓存命中时每条约 1—2 ms，只占约 1—2 个连接；一旦随机读未命中、要等 70—80 ms 的磁盘，持有时间就会上升一个数量级。
- **日志事务**：每个请求 2 个，约 86 个/秒。每个至少 5 次往返（BEGIN、advisory lock、查重、插入、COMMIT），插入还会触发全局 ID 登记，每次都可能遇到随机读。仅日志就足以长时间占用十几个连接。

一旦平均占用接近 17，排队时间就不再线性增长，而是急剧上升。这与线上现象一致：

- 无竞争时 15—30 ms；
- 故障日 P50 1.8 s、P95 10 s；
- 复测时一次采样里 17 个连接全被日志 SQL 占用。

排队还会反馈到客户端：请求变慢 → `exhaustMap` 下一周期跳过仍在途的文档 → 但新增的标签页和入口照样发 → 服务端仍然处在饱和点。

#### 6.3.6 用户感知：“暂无资源”，而不是“加载中”

`readableDocIds$` 先以 4 路并发检查全部候选，`Promise.all` 结束后才发布结果，此前一直发出空集合。资源列表“加载中”的判断只看目录、查询和文档列表是否就绪，不看权限检查，所以检查期间显示的是“暂无资源”。

机制估算：等待时间约 ⌈N / 4⌉ × t。N = 214 时，t = 0.2 s 约 11 秒；t = 1.8 s 约 96 秒。

此外，`useMemo` 依赖 `docGroups` 数组本身。文档元数据同步、排序等任何引起新数组的变化，都会让全部候选重新检查一遍。

#### 6.3.7 其他边界缺陷

- **失败无限重试**：`backoffRetry({ count: Infinity })`，200 ms 起步、15 s 封顶、无 jitter。
- **取消信号断在中途**：`AbortSignal` 只停止 `readableDocIds$` 的后续循环，没有传到 `GuardStore` 的 GraphQL 请求，已发出的 HTTP 请求不会被中止。
- **列表行各自订阅编辑权限**：资源列表行 `MixedDocRow` 用 `can$('Doc_Update', id)` 订阅编辑权限，只为了“更多”菜单里的“编辑标签”一项，于是每个可见行都进入 5 秒刷新。

### 6.4 新方案与备选方案对比

| 方案                                                                | 成本                                                                         | 收益                                                                   | 风险与适用条件                                                      | 结论                       |
| ------------------------------------------------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------- | -------------------------- |
| 只把 5 秒改成 60 秒                                                 | 极低                                                                         | 请求降为 1/12                                                          | 打开的文档撤权收敛变慢；仍是逐篇、仍同步突发                        | 不单独采用                 |
| 分级刷新：打开的文档 5 秒、列表 60 秒、隐藏暂停、全局并发、在途合并 | 低（只改前端）                                                               | 后台标签页请求降为 0；同时在途不超过 4；列表请求降为 1/12              | 服务端单次成本不变                                                  | **止血，已合入**           |
| 服务端批量只读接口                                                  | 中（新增一个 GraphQL 字段、前端改调用）                                      | 一个请求覆盖 100 篇，SQL 数与篇数无关                                  | 需要定义存在性语义与 Project 隔离；旧客户端仍走单篇                 | **根治扇出，已实现**       |
| 前端 DataLoader 式合并                                              | 中                                                                           | 6 个入口、侧栏 N 个节点合成同一批请求                                  | 合并窗口带来十几毫秒延迟；取消需要引用计数                          | **与批量接口配套，已实现** |

| 复用目录快照的 `rights`                                             | 中                                                                           | 列表与权限一次返回（类似 Google Drive `files.list` 的 `capabilities`） | 目录的 `canWrite` 不等于正文 `Doc_Update`；候选集合与目录集合需一致 | 后续评估                   |

选型理由：

- **为什么前后端都要改。** 只有前端合并，服务端仍逐篇算 17 项；只有服务端批量，6 个入口和侧栏节点各自发起时仍然是 N 个请求。
- **为什么批量接口只返回“可读 ID”。** 列表只需要这一项，不再计算 16 个用不上的写类动作；返回形态也最小，不暴露其他权限细节。
- **为什么暂不做推送失效。** 批量化后，一个 214 篇的列表每分钟只需 3 个请求，轮询成本已经很低；推送的完整协议（事件覆盖面、断线补读、版本）成本高，应在实测后再决定。

#### 6.5.3 边界条件与失败模式

| 情况                                 | 行为                                                                   |
| ------------------------------------ | ---------------------------------------------------------------------- |
| 同一篇文档被列表、侧栏、搜索同时检查 | 窗口内合并为一项；已在途时加入该批次                                   |
| 某个调用方取消（切页、组件卸载）     | 只拒绝它自己的等待者；同批其他等待者不受影响                           |

| 超过 200 篇同时检查                  | 最多 2 批在途，其余排队，前一批完成后继续                              |
| 管理员、单文档范围、共享模式         | 不走批量，沿用原逐篇逻辑：管理员直接放行，范围外文档直接拒绝           |
| 服务端是旧版本                       | 第一次批量请求被拒后，永久改为逐篇                                     |
| 批量请求瞬时失败                     | 列表显示可重试的错误；不逐篇重试                                       |
| 本地新建、尚未同步到服务端的文档     | 按 Workspace 成员默认角色判断，与单篇查询一致，仍然可见                |

### 6.6 为什么有效

| 对应 SQL               | 214 × 19 ≈ 4,066 条每 5 秒（约 813 条/秒） | 服务端逐篇读取文档并计算完整权限，随篇数线性增长（未实测）                             | 3 × 11 = 33 条每分钟                                     |
| 后台标签页             | 每分钟 214 个                              | 0（隐藏暂停）                                                                          | 0                                                        |
| 列表行编辑权限订阅     | 可见行数 × 每 5 秒                         | 同左（第一批未覆盖）                                                                   | 0（只在菜单打开时查一次）                                |
| 侧栏 N 个文档节点      | 各自发起                                   | 各自发起（每次 1 篇的批量请求）                                                        | 16 ms 窗口内合并进同一批                                 |
| 首次进入列表           | ⌈214/4⌉ × t，期间显示“暂无资源”            | 3 个批量请求，期间仍显示“暂无资源”                                                     | 3 个请求，期间显示“加载中”，失败可重试                   |
| 权限请求附带的日志事务 | 每请求 2 个                                | 成功且不慢的 GraphQL 合并为每 operation 每分钟 1 条；`/graphql` 成功的 HTTP 日志不入库 | 同左                                                     |

剩余的周期成本来自打开的文档：每个打开文档的可见标签页每 5 秒 1 次完整权限查询（19 条 SQL）。容量估算见第 10.6 节。

### 6.7 正确性与安全

- **降低前端刷新频率为什么不削弱授权。** 服务端对每次文档读取（同步、快照、GraphQL）和写入（更新、发布、成员管理）都实时检查 ACL；前端权限只决定界面是否显示入口。刷新变慢，最坏情况是界面多显示一会儿“可编辑”，用户点下去会被服务端拒绝；不会因此读到或写入无权访问的内容。
- **撤权后多久在界面上收敛**（不含请求本身耗时）：

  | 场景                             | 收敛时间                                           |
  | -------------------------------- | -------------------------------------------------- |
  | 打开的文档                       | ≤ 5 秒                                             |
  | 可见页面上的列表、侧栏、搜索候选 | ≤ 60 秒                                            |
  | 隐藏页面                         | 恢复可见时立即刷新；窗口聚焦、网络恢复也会触发刷新 |
  | 实际访问                         | 立即被服务端拒绝                                   |

- **批量接口如何对待“不存在”。**
  - 被拒绝的文档只是不出现在结果里，接口不返回原因。
  - 服务端没有记录的 ID，按 Workspace 成员默认角色判断，与单篇查询和 `workspaceDirectory` 相同；本地新建、尚未同步的文档因此保持可见。
  - 这意味着对默认可读的成员来说，“不存在”与“默认可读”无法区分；但“存在且被设为私有”的文档与随机 ID 的结果不同。这与单篇查询已有的行为相同（后者对存在但无权的文档返回 403，对不存在的文档返回按默认角色构造的结果），批量接口没有新增这类信息。
  - 只有把未知 ID 一律视为不可读，才能彻底消除这类差异，但那会让离线新建的文档在同步前从列表消失，见第 11 节待办。
- **Workspace 与 Project 授权隔离。** `projectScope(null)` 让权限上下文不加载 Project 授权（`context-loader.ts` 只在 `projectId` 为字符串时才查询 `ai_context_project_grants`），符合“Workspace 直接访问只用个人与 Workspace ACL”的规则。e2e 用例有正向对照。
- **取消不误伤。** 共享请求只有在所有等待者都取消后才中止；取消只影响客户端等待，已经到达数据库的查询照常完成，只读，没有副作用。

### 7.2 演变过程

- 09-14 日志系统上线时，写入路径、spool、清理都按上表设计，没有上限测试，也没有千万行规模的测试。

### 7.3 出现的问题与机制

#### 7.3.1 Prisma 交互事务与连接池

- 每条运行日志调用 `prisma.$transaction(async tx => ...)`。这是交互事务：整个回调期间独占一个连接，期间依次执行：
  1. `BEGIN`；
  2. advisory lock；
  3. 在 4 个日志分区和归档表中查重；
  4. 插入，并由触发器写全局 ID 登记；
  5. `COMMIT`。
- Prisma 交互事务默认 `timeout`（事务总时长）为 5 秒；日志写入把 `maxWait`（等待取得连接）设为 5 秒。任一超出就抛错，日志转入 spool。
- `DATABASE_URL` 没有设置 `connection_limit` 时，Prisma 的默认连接池大小为 2 × CPU 数 + 1，8 vCPU 时约 17 个。业务请求与日志共用这一个池。
- 前文的权限上下文加载用 `Promise.all` 并行发出查询，一个业务请求同时要 5 个连接。

结果：日志事务越慢，占用连接越久；业务请求等不到连接；业务越慢，日志事务也越慢。

#### 7.3.2 PostgreSQL 随机 UUID 索引、缓存与 DataFileRead

- 日志分区的主键 `id`、`event_id`、`request_id`，以及全局登记表主键，都是随机 UUID。B-tree 插入随机键时，要找到键值所在的叶子页；在约 5 GB 的索引里，这些页几乎都是随机分布的。
- `shared_buffers` 是 PostgreSQL 自己的缓存，只有 128 MiB。未命中时向操作系统读页：命中 OS 页缓存时很快；否则要访问磁盘，在等待事件里表现为 `DataFileRead`。
- 这台主机的磁盘随机读约 70—80 ms，所以一条日志插入、查重时遇到几次未命中，就是几百毫秒的事务时长。
- 时间相关的索引（`occurred_at`）是追加写，基本命中；随机 UUID 索引才是读放大的来源。

这解释了“写入为什么表现为读 I/O”：要写一个随机位置，先得把那一页读进来。

#### 7.3.3 保留清理：每小时一次大扫描，什么也没删

```ts
await prisma.$transaction(async tx => {
  await tx.$executeRaw`SELECT pg_advisory_xact_lock(...)`;
  const count = await tx.localMindLogEvent.count({ where }); // 回表判断 retention_class 与 severity
  return (await tx.localMindLogEvent.deleteMany({ where })).count;
});
```

7 次失败时，到达 `deleteMany()` 前事务已经持续了：

| 时间（UTC） | 事务已持续 |
| ----------- | ---------: |
| 04:26:28    | 112,239 ms |
| 05:25:23    |  47,410 ms |
| 06:26:14    |  98,187 ms |
| 07:26:18    | 102,169 ms |
| 08:25:30    |  54,352 ms |
| 09:25:04    |  28,287 ms |
| 10:24:55    |  18,854 ms |

- 事务预算是默认的 5 秒，所以 `deleteMany()` 被 Prisma 拒绝，一行都没删。
- `count()` 要逐行判断保留分类与级别，读取大量过期行，与写入争抢同一块磁盘和缓存。
- 表从不收缩，下一轮更慢。
- 失败在 `try` 之外抛出，只留下 Scheduler 错误，没有持久的失败状态。

11-01 复测中，清理失败的两分钟里，权限请求 P95 升至 4.1 s 和 4.5 s，可见它是重启后仍在制造的尖峰。

#### 7.3.5 降级路径：libuv 线程池与“并发 × 文件数”

```ts
async bytes() {
  let total = 0;
  for (const file of await this.list()) total += (await stat(file)).size;  // list(): readdir + filter + sort + map(join)
  return total;
}
```

- 一条非关键日志进入 `spoolRuntime()` 后执行 3 次 `bytes()`：预检查 1 次、`append(record)` 内 1 次、`append(降级记录)` 内 1 次，并写 2 个文件。
- 每次 `bytes()` 新建完整路径数组，再逐个 `await stat()`；在遍历结束前，数组一直存活。

**libuv 线程池。** Node.js 的 `fs.promises`（`readdir`、`stat`、`writeFile`、`rename`）在 libuv 线程池中执行，默认只有 4 个线程，仓库没有设置 `UV_THREADPOOL_SIZE`。

- K 个扫描同时进行时，每个扫描任一时刻只有 1 个 `stat` 在排队，于是 K 个扫描轮流各推进一步。
- 单次扫描完成时间 ≈ F（文件数）× K ÷ 线程池吞吐。
- 文件数和在途扫描数同时增长，扫描时间按乘积增长；变慢又让更多日志同时停在扫描里，形成正反馈。
- 同一线程池还承担本地文件存储读写、`dns.lookup`（包括访问模型服务时的域名解析）、zlib 和部分 crypto。扫描占满线程池时，这些与日志无关的业务也会排队。这一影响由机制推出，未在线上单独测量。

**量级闭环（强推断）。** 本地复现（附录 B.1）：

- 64 路扫描 8,305 个文件，共 53 万次 `stat`，用时 10.8 秒，约 4.9 万次/秒；
- GC 后每路约保留 2.9 MiB。

线上末期单次扫描约 157 秒（第 4.5 节），反推同时在途的扫描约 157 × 49,000 ÷ 8,305 ≈ 930 路，对应保留约 930 × 2.9 MiB ≈ 2.6 GiB，与故障堆同一量级。

该估算基于 arm64 本地吞吐和近似文件数，只能证明“这个机制足以解释数 GB 的堆”，不能给出各类对象的准确占比；那需要同一故障进程的堆快照，而故障进程已经结束。

补写也受同一问题影响：`flushSpool()` 每 15 秒先列出完整目录再取前 100 个，逐条单独事务补写，理论上限约 6.7 条/秒，低于故障期的新增速度。

#### 7.3.6 V8 堆：“在途工作堆积”与泄漏的区别

V8 的垃圾回收只回收从根不可达的对象。一个尚未完成的 async 函数，其续体被 libuv 的待执行请求引用；续体又引用它的局部变量，包括那个路径数组。所以在途工作所需的对象是“活的”，GC 再频繁也回收不了。

|             | 泄漏                 | 在途工作堆积                                                                 |
| ----------- | -------------------- | ---------------------------------------------------------------------------- |
| GC 后保留量 | 单调上升，不再回落   | 随在途数量起伏，工作完成后回落                                               |
| 本次表现    | —                    | 11:05 的 2,115 MiB 在 11:09 回落到 225 MiB；本地复现中扫描结束后堆回到起始值 |
| 正确的修复  | 找出并断开错误的引用 | 限制在途数量与单项成本                                                       |
| 无效的做法  | —                    | 定时 `global.gc()`；只调大堆（只能推迟 OOM，还会拉长 GC 停顿）               |

最后两次完整 GC 各耗时约 3.5 秒，只回收约 7 MB。这说明到了末期，几乎所有对象都仍被在途工作引用。

#### 7.3.7 stdout 管道背压

`mirror()` 用 `process.stdout.write()` 输出每条日志，并忽略返回值。本地实验（附录 B.2）：容器内 stdout 是管道；读取方停顿时，Node 不会阻塞写入，而是把待写内容排队，而且排队的是 JS 字符串，计入 `heapUsed`，不计入 `external`。

- 写入 10 万条约 500 字节的不同记录：排队约 49.4 MiB，GC 后堆增加约 59.6 MiB，external 无变化。
- 所以不能用“external 很低”来排除 stdout 积压。
- 但故障末期 Docker 读取 stdout 只滞后 85 ms（第 4.5 节），现有证据不支持它是本次的主要来源。它是必须设上限的次要风险。

#### 7.3.8 PID 1 的信号语义与“进程不退出”

在 Linux 的 PID 命名空间里，PID 1 没有为某个信号安装处理函数时，内核会忽略同一命名空间内发给它的该信号，包括它自己用 `abort()` 发出的 SIGABRT。

- glibc 的 `abort()` 在 SIGABRT 被忽略后，会执行一条使进程崩溃的兜底指令，所以本地实验中 PID 1 以 SIGTRAP（133）退出，而不是 SIGABRT（134）。
- 本地 arm64 的四组实验都正常退出，没有复现线上的卡死（第 4.8 节）。

无论根因如何，有两条确定的事实：

- Docker 的 `restart: unless-stopped` 只在进程退出后才生效，进程卡死时它什么也不做；
- 实例没有健康检查，也没有外部看门狗。

另外，以 PID 1 运行时，进程内看门狗想对自己发 SIGKILL 也不会生效，这也是改用 `init: true` 的理由之一。

```text
closed ──连续 5 次失败或慢写（>2 s）──→ open（等待 breakerOpenMs，初始 5 s）
open ──等待结束──→ probe（只放行 1 条写入）
probe ──成功──→ closed（breakerOpenMs 复位，写 recovered）
probe ──失败──→ open（breakerOpenMs 翻倍，最多 60 s）
open 期间：运行日志直接写 spool；spool 补写暂停
```

[spool.ts](../packages/backend/server/src/base/logger/spool.ts)：

- 首次使用时流式扫描一次目录，之后在内存里维护 `{ bytes, files }`；
- 追加前在同一同步段内检查并预留容量（`reservedBytes`），写入成功才计入；
- 删除、隔离、迁入时同步更新计数；删除会等待首次扫描完成，避免重复扣减；
- 补写用 `opendir` 只读取前 N 个文件；
- 无法读取或校验失败的文件移入 `quarantine/`，不再阻塞后续补写；
- 目录名改为稳定的 `LOCALMIND_NODE_ID`（默认 `primary`），首次补写时迁入旧版按进程 ID 命名、且未被锁定的目录。

保留清理：

- 每批在独立事务中用 `pg_try_advisory_xact_lock` 抢锁，抢不到即本轮让出（`contended`）。
- 按 `(occurred_at, id)` 游标前进，并带上 `occurred_at >= 游标`，让时间索引可以定位起点。
- 批大小按单批耗时减半或加倍。部署版本的范围是 200—10,000、初始 2,000；11-02 修复后改为 10—5,000、初始 100（见下方“11-02 修复”）。
- 每轮最多 60 秒、50 万行；执行路径不做精确计数，dry-run 计数上限 10 万。
- 批次之间重新检查法务留置与冻结（`paused`）。
- 每轮写入新表 `localmind_log_retention_runs`：状态、计数、游标位置、失败代码、下次时间。状态取值为 `running`、`completed`、`partial`、`contended`、`paused`、`failed`、`interrupted`；超过 1 小时仍为 `running` 的记录，下一轮标为 `interrupted`。记录保留 90 天。
- 迁移 [20261101100000_localmind_log_retention_runs](../packages/backend/server/migrations/20261101100000_localmind_log_retention_runs/migration.sql) 只新建表，带状态、触发方式和计数的 CHECK 约束。

测试中发现并修正的问题：

1. 批量写入的定时器设了 `unref()`。测试进程里没有其他东西保持事件循环，排队的日志永远不会写出，表现为测试“永不结束”。生产环境里服务的其他句柄会掩盖这个问题，但退出时一样会丢掉排队日志。去掉了 `unref()`，并新增 `onModuleDestroy` 在退出时最多花 2 秒写完队列。

### 7.6 为什么有效

- **内存有固定上限。** 运行日志在途最多 1,000 条、4 MiB，error、fatal 最多再加一倍。数据库再慢，也只会丢弃并计数，而不是无限堆积。
- **降级成本与积压无关。** 追加时不再扫描目录，每条日志的降级成本是常数；也不再为每条失败写降级文件。
- **数据库压力下降。**
  - 日志行数：成功的 GraphQL 请求从每请求 2 条变为每 operation 每分钟 1 条；debug、定时任务、上传请求本身不再入库。
  - 事务数：批量后从每条 1 个变为每批 1 个。
  - 首次写入：不再加锁和查重。
  - 连接：日志最多占 3 个独立连接，不再与业务争抢。
- **清理能持续推进。** 每批在预算内提交，失败有记录；表不再只增不减，每小时的大扫描尖峰消失。
- **进程能恢复。** `init` 让 node 不再是 PID 1；存活检查让卡死可被发现；看门狗负责重启；诊断报告让下次故障留下证据。

### 7.7 正确性

- **审计不进入可丢弃路径。** `writeAudit()` 没有改动：同步写库，失败时写 spool 并向调用方抛错（fail-closed）。准入、熔断、采样只作用于 `write()` 和 `writeBatch()` 的运行日志。
- **跳过查重为什么安全。** 只有服务端用 `randomUUID()` 生成、且是第一次尝试写库的记录才跳过查重。UUID v4 有 122 位随机数，碰撞概率可以忽略；万一出现，全局 ID 登记触发器会以 23505 拒绝整批，这批随即转入 spool，回放时走查重路径。
- **“提交成功但客户端以为失败”。** 这批记录进入 spool，回放时查重发现已存在，于是删除文件、不重复插入，也不重复镜像到 stdout。
- **客户端回执。** `writeBatch()` 只为已写入数据库或 spool 的 event ID 返回 accepted；超出准入预算时整批不确认，由客户端保留副本重试；关键日志在 spool 满时抛错，不伪造回执。
- **并发容量预留。** `append()` 在 `await` 恢复后的同一同步段内完成检查与预留，并发追加不会同时越过上限。测试中 10 个并发追加、容量 3 份时，恰好 3 个成功。
- **清理与冻结。** 每批之间重新读取策略；冻结后最多再完成正在进行的一批。抢锁失败直接让出，不长时间等待全局锁。

- 只读 `EXPLAIN ANALYZE` 显示扫描 1,000 行只需 0.85 ms（走时间索引和增量排序），所以慢的不是扫描。
- 同一时段 PostgreSQL 日志里没有 SQL 错误，符合 Prisma 客户端 20 秒交互事务超时的特征。
- 推断原因：删除每一行都要触发器去 `localmind_log_event_ids` 删除登记。待删的 9 月行和登记都是冷数据，每行要读好几个随机页。按 2,000 行一批，约 7 ms 一次的随机读就会超过 20 秒。
- 自适应批大小只在批次**成功**后才调整，超时后整轮直接失败，不会缩小重试。
- 定时入口用 `.catch(() => null)` 吞掉了错误，容器日志里没有失败原因，可观测性也有缺口。

修复状态：11-02 已合入 `main`，未部署（第 7.5.2 节“11-02 修复”）。冷存储模拟中，部署版本的参数在第一批就超时失败，复现了 04:19 这一轮；新逻辑连续 4 轮都没有失败，见附录 B.5。

**三、客户端调试日志仍然入库。**

修复后 6,261 行日志里，`client.debug.affine:fetch` 有 3,602 行（57.5%）。debug 不入库的规则只覆盖服务端 `emit()`，没有覆盖客户端批量上传的调试日志。

## 9 不采用的方案和理由

### 9.1 缺陷 A

| 做法                                       | 理由                                                                   |
| ------------------------------------------ | ---------------------------------------------------------------------- |
| 取消前端权限刷新                           | 撤权后界面会长期显示旧权限                                             |
| 永久缓存 ACL，或把前端结果当作授权         | 违反实时 ACL 契约；写操作必须由服务端实时检查                          |
| 只改刷新间隔                               | 仍是逐篇、仍是同步突发，服务端单次成本不变                             |
| 只做前端通用请求协调器，不接服务端批量接口 | 服务端单次成本仍随篇数线性增长                                         |
| 版本化增量协议、渐进分批展示               | 方向合理但成本高；批量化后 N 篇只需 ⌈N/100⌉ 个请求，收益要实测后再评估 |
| 把目录快照的 `canWrite` 当作正文写权限     | 目录能力不等于 `Doc_Update`                                            |

### 9.2 缺陷 B

| 做法                                  | 理由                                                       |
| ------------------------------------- | ---------------------------------------------------------- |
| 只调大 `--max-old-space-size`         | 只推迟 OOM，GC 停顿更长                                    |
| 定时 `global.gc()`                    | 在途对象仍可达，回收不了                                   |
| 只调大 `UV_THREADPOOL_SIZE`           | “并发 × 文件数”的放大仍在                                  |
| 只限制执行并发、不限制等待队列        | 等待中的闭包与记录照样累积                                 |
| 只放大 spool 容量                     | 旧实现里目录越大，每次扫描越慢                             |
| 只加 Prisma 超时或连接数              | 长事务更多，与业务争抢磁盘更严重                           |
| 把日志移到 worker thread 或换 logger  | 线程间队列与下游写入仍无界，也得不到审计、幂等与回执语义   |
| 引入 Kafka、ELK、OTel Collector       | 自托管部署方需另行安装；不提供审计契约                     |
| 删除 spool、TRUNCATE 日志表、关闭审计 | 破坏证据与审计契约                                         |
| 立即 `VACUUM FULL` 或删除年分区       | 长时间锁表、额外磁盘、数据保留风险；年分区里混有未到期数据 |
| 只调小或调大 `shared_buffers`         | 缓解项，不改变请求扇出、事务数和清理扫描                   |

### 9.3 复核中被否定或修正的判断

| 判断                                                                | 原出处                   | 修正                                                                                     |
| ------------------------------------------------------------------- | ------------------------ | ---------------------------------------------------------------------------------------- |
| “权限轮询是否为最初触发源，待复现”                                  | 页面加载记录第 3.2、4 节 | 提交历史、线上 bundle 和请求批次结构已足以确定（第 4.6 节）                              |
| 第 2.1 节的 6.9 s 中位数代表故障期延迟                              | 页面加载记录             | 那是 OOM 前约 30 分钟的末段；同一进程全程中位数为 1.8 s                                  |
| 普通运行日志需要持久化确认点、checkpoint，正常路径先落盘            | 页面加载记录第 7.5 节    | 运行日志允许采样，磁盘正是瓶颈；运行日志用有界内存批次，熔断时再落 spool，审计保持原契约 |
| 先建立完整基线、再止血                                              | 页面加载记录第 10 节     | 线上靠重启维持且条件未消除，应先发布低成本、可回滚的削减项                               |
| 通用请求协调器、版本化协议排在前面                                  | 页面加载记录第 7、10 节  | 先接批量接口，再按实测决定                                                               |
| Linux 下写 stdout 管道是同步的，不占堆                              | 本文作者早期判断         | 实验证明读取方停顿时会排队进入 JS 堆（附录 B.2）                                         |

| 批量接口返回 granted/denied/missing 与完整权限（`docsPermissions`） | 第一批实现               | 能区分拒绝与不存在，且每篇仍算完整权限；替换为 `readableDocIds`（第 6.5.2 节）           |

### 10.5 观测指标与告警阈值（建议）

数据来自 `localmindLogIngestionStatus`。它读取进程内计数，不依赖日志表；清理记录读取超过 2 秒即标为不可用。

| 指标                                  | 告警阈值（建议起点）                           |
| ------------------------------------- | ---------------------------------------------- |
| `ingestion.breakerOpen`               | 持续 5 分钟以上                                |
| `ingestion.window.dropped.admission`  | 连续 3 个窗口大于 0                            |
| spool `files`                         | 大于 1,000，或 30 分钟内持续增长               |
| `retention.runs[0].status`            | 连续 2 轮 `failed`，或 24 小时没有 `completed` |
| 容器健康状态                          | unhealthy                                      |
| 权限请求速率（按 operation 汇总日志） | 超过部署后基线 3 倍                            |
| `iowait`、`sda` 读等待                | 由主机监控另设                                 |

### 10.6 容量规划（机制推算）

修复后，权限相关的周期请求只剩两项：

- 打开文档的可见标签页：每个每 5 秒 1 次完整权限查询，19 条 SQL；
- 列表、侧栏、搜索：每个可见标签页每 60 秒 ⌈N/100⌉ 次批量查询，11 条 SQL。

| 场景                                                       | 修复前                         | 修复后                                                                    |
| ---------------------------------------------------------- | ------------------------------ | ------------------------------------------------------------------------- |
| 1 个标签页，列表 214 篇                                    | 42.8 次/秒，约 813 条 SQL/秒   | 每分钟 3 次，约 0.55 条 SQL/秒                                            |
| 50 个用户，各 1 个可见标签页、各打开 1 篇文档、列表 200 篇 | 列表约 2,000 次/秒（不可承受） | 打开的文档 10 次/秒（190 条 SQL/秒），列表约 1.7 次/秒（约 18 条 SQL/秒） |
| 500 个用户（同上）                                         | —                              | 打开的文档 100 次/秒（1,900 条 SQL/秒），成为主要成本                     |

因此下一个容量瓶颈是“打开文档的 5 秒完整权限刷新”，它随同时打开文档的可见标签页数线性增长。改为事件失效后才能消除（第 11 节）。

日志侧的固定上限：

- 在途 1,000 条、4 MiB；
- spool 50 MiB，约 10 万条 500 字节记录；
- 日志连接 3 个；
- 汇总日志的行数与请求量无关，只与 operation 数（≤ 200）相关。

### 11.3 为什么约 43 小时才恢复：监控缺口与流程问题

**监控缺口**：

- 没有应用层健康检查：容器状态一直是“运行中”，重启计数为 0。
- Docker 重启策略只在进程退出时生效，而进程卡在退出路径上。
- 没有外部可用性探测或告警；`__typename` 和首页 200 不能代表业务可用。
- 内存采样（MonitorService）本身要经过同一条日志管道写库，故障时最先失效。
- 保留清理每小时失败，只留下 Scheduler 错误，没有告警。
- 请求日志没有路由与会话字段，无法快速定位是哪个页面在制造流量。

**流程问题**：

- `f4a00b882a` 是一次大型合并提交，把单文档刷新扩展到列表，没有评估“每个组件、每篇文档、每个周期”的请求放大。
- 没有负载测试：单元测试覆盖了 4 路上限与撤权，但没有多入口、多标签页、长时间运行的测试。
- 日志系统上线时，没有千万行规模和数据库变慢场景下的容量测试。
- 部署没有健康检查与资源上限，也没有记录部署时间。

## 12 经验与可推广的原则

| 原则                                 | 本次的具体证据                                                                                                                              |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 异步不等于有界                       | `void write()` 不等待，但每条日志仍创建一个在途任务；数据库变慢时，在途任务堆到数 GB 堆                                                     |
| 每一级都要有上限                     | 入口（准入）、队列（批量）、连接（独立池）、降级（spool 计数）、输出（stdout 上限）、维护（清理批次与时长），缺任何一级，压力就在那一级积压 |
| 局部并发上限不等于全局上限           | `readableDocIds$` 每次调用 4 路，侧栏每个节点调用一次；`exhaustMap` 只管同一篇文档                                                          |
| 列表场景避免 N+1 授权                | 列表 214 篇时，逐篇查询每 5 秒 4,066 条 SQL；批量只读查询 11 条，与篇数无关                                                                 |
| 窄需求不要支付宽查询的成本           | 列表只要“能否读”，却每篇计算 17 项权限、加载三遍上下文                                                                                      |
| 降级路径的成本不能与积压规模相关     | 每条失败日志扫描全部积压文件，故障越严重越慢，单次扫描到了 2.5 分钟                                                                         |
| 可观测性数据本身不能成为负载来源     | 日志写入占数据库读取的 99.8%；内存采样也走同一条管道                                                                                        |
| 降级报告要按状态转换，不按事件       | 每条失败日志一个降级文件，4,031 个降级文件占遗留 spool 的近一半                                                                             |
| 维护任务必须能分批推进，并记录失败   | 一个大事务的清理每小时失败、什么也没删，表只增不减                                                                                          |
| 存活不等于可用，可用不等于能自动恢复 | 首页 200、`__typename` 正常时业务已慢；进程卡死时容器仍“运行中”                                                                             |
| 浏览器节流不是限流                   | 后台标签页每分钟仍整批发出 173 个请求                                                                                                       |
| 先止血、再根治、后重构               | 线上故障条件仍在时，低成本、可回滚的削减项优先于完整基线与通用框架                                                                          |
| 把假设写成可以被实验推翻的形式       | stdout“同步不占堆”、PID 1“导致卡死”都被实验修正或否定                                                                                       |

### B.1 spool 容量检查的内存放大

条件：容器 `localmind_hot_backend`（`localmind-affine:dev-base`，Node v22.23.3；线上为 v22.22.3），用 `transpileModule` 加载与线上 hash 一致的 `spool.ts`，在随机临时目录创建 8,305 个 521 字节文件，分别以 1、32、64 路并发调用 `bytes()`；每 20 ms 采样 `heapUsed`，每 300 ms 强制 GC 后采样。

| 并发 |      耗时 | 起始堆 MiB | 采样峰值 MiB | 运行中 GC 后最大 MiB | 结束 GC 后 MiB |
| ---- | --------: | ---------: | -----------: | -------------------: | -------------: |
| 1    |    387 ms |       22.5 |         30.5 |                 24.5 |           22.5 |
| 32   |  3,886 ms |       22.5 |        133.6 |                115.8 |           22.6 |
| 64   | 10,823 ms |       22.6 |        216.8 |                206.6 |           20.0 |

结论：GC 后仍保留的内存与并发数近似成正比，结束后完全回落，属于在途工作保留而非泄漏。

### B.4 权限请求的 SQL 条数

方法：

1. 在本地 `localmind_stream_fix_db`（PostgreSQL 16）新建一次性数据库，执行全部迁移。
2. 对该库执行 `ALTER DATABASE <库名> SET log_statement = 'all'`，只有这个库的语句会写入容器日志。

### B.5 保留清理的冷存储模拟

目的：在接近线上的“冷数据、慢磁盘”条件下，对比部署版本的参数与新逻辑。

环境：

- 一次性容器 `pgvector/pgvector:pg16`，`shared_buffers=16MB`；
- 执行全部迁移后写入 30 万行 9 月的运行日志（2% 为 error），表与索引约 211 MB，ID 登记约 55 MB；
- 写入完成后把容器内存限制为 96 MiB，并通过 cgroup `io.max` 把读 IOPS 限制为 50、写 IOPS 限制为 300，接近线上磁盘约 7 ms 一次随机读的量级；
- 每轮前重启容器以清空 `shared_buffers`，并在宿主虚拟机执行 `drop_caches` 清空页缓存。

每轮通过临时 ava 用例调用 `cleanupRetention()`，每轮 60 秒预算。

| 轮次 | 参数                                        | 结果                                                      | 删除行数 | 批次数 | 最大单批耗时 |        超时次数 |
| ---- | ------------------------------------------- | --------------------------------------------------------- | -------: | -----: | -----------: | --------------: |
| 1    | 部署版本（初始与最小批 2,000，不重试）      | `failed`，`LOCALMIND_LOG_RETENTION_BATCH_TIMEOUT`，22.5 s |        0 |      0 |            — |               1 |
| 2    | 新逻辑                                      | `partial`                                                 |  107,065 |     77 |     5,699 ms |               0 |
| 3    | 新逻辑（接着第 2 轮）                       | `partial`                                                 |   14,332 |     56 |     5,600 ms | 1（缩小后继续） |
| 4    | 新逻辑（接着第 3 轮）                       | `partial`                                                 |    1,391 |     43 |     5,596 ms |               0 |
| 5    | 新逻辑（接着第 4 轮，等 autovacuum 结束后） | `partial`                                                 |    1,427 |     26 |     7,692 ms | 2（缩小后继续） |

结论：

- 部署版本的参数在冷数据上第一批就超时，整轮失败、一行未删，与线上 04:19 一轮一致。
- 新逻辑每轮都有进展，没有一轮失败；超时都通过缩小批次在本轮内化解；最大单批耗时始终低于 10 秒的语句超时。
- 吞吐波动很大：第 3、4 轮期间 autovacuum 正在扫描这张表和 ID 登记表，与清理争抢同一个 50 IOPS 的读预算；第 5 轮的第一批要重新读入冷页。这个配额比线上紧得多，所以表中的行数只说明“在极端条件下仍能推进”，**不能**当作线上吞吐的估计。

测试中发现并撤回的一项改动：曾尝试把“是否可删”的条件放进扫描，让被保留的 error 行不占批次。冷存储下，一条语句要一直扫过前几轮删除留下、尚未回收的大段死元组才能凑够一批，反而每批都超时。最终改为“接着上一轮的游标继续”，让每一轮只扫描新的区间。

模拟结束后，容器、卷、临时用例与脚本都已删除，模拟中临时拉取的 `alpine` 镜像也已删除。本地 Docker 数据盘（Colima `/dev/vdb1`）在模拟期间只剩约 1.3—2.3 GB 可用（使用率 97%—98%），数据量因此控制在 30 万行。

### F.4 复测方法

1. 将 `agg_logs.py` 与 `db_metrics.sh` 复制到服务器 `/tmp`。
2. 运行：

   ```sh
   docker logs --since <开始> --until <结束> localmind_affine_server 2>&1 | python3 agg_logs.py <输出.json> <开始> <结束>
   sh db_metrics.sh <输出目录>
   ```

   `db_metrics.sh` 中修复前、修复后两个窗口的起点写在脚本里，再测时改成新的窗口。

3. 用完删除 `/tmp` 中的脚本，结果目录设为仅当前用户可读。
4. 再测时选择与修复前相近的时段，并记录当时的前端版本：可用 `getReadableDocIds` 是否出现来判断。
