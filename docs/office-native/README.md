# LocalMind Native Office

This directory is the source of truth for LocalMind's native Office subsystem.

LocalMind Native Office does not embed, proxy, or depend on a third-party
Office editor runtime. It owns the resource model, editing model,
collaboration, authorization, revisions, audit evidence, UI, and AI command
execution. Compatible parsing, rendering, compression, and codec libraries may
be used when their licenses and deployment model fit LocalMind, but they must
not become a second document service or source of truth.

## Product Boundary

Native Office resources are peers of the existing BlockSuite page and edgeless
document, not new BlockSuite view modes:

```text
LocalMind Workspace
|- BlockSuite Page / Edgeless
|- LocalMind Docs
|- LocalMind Sheets
|- LocalMind Slides
`- LocalMind PDF
```

The resource kinds are persisted as:

| Product surface | Artifact kind  | Primary editable format |
| --------------- | -------------- | ----------------------- |
| Docs            | `document`     | `.docx`                 |
| Sheets          | `workbook`     | `.xlsx`                 |
| Slides          | `presentation` | `.pptx`                 |
| PDF             | `pdf`          | `.pdf`                  |

Importing one of these formats should eventually create an Office Artifact by
default. Converting content into a BlockSuite page remains an explicit,
separate action.

## Shared Platform

The engines are isolated from BlockSuite's document schema but reuse LocalMind
platform services:

- workspace membership, ACL, sharing, approval, and audit;
- blob storage, immutable source evidence, revisions, and retention;
- realtime transport and CRDT collaboration;
- search, indexing, previews, comments, and notifications;
- Copilot Provider routing, Agent Runtime, worker leases, and cancellation.

Frontend code must not bypass GraphQL/API authorization to call backend Office
models directly. AI tools, HTTP/GraphQL entrypoints, and workers must reuse the
same Office domain model and command validation.

## Storage Contract

The first foundation slice introduces two durable records:

### `OfficeArtifact`

The artifact owns stable workspace identity and immutable import evidence:

- artifact kind and title;
- original filename, MIME type, blob key, byte size, and fingerprint;
- import idempotency key and fingerprint;
- monotonic revision counter;
- bounded compatibility diagnostics;
- creator and timestamps.

The original imported blob is immutable evidence. Renaming an artifact must
not rewrite its original filename or fingerprint.

The foundation currently accepts only the native package MIME for each kind:
DOCX for `document`, XLSX for `workbook`, PPTX for `presentation`, and PDF for
`pdf`. Legacy binary formats are conversion inputs, not alternate package MIME
types for an editable Artifact.

### `OfficeRevision`

Every saved state is an immutable, linearly linked revision:

- artifact/workspace identity and sequence;
- parent revision;
- origin: `import`, `user`, `ai`, or `system`;
- idempotency key and fingerprint;
- generated Office package blob evidence;
- optional structured-model/CRDT snapshot blob evidence;
- model version and bounded operation summary;
- creator and creation time.

Revision rows cannot be updated after insertion. A new edit creates a new
revision. The model rejects stale parent revisions so concurrent writers cannot
silently overwrite each other.

Writers serialize on the Artifact, insert the immutable Revision first, and
only then advance its revision counter. Deferred database guards require every
Artifact to commit with an initial revision and every inserted Revision to be
covered by the committed counter. Blob rows are locked while a new reference is
created; referenced Office blobs cannot be soft-deleted, permanently deleted,
or have identity-bearing metadata rewritten.

Large package and structured-state bytes belong in blob storage, not JSONB or
database logs. Compatibility diagnostics are limited to 64 KiB and operation
summaries to 32 KiB.

Fingerprint values are evidence fields computed by trusted server-side
import/save services from the actual stored or generated bytes. Future API and
worker entrypoints must not accept client-provided hashes as authoritative
evidence.

The native DOCX importer reads a bounded workspace Blob, verifies its database
and object-storage metadata, computes SHA-256 from the actual bytes, and copies
those bytes into a LocalMind content-addressed package Blob before creating the
Artifact. The initial Revision also references a content-addressed JSON state
Blob produced by the native semantic reader. Temporary upload keys are inputs
to import, not immutable Office package evidence.

## Editing Pipeline

```text
Original package
  -> package parser
  -> LocalMind semantic model + CRDT state
  -> validated user/AI commands
  -> layout/calculation/scene engine
  -> part-level package writer
  -> immutable Office revision
```

The active semantic model is the editing source of truth. OOXML/PDF is the
interchange and preservation representation. Unsupported package parts must be
preserved opaquely whenever safe; writers should rebuild only changed parts.

## Engine Boundaries

### Docs

Docs owns sections, paragraphs, runs, styles, lists, tables, drawings, headers,
footers, notes, comments, revisions, pagination, and font measurement.
BlockSuite rich text may supply reusable primitives, but it is not the DOCX
layout or preservation model.

### Sheets

Sheets owns workbook/worksheet state, sparse cells, formula ASTs, dependency
graphs, deterministic calculation, style registries, named ranges, tables,
filters, charts, and drawings. AI may author formulas and transformations, but
only the calculation engine determines cell results.

### Slides

Slides owns themes, masters, layouts, placeholders, slides, shape trees, notes,
comments, and animation timelines. Edgeless/GFX primitives may be reused for
selection and geometry without making BlockSuite the PPTX source of truth.

### PDF

PDF remains fixed-layout. Its native surface starts with rendering, search,
annotations, forms, signatures, page organization, print, and redaction.
Reflow into Docs is an explicit conversion rather than hidden mutation of the
PDF model.

## Command Contract

Toolbar, keyboard, automation, and AI changes converge on one structured
command bus:

```text
intent
  -> stable target resolution
  -> schema validation
  -> ACL and approval
  -> preview/diff
  -> atomic CRDT transaction
  -> package generation
  -> immutable revision and audit evidence
```

The shared `@localmind/office` package owns 47 strict command schemas under
`localmind-office-command/v1`: 12 Docs commands, 15 Sheets commands, 11 Slides
commands, and 9 PDF commands. Every command requires an expected revision,
command id, idempotency key, source, and stable resource-specific target where
applicable. Unknown fields are rejected instead of being silently dropped.

Ephemeral values such as `current_selection` must be resolved by the client or
planner before persistence. AI cannot directly rewrite OOXML or bypass command
validation.

All four engines execute through the same permission, preview, idempotency,
evidence, and immutable-revision path. Commands reject stale or missing parent
revisions and invalid targets. AI uses the same commands as the toolbar and
cannot directly rewrite OOXML/PDF or bypass authorization and validation.

## Implemented Capability Matrix

The current implementation is a native LocalMind vertical slice, not an
embedded third-party editor. Each successful edit writes a new immutable,
linearly linked `OfficeRevision`; the previous package remains available for
history and comparison.

### Docs (`.docx`)

- Open, inspect, edit, save, reopen, download, print, and export to PDF.
- Edit text and paragraph formatting, including font family and size, text
  color, bold, italic, underline style/color, paragraph style, alignment,
  spacing, indentation, numbering, outline level, and pagination controls.
- Replace text and insert line, page, and column breaks or new sections.
- Configure page size, orientation, margins, header/footer distance, gutter,
  columns, and first-page behavior.
- Insert tables, PNG/JPEG/GIF images, basic shapes and text boxes, equations,
  and column/bar/line/pie charts.
- Read and update headers, footers, content controls, and mail-merge fields.
- Inspect tracked OOXML changes and accept or reject selected/all changes.
- Show headings, bookmarks, review metadata, approximate pagination, and a
  multi-page document view.
- Compare immutable revisions using bounded semantic diffs.
- Add LocalMind comments and replies anchored to a revision and text range,
  and show collaborators collected from revision and comment activity.

### Sheets (`.xlsx`)

- Open, inspect, edit, save, reopen, and download workbooks while preserving
  unchanged OOXML package parts.
- Edit sparse string, number, boolean, blank, and formula cells.
- Parse and deterministically evaluate arithmetic, comparison, references,
  ranges, and the supported functions `SUM`, `AVERAGE`, `MIN`, `MAX`, `COUNT`,
  `COUNTA`, `IF`, `IFERROR`, `AND`, `OR`, `NOT`, `ABS`, `ROUND`, `COUNTIF`, and
  `SUMIF`.
- Format ranges; merge/unmerge cells; change row height/visibility and column
  width/visibility; insert/delete rows and columns.
- Set filters and data validation; add, rename, delete, and reorder sheets.
- Add/remove OOXML tables and column/bar/line/pie charts.

### Slides (`.pptx`)

- Open, inspect, edit, save, reopen, and download presentations while
  preserving unchanged OOXML package parts.
- Edit shape text and geometry; add/delete text and basic geometric shapes.
- Insert PNG/JPEG/GIF images.
- Add, duplicate, delete, and reorder slides.
- Edit speaker notes and theme colors.

### PDF (`.pdf`)

- Open, validate, render with PDF.js, search extracted text, download, and
  print fixed-layout PDFs.
- Add, update, and delete text/highlight/underline/strikeout annotations.
- Read and set supported AcroForm field values.
- Rotate, delete, and reorder pages.
- Add an explicit visual signature appearance.
- Apply permanent redaction by replacing the affected page with a flattened
  rendered image in a new immutable revision.

### Shared Product Surface

- Workspace-scoped GraphQL queries and mutations for import, listing, open,
  preview, execute, revision history/comparison, comments, replies, and
  collaborators.
- Authorized HTTP delivery for revision package/state/part bytes and DOCX PDF
  export.
- User and AI commands share validation, ACL checks, preview/diff, command
  request persistence, approval/cancellation state, idempotency, and audit
  evidence.
- Desktop and mobile workspace routes keep Office Artifacts separate from
  BlockSuite pages and open each kind in its native editor surface.

## AI Editing Loop

The native Office AI editing loop was completed on 2026-09-04. Docs, Sheets,
Slides, and PDF pages reuse the existing LocalMind AI Chat and attach a strict
`localmind-office-ai-context/v1` value containing the current workspace,
Artifact, immutable Revision, resource kind, and an optional stable selection.
Selections are captured at send time and use resource-owned identifiers rather
than ephemeral `current_selection` values.

User-generation routing is BYOK-only. An Office chat cannot fall back to a
quota-backed or global chat provider. The planner exposes only the native,
bounded `office_read`, `office_command_request`, and
`office_command_batch_request` tools, requires a successful read before a
write request, and prevents the model from submitting complete OOXML/PDF
replacement bytes.

Single commands retain `localmind-office-command/v1`. Atomic multi-step edits
use `localmind-office-command-batch/v1`, limited to 64 commands and 32 MiB,
with one Artifact, one expected parent Revision, one preview, one persisted
approval, and at most one resulting Revision. Commands execute in order on one
in-memory semantic state; any invalid target or failed child command aborts the
whole batch before package/state evidence or a Revision is committed.

Every AI write persists immutable command evidence and a waiting-approval
Agent Runtime run. After approval, the worker rechecks the delegated user's
current ACL, cancellation state, command Blob identity and fingerprint,
expected Revision, regenerated preview fingerprints, idempotency, and existing
side-effect evidence. Reject, cancel, permission loss, stale Revision, and
preview drift terminate without an Office Revision. A successful execution
creates exactly one `origin=ai` Revision and one execution-result ledger entry.

The Office task panel renders preview, approval, queued/running, rejected,
cancelled, conflicted, failed, and completed states. On completion it accepts
only immutable revision evidence for the current Artifact, reloads the new
state without a page navigation, restores the stable selection when the target
still exists, and clears it with a notice when the target was removed. PDF
tool policy and UI consistently limit AI edits to fixed-layout operations such
as annotations, forms, page changes, signature appearances, and redaction.

## Compatibility Levels

Feature support should be reported independently instead of claiming complete
Microsoft Office compatibility:

| Level | Meaning                                     |
| ----- | ------------------------------------------- |
| L0    | Unknown content is preserved                |
| L1    | Content is rendered correctly               |
| L2    | Content can be edited safely                |
| L3    | Content supports collaboration and AI       |
| L4    | Content survives a high-fidelity round trip |

Current native editable inputs are `.docx`, `.xlsx`, `.pptx`, and `.pdf`.
Legacy `.doc`, `.xls`, and `.ppt`, plus `.odt`, `.rtf`, and `.txt`, remain
separate conversion tracks and are not currently native editable inputs.

The implementation does not claim macro execution, ActiveX, editable arbitrary
OLE objects, complete SmartArt, every Excel function, complete PowerPoint
animation, or Microsoft Office-identical rendering. In particular:

- DOCX pagination is approximate and does not yet use Word-identical font
  metrics or a complete layout engine.
- DOCX PDF export uses the `pdf-lib` standard Helvetica font and a simplified
  layout pass. Characters outside the WinAnsi encoding are replaced with `?`.
- LocalMind comments/replies are a revision-anchored collaboration layer; they
  are not a complete write-back implementation of OOXML comments and replies.
- PDF signature insertion creates a visible appearance stamp only. It is not
  a cryptographic digital signature and does not create or validate a trust
  chain.
- Permanent PDF redaction deliberately rasterizes the affected page. This
  removes the original text and objects from that page but also sacrifices
  vector and selectable-text fidelity there.

## Delivery Order

1. Office Artifact/Revision persistence and command contracts.
2. DOCX package inventory, opaque-part preservation, and a read-only semantic
   model.
3. Docs text/style editing, package save, reopen, and AI format operations.
4. Docs pagination, tables, images, headers/footers, comments, and PDF export.
5. Sheets workbook/cell/formula vertical slice.
6. Slides theme/master/shape-tree vertical slice.
7. PDF annotation/page-operation vertical slice.

Each engine must prove open, edit, save, reopen, and preservation before its
feature surface expands.

The DOCX reader validates the OPC content-type table and root
relationship, rejects unsafe ZIP paths, duplicate normalized entries,
unsupported compression, excessive entry/byte counts, package-root escapes,
and XML DTD/entity declarations. It inventories relationships and content
types, preserves every package part byte-for-byte in the in-memory package,
and emits paragraphs, runs, text formatting, tables, content controls, styles,
sections, header/footer references, external relationships, and explicit
opaque-part diagnostics into `localmind-office-docx-state/v1`.

The writers preserve namespace-qualified and unknown XML nodes through ordered
trees, rebuild only the package parts affected by a command, create a
deterministic package, reopen it through the strict reader, and verify the
result before persistence. The server verifies parent Revision package bytes
and fingerprints, writes content-addressed package/state Blobs, and appends an
immutable Revision after permission and command-request checks.

Broad OOXML round-trip coverage and higher-fidelity layout/calculation remain
ongoing compatibility work. A feature being visible in the editor does not
raise every document containing that feature to L4; compatibility must still
be reported per feature and fixture.

## Validation

Every persistence change requires:

- Prisma schema validation and generated client;
- all migrations applied to a disposable PostgreSQL database;
- focused model tests for idempotency, stale revision rejection, immutable
  evidence, authorization rejection once API surfaces exist, and at least one
  failure path;
- formatter, oxlint, typecheck, and `git diff --check`;
- the smallest sufficient `localmind-affine:test` container validation under
  `docs/localmind-docker-development-constraints.md`.

OOXML engine changes additionally require package round-trip fixtures and
structural part comparison. Rendering features require deterministic reference
documents and visual-diff tolerances.
