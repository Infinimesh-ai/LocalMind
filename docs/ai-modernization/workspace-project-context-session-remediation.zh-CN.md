# Workspace / Project AI 会话与上下文管理实施方案

更新日期：2026-09-22。

状态：P0—P4 已完成源码实现与隔离环境聚焦验证，P5 的生成物和文档同步已完成；真实模型质量评测、完整浏览器矩阵、真实业务备份恢复和运行环境同步仍是上线关卡。本文已按用户纠正后的“一个 Project 共享一份 Memory”更新，替代此前按用户隔离 Project Memory 的方案；本文不代表业务运行环境已切换。实际结果见[执行记录](workspace-project-context-session-remediation.execution.zh-CN.md)。

适用范围：Workspace / Project AI 会话授权、Project 共享 Memory 与 Automatic Memory、引用版本、会话删除与长期审计、Workspace AiContext 唯一性、滚动上下文整理。

核心边界：共享的是项目长期知识，不是成员的聊天原文、私人附件或会话滚动摘要。修订本开发文档不授权回退现有代码、改写已执行迁移或公开旧私人记录。

## 1. 文档定位与决策边界

### 1.1 已明确的产品要求

| 编号 | 必须满足的要求                                                                                                              |
| ---- | --------------------------------------------------------------------------------------------------------------------------- |
| D01  | 会话访问必须先授权，不能先检索 Memory、装配上下文或产生副作用再拒绝请求。                                                   |
| D02  | 一个 Project 共享一份长期 Memory，以 projectId 为归属；当前有效成员均可召回合法共享的记录。                                 |
| D03  | 保留成员管理自己贡献、Owner 管理全部的方向；具体记录权限按贡献及版本判断，多人合并记录不得由一个贡献者单方面删除。          |
| D04  | Memory 共享不授予读取他人原始会话、私人附件或滚动摘要的权限；Owner 也不因管理记忆自动获得这些权限。                         |
| D05  | 用户进入 Project 1 召回 Project 1 的共享记忆；切换 Project 2 仅召回 Project 2 的共享记忆，不混入其他 Project 或 Workspace。 |
| D06  | Project Automatic Memory 使用项目级设置、去重、事实链、锁与配额；作者用于追溯而非召回隔离，不依赖 Workspace。               |

| D08  | 删除会话应清理正文及相关派生内容，同时可长期保存最小、脱敏的操作审计证据。                                                  |
| D09  | Workspace 一个会话最多有一个 AiContext，由数据库约束保证。                                                                  |
| D10  | 上下文接近预算时自动滚动整理，向用户展示进行中、完成、失败状态；不能静默截断后假装完整理解。                                |

## 3. 全局不变量与数据分类

### 3.1 三类信息不可混用

| 类别           | 身份与作用域                                                            | 目的                                         | 生命周期                                   |
| -------------- | ----------------------------------------------------------------------- | -------------------------------------------- | ------------------------------------------ |
| 长期 Memory    | Workspace/Document 保持原有个人规则；Project 以项目为归属、有效成员共享 | 跨会话保存事实、项目决策和约定               | 保留贡献与版本；不随个人会话删除而级联清除 |
| 会话工作上下文 | 本人 + 明确作用域 + session + contextEpoch                              | 当前会话继续工作，含原文、滚动摘要、资料片段 | 随会话及依赖失效、整理或清理               |
| 最小审计证据   | 行为主体、资源作用域、操作与结果                                        | 证明谁在什么授权下做了什么                   | 按保留策略归档，不供模型召回               |

`contextEpoch` 是建议新增的会话上下文代次，用于拒绝删除、迁移、撤权或资料失效前产生的旧结果；不是权限替代品。具体字段名可适配现有模型，但相同语义只保留一套真相源。

### 3.2 不变量

1. 作用域由服务端从持久化会话解析，不信任客户端传入的 userId、projectId 或 workspaceId。
2. Project 会话不自动混入其他 Project 或 Workspace 的 Memory；通用个人偏好如需保留，应有独立明确的产品契约，不能夹带其他项目事实。
3. 项目 Memory 共享不等于会话共享。仅允许向项目共享的来源可形成共享记忆；个人会话、附件和摘要不因位于 Project 中自动公开。
4. 召回权限与管理权限使用不同领域操作；成员可召回他人合法贡献，但不因此获得任意改删权限。Owner 管理入口不接入模型工具。
5. 内容缓存、摘要、向量、任务快照都不能扩大原始来源的权限。
6. 写入、取消、删除、撤权及重试使用条件更新/事务处理竞争；幂等结果不能用不同 payload 覆盖。
7. 私密正文不写入日志、审计 metadata、错误、指标标签或 support bundle。
8. UI 反映服务端持久状态，刷新、断线或多标签页不能改变事实。

## 4. F01：会话授权修复

### 4.1 领域层访问流程

建议将现有 owned-session 能力收敛为统一访问策略，区别 `readMeta`、`readHistory`、`update`、`fork`、`delete`、`submit`、`cancel` 等操作。名称是设计描述，不要求新增一个大型权限框架。

1. 仅加载会话最小授权字段：所属用户、Workspace/Project/Document、删除状态和版本。
2. 校验真实 actor、预期作用域、操作权限、实时项目成员/文档 ACL。
3. 返回经过授权的领域访问上下文，再读取历史、Memory、附件和模型配置。
4. 涉及写入时在最终事务内重查必要条件；涉及执行时沿用现有 worker 的实时 ACL 和能力上限。
5. 对不存在与不可访问对象使用一致且不泄密的错误映射。

禁止以 history projector 的显示过滤替代授权；`skipVisibilityFilter` 即使移除，也不能单独解决所有权缺口。

### 4.2 入口清单

- [ ] GraphQL：单会话元数据、会话列表、历史、更新、fork、删除。
- [ ] HTTP/SSE：发送、续传、重试、取消、结构化/图片生成。
- [ ] Context：列表、设置、上传、附件读取、摘要和计划诊断。
- [ ] Runtime：准备轮次、工具调用、后台标题、队列恢复及回调。
- [ ] Compatibility：现存 wrapper 和内部调用；不为修复重新注册退休 MCP 工具。

后台任务必须有明确的任务身份和作用域，不能通过通用 `skipAuthorization` 参数绕过所有检查。

### 4.3 保留兼容行为

现有 Workspace 文档场景中允许的共享历史/fork，保留独立、明确的文档 ACL 规则。共享读取/fork 不授予修改、删除、发送到别人会话或读取其私人 Memory 的权利。创建 fork 时不得复制未授权 Memory、摘要或私人附件。

Project 会话绑定不可被更新接口改为另一个 Project；原生 Project 会话不因缺少 Workspace 被拒绝，也不寻找替代 Workspace。

### 4.4 完成条件

未授权请求获取不到数据，并且模型调用数、Memory 检索数、来源写入数和任务创建数均为零。授权通过但提交前撤权/删除的请求，不产生新的持久写入或执行步骤。

## 5. F02：Project 共享 Memory 与 Automatic Memory

### 5.1 权限矩阵

共享召回是确定要求；下表将“成员管理自己的贡献、Owner 管理全部”落实为建议的记录级管理规则。自动事实合并不得绕过这些规则。

| 能力                                                | 普通有效成员                               | Project Owner                   |
| --------------------------------------------------- | ------------------------------------------ | ------------------------------- |
| 查看/AI 召回本项目有效共享 Memory，包含其他成员贡献 | 允许                                       | 允许                            |
| 向共享库新增合法项目事实                            | 允许，经来源和内容检查                     | 允许，经相同检查                |
| 管理自己独立贡献且未被他人修改/合并的记录           | 允许，检查当前版本及贡献关系               | 允许                            |
| 撤回自己的贡献证据                                  | 允许，不删除其他人的贡献或直接覆盖共享事实 | 允许，并记录实际操作者          |
| 修改/删除他人记录或多人合并后的共享事实             | 可提出纠正，不能直接覆写或删除             | 允许，检查版本并确认共享影响    |
| 修改项目级自动记忆设置                              | 不允许                                     | 允许                            |
| 控制自己的会话是否自动贡献记忆                      | 允许                                       | 允许                            |
| 读取他人原始会话、私人附件或滚动摘要                | 不允许                                     | 不因 Memory 管理身份授予        |
| 非成员或已退出成员召回、管理共享库                  | 不允许                                     | 失去有效 Owner 身份后同样不允许 |

管理页可返回共享 Memory 正文、来源类型、受控作者信息、版本和管理事件；不得返回他人的原始提示词、源会话正文、私人附件 URL 或摘要。来源链接独立鉴权；无权打开时只显示“来源会话不可访问”等脱敏说明。

“我的贡献”是共享库的过滤视图，不是另一份个人记忆库。最初作者不永远拥有整条事实：有他人贡献、修改或合并后，删除/改写权限按当前版本和贡献关系重新判定。

### 5.2 数据约束

保留现有 Memory 模型并演进，不按成员复制存储系统。

- Project 记录归属 projectId；技术性 workspaceId 不参与其内容身份、检索和配额。
- 活跃共享内容唯一键采用 `(projectId, kind, fingerprint)`；活跃自动事实唯一键采用 `(projectId, kind, factKey)`。partial predicate 明确限定“已获共享资格且有效”的记录，不能包括旧私人或隔离记录。
- supersedes 链匹配 projectId、kind 和事实身份；合法链允许不同贡献者，但跨成员变更仍须遵守冲突与管理权限，不能仅因为 projectId 相同就放行更新。
- writer lock 和 quota 使用项目/事实身份；事件幂等额外绑定真实 actor、源会话/轮次与 payload 指纹，不能把不同人的操作当成同一请求。
- 配额按项目计数；用有界批处理/贡献限速防止刷写挤占共享库。待确认冲突、人工固定事实不能被普通自动 LRU 静默淘汰；具体保留分类在实现时版本化。
- 保留 createdBy、lastEditedBy、contributions 和来源等必要追溯信息，字段名可适配现有模型。legacy ownerUserId 不再代表项目资产所有者，也不能被当作始终真实的原始作者。
- 管理修改使用 expectedVersion；正文变化创建受控内容版本，同时递增建议的 projectMemoryRevision 以失效跨成员缓存。正文版本受删除策略约束，不作为永久审计存档。

项目级设置建议名 `AiProjectMemorySettings`，以 projectId 唯一，包含 autoMemoryEnabled、revision、updatedBy 和时间字段。会话级 allowMemoryCapture 只控制当前会话自动贡献，不影响召回范围，也不允许成员改变整个项目的设置。Workspace `AiContextPreference` 保持原义；已出现的用户项目偏好不能直接作为新共享库的真相源，迁移见 5.8。

共享状态必须显式表达。不能仅把旧 visibility='private' 改名或删除查询 owner 条件，就将所有历史记录变为共享；共享资格由创建时契约、来源证据及必要的显式发布记录证明。

### 5.3 召回与管理分离

召回固定步骤：确认本人拥有该会话及当前有效项目成员身份 → 限定当前项目已获共享资格的有效 Memory → 在授权候选中检索与排序 → 返回前重查成员/项目/记忆状态 → 记录无正文来源证据。贡献者不是召回过滤条件；同项目的新成员可召回仍有效的已有共享记忆，不可访问旧私人记录。

需要核对并按新契约调整：

- buildContextMemoryVisibilityWhere 与相应 SQL；
- memoryManagementWhere、管理 resolver 和来源详情脱敏；
- applyWriterDecision、跨贡献者冲突、撤销、删除和 quota；
- embedding 候选、缓存键、重新嵌入任务和返回前校验；
- recordRecalledMemorySources 等来源登记逻辑。

共享检索缓存至少包含项目、Memory 合约版本、projectMemoryRevision 及相关查询/策略信息。请求级授权与会话缓存仍区分真实用户和会话；命中共享缓存不免除实时成员检查。修改、删除、禁用或撤权时，对全部依赖该记录的成员会话/摘要失效，不能只通知作者。实时通知只发身份与版本等最小字段，拉取内容时再次鉴权。

### 5.4 Automatic Memory 写入流程

1. 从已持久化且归属明确的本轮输入解析会话、actor 和 Project。
2. 读取项目开关和本会话贡献设置；任一关闭时跳过普通隐式提取。界面明确说明自动保存的内容将供项目成员共享。
3. 区分项目事实自动提取与用户明确的记住、更新、忘记命令。主动保存不受自动开关限制，但必须告知项目共享范围；破坏性命令仍检查管理权限、版本并确认影响。
4. 使用现有 DLP、结构化输出校验和全局 Project BYOK；拒绝不适合长期保留或共享的内容。
5. 保留并补齐项目共享来源检查：当前可读不等于可以共享。私人附件、仅本人可读的 Workspace 内容、其他项目材料和未获共享资格的数据不能写入共享库；摘要不能作为洗掉来源限制的中间层。
6. 在项目/事实锁下重查成员、项目设置及会话设置 revision、session 删除状态、共享来源资格和删除标记，再按贡献权限与冲突规则提交。
7. 成功后更新向量、提升项目 Memory 版本、失效全部受影响会话缓存并执行项目配额；各异步步骤可重试且幂等。

提取范围以项目事实、共同约定、决策和任务状态为主。共享模式的说明不构成自动共享任意正文的许可：敏感个人信息和明显私密陈述默认不提取；来源不明或共享资格不确定时跳过并给出可操作提示。AI 输出只能作为有证据的辅助材料，模型猜测不能升级为项目事实。

### 5.5 多人贡献与事实冲突

- 内容和含义确实相同的贡献可按项目去重并合并来源，保留各贡献者；不能因相同 factKey 就认为事实相同。
- 出现互斥值、日期或状态时，新贡献形成 pending 冲突候选，保存来源与版本；不得以“最后一次发言”或自动置信度最高者覆盖有效共享事实。
- 原作者可明确纠正自己尚未被他人修改/合并的独立记录；涉及他人或多方贡献的共享事实，由 Owner 确认解决。普通成员可提交纠正但不能直接覆盖。
- 待确认冲突不作为确定事实注入模型；必要时明确提示“存在待确认冲突”，不把一方默认为正确。
- pending 候选采用有界的待确认存储/状态，不参与 active 唯一键；解决、撤销和并发提交使用 expectedVersion，记录选择、保留及被否定的来源关系。
- 撤回自己的贡献只撤回该来源，不删除其他人的贡献。若原结论因此失去足够依据，标记待复核或失效，而非任意选择一个值。

### 5.6 关闭、删除、撤销及成员生命周期

- Owner 关闭项目自动保存或用户关闭本会话自动贡献时，提升对应 revision；排队任务提交前重查，不能关闭后补写。旧有效共享记忆仍可召回，UI 明确说明。
- “忘掉”不能绕过权限：先区分撤回本人贡献与删除共享事实，再按 5.1 确认权限、版本及对所有成员的影响。授权删除后清理衍生缓存，保存不含正文的标记防止旧事件重放恢复。
- 删除标记不永久禁止新的合法主动保存，但后续贡献不能借新事件身份绕过已确认删除或被否定事实的管理决定。
- 删除标记/恢复屏障至少覆盖关联重放、任务与备份的有效生命周期，不早于这些载体清理。
- 撤销绑定同一项目、事件、贡献和当前版本，不回滚他人后续修改；Owner 操作和本人操作有独立 actor 记录。
- 退出或被移出项目后，停止共享库读取、召回和管理，不因曾贡献记录而保留访问权；已合法形成的项目知识不随退出自动消失。
- 删除账号时，私人会话和旧私人记录按个人数据生命周期处理；合法项目共享记忆继续属于项目，按策略处理作者标识，不把作者伪造成其他 Owner。项目最后一位 Owner 的治理约束独立保留。
- 退出/删除前已经看到的内容不能承诺远程撤回，但服务端、缓存和后续运行必须停止不再授权的访问。

### 5.7 Rule、项目摘要与来源边界

项目共享 Rule、Project Summary 按其明确共享类型供成员使用；具有强制作用的项目 Policy 保持独立权限和信任层级，不能由自动记忆生成或提升。个人用户 Rule 不因项目记忆共享而自动发布。旧个人 Project Rule/Summary 适用与旧私人 Memory 相同的共享资格审查。

区分用户向共享模式明确提供的项目事实、已合法共享的项目资源、私人附件和受限外部内容。记录来源版本与共享资格，不把项目作用域、Owner 身份、全文摘要或来源会话可读性当作分享授权。

Project 导入和显式发布继续按原契约执行；对已批准独立复制的资源按其有效复制授权判断，不把来源成员后续变化一概视为可以撤回已批准复制。普通 Workspace 写入仍以实时 ACL 为准，来源证据只用于审计。

### 5.8 历史数据与在途个人化实现迁移

首先核对 `20260904010000_intelligence_workbench_phase_1` 与新增 `20260921010000_private_project_memory_and_session_context` 的源码、应用记录和实际数据，区分下列分支。不得编辑已发布/已执行迁移，不得由文档任务回退代码或运行生产 SQL。

| 实际状态                                    | 实施前处置                                                                                                           |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 只有未执行、未发布的个人化代码/迁移草稿     | 记录确认依据，在获准实现时调整待发布迁移计划；保留会话授权、contextEpoch 和 AiContext 唯一性等仍需的修复，不整份丢弃 |
| 个人化迁移已执行，但没有新增私人数据        | 新增前向纠正迁移，复核并恢复原本合法共享的记录；不能只按旧隔离 reasonCode 批量启用，因为之后可能另有删除或撤权       |
| 个人化契约已产生私人记录或私有 Rule/Summary | 按契约版本、创建时间和来源证据分类；既有私人记录不自动公开，原作者明确确认发布的具体内容后才进入共享库               |
| 执行状态、创建时契约或共享资格无法证明      | 停止相关切换，将不确定记录留在受控隔离区，排除召回；不根据当前 ownerUserId 或 visibility 字面值猜测                  |

历史共享库的多人事实链是正常协作，不因跨成员就认定为污染。记录资格审查：

- 可证明在共享契约下形成，且来源允许项目共享：保留项目身份、合法事实链、贡献与审计，不按成员拆库。
- 历史作者被转移：修复项目归属表达，保留原始审计；真实作者未知时标注未知，不把当前 ownerUserId 当已验证作者。
- 旧私人记录：提供受控发布预览，确认绑定原作者、具体内容版本、目标项目及来源许可；Owner 的管理身份不能代替原作者发布私人内容。无法确认则隔离或按期限清理，不另建活跃个人 Project 记忆产品。
- 包含非共享私人来源、跨项目越权内容、敏感内容或非法来源：继续隔离/清理，不因恢复共享模型就解除保护。

旧个人偏好不能以任意成员的开关或 OR 聚合变成项目开关；由 Owner 明确配置新的项目设置，切换默认见 1.2。已有会话的“不贡献”意图应保留为会话级控制或在继续前重新确认，不能当成同意共享旧数据。

切换时版本化 Memory 契约与项目设置，拒绝旧任务按个人合约提交或绕过共享来源检查。合法共享内容无需因“由别人贡献”重置会话；只有确有未授权内容或无法证明安全的派生污染，才失效相关缓存/摘要并开启干净上下文。私人聊天、滚动摘要和原始附件始终不作为公共重建材料。

### 5.9 前端交付

- 项目内统一提供“项目记忆”，所有有效成员看到相同授权共享库；“我的贡献”仅作筛选，Owner 的管理操作在同一库中体现。
- Owner 可修改项目自动记忆开关；会话提供“不自动贡献记忆”控制，两者不等同于关闭共享召回。
- 提示“本项目开启自动记忆，符合条件的项目事实可能保存为成员共享记忆”；主动保存反馈“已保存到项目共享记忆”。
- 展示贡献者、版本、来源类型、冲突/待确认状态及可执行操作；多人事实的修改、删除和冲突解决提示对所有成员的影响。
- 来源会话无权打开时不提供正文、URL 或旁路预览；不展示其他成员会话摘要。
- 共享记忆更新后刷新相关视图并失效依赖；切换 Project/会话丢弃迟到响应，成员移除后清除可访问缓存并停止订阅。

## 6. F03：引用版本与上下文刷新

### 6.1 快照语义

`ProjectChatContext` 继续保存每会话选择及 version；发送消息时冻结资源 ID、sequence、附件身份和上下文版本。latest sequence 仅用于提示，不自动替换冻结内容。

前端完整保留 frozen sequence 与 currentSequence，显示“当前引用 v3，最新 v5”。用户可刷新单项或全部选择。

刷新步骤：

1. 请求携带 expectedContextVersion 和明确选择范围。
2. 服务端检查会话归属、Project、资源状态和实时权限。
3. 在一致性事务内解析最新可读版本并更新选择，条件更新失败返回冲突。
4. 递增上下文版本，失效依赖旧资料的摘要/片段缓存。
5. 仅影响后续消息；过去消息及原轮次重试仍指向原快照。

重试并不免除实时权限检查：旧版本已不可访问时应拒绝继续读取。希望用最新版回答时创建新轮次，不能覆盖历史证据。

### 6.2 实时与失效

复用现有 `project.resource.changed` 及 15 秒兜底快照，不新增重复高频轮询。切换页面、隐藏页面和断线恢复沿用既有请求序列与节流机制。

资源更新：提示用户并等待刷新。资源删除或撤权：立即阻止后续输入中的原文及派生摘要使用，不能等待用户刷新后才执行权限变化。

摘要中区分“当时依据旧版本做出的决定”与“现在仍成立的事实”，避免同一问题混入新旧事实且不解释冲突。

## 7. F04：会话删除、内容清理与长期审计

### 7.1 删除清单

执行前建立内容载体清单，覆盖数据库、对象存储、Redis、队列 payload、日志和客户端缓存。重点包括：

- 会话消息、标题和含正文元数据；
- AiContext 配置中的私密内容、提取片段、embeddings；
- Project 选择中的会话专属附件引用；
- 滚动摘要、checkpoint 的私密内容、资料摘要；
- pending submission、消息及附件缓存、可重放 token；
- run/step/tool 输入输出、失败快照及排队任务中的正文；
- blob/下载授权及客户端本地会话缓存；
- 若另行授权删除共享记忆，则清理对应 Memory 内容版本和事件中的正文副本；个人会话删除不自动触发该操作。

清理不能删除独立项目资源、其他会话使用的附件或不可变外部执行回执。含正文的运行记录应拆分为“可清理 payload”和“不可变最小回执”，不能为了审计永久保存 payload。

### 7.2 删除状态机

建议沿用软删除标记并增加持久清理任务：

`requested → purging → completed`

`purging → retry_wait → purging`；重试耗尽为 `failed`，显式重试进入 retry_wait。依法或按已授权策略保全的内容进入 `held`，解除保全后才能继续 purging；每次破坏性清理前重查保全状态。

每个任务有稳定 deletionId、sessionId、contextEpoch、lease、attempt、清理项进度、nextAttemptAt、结果计数和脱敏错误。completed 仅表示配置范围内的在线副本已清理；备份到期和保全状态单列，不混为“全部物理擦除”。

1. 接受删除请求时，同一事务写 deletedAt、contextEpoch、任务及最小审计。
2. 立即拒绝读取、发送、恢复与新步骤；对可取消运行发起取消。
3. worker 分批删除内容，各步可重复执行，避免大事务长时间锁库。
4. 所有在途任务终态写入前检查 session 和 epoch，拒绝内容复活。
5. 每项完成后更新进度；全部满足后写删除回执。

并发边界：已经提交的外部副作用保留真实回执，不宣称撤销；授权检查之后、外部执行之前要沿用既有取消/租约检查，不能靠删除任务倒推外部行为已被阻止。

### 7.3 Blob 与备份

Blob 清理由真实引用关系决定。检查其他会话、资源、不可变 revision、Office 产物和有效保全引用；必要时补齐引用登记，使用标记清理和最终事务复查防止重新挂载竞争。不能仅按文件名或内容哈希删除整个对象。

删除下载授权并停止签发新链接；已签发链接的失效能力受存储实现影响，须明确 TTL 上限和可撤销方式，不能承诺所有预签名链接即时失效。

删除标记与恢复屏障应进入备份恢复流程：恢复服务开放读取和 worker 前，先重放仍适用的删除、撤权和 Memory 隔离记录。备份到期策略及保全例外应在 Admin 中可查询。

### 7.4 共享 Memory 与会话删除分离

Project 会话删除默认仅清理当前会话及派生上下文，保留已合法形成的项目共享记忆。取消原方案的“同时删除此会话产生的记忆”无条件勾选框，改为“查看本会话贡献的共享记忆”，由独立管理流程检查权限、版本和共享影响。

- 成员可管理仍属本人独立贡献且未被他人修改/合并的记录；多人合并事实按 5.1、5.5 撤回贡献或交由 Owner 处理。
- 删除会话不是撤回此前合法共享的同意，也不授予批量删除共享资产的权限。源会话删除后保留最小来源身份/指纹，展示“来源会话已删除”，不继续保存可读取的原始聊天副本。
- 如果另行请求并获授权删除某项共享内容，删除正文版本、向量、缓存及派生注入，保存最小事件；所有依赖该记忆的成员会话都要失效。
- 多来源事实不得因一个会话删除而整条删除；撤回贡献后若事实依据不足，标记待复核或失效。涉及未经允许共享的内容，应按来源安全规则隔离，不能以“项目资产”为由继续保留活跃召回。
- Workspace 的私人 Memory 删除选项保持原有作用域，不与 Project 共享管理混用；不默认删除其他会话、其他项目记忆或项目文件。

### 7.5 最小审计字段

优先复用 `LocalMindAuditEnvelope` 与现有领域 ledger。建议字段白名单：

- eventId、occurredAt、eventName、schemaVersion；
- actor 的受控标识及角色/作用域快照；
- session/run/step/request/operation 关联 ID；
- action、resourceType、resourceId、resourceVersion；
- policyVersion、必要的授权判定摘要和 reasonCode；
- outcome、稳定幂等身份、receiptId；
- 内容版本指纹、清理/归档进度计数；
- retentionClass、expiresAt、保全引用和脱敏版本。

不保存完整 Prompt、消息、Memory、摘要、工具正文、附件、凭据或可绕过 ACL 的 URL。短且可猜测的内容使用受控带密钥指纹或其他适当方案，不能把普通哈希视为可靠匿名化。

账号删除后使用目的受限的匿名化/假名化主体关联，遵循实例保留政策。合法共享记忆继续归属项目，不把作者改写为 Owner 或审计管理员；私人会话与未发布旧私人记录另按删除策略处理。

### 7.6 事务与归档

现有日志写入器单独开启事务，不等价于与业务写入原子提交。实施时增加可复用的事务内审计写入，或将领域事件/outbox 与业务变更同事务持久化，再幂等汇入现有审计外壳。

- 关键成功事件与业务提交一致；失败事务不能留下成功审计。
- 拒绝事件使用独立、受控的失败审计路径，不能随业务回滚一并消失。
- 相同 eventId 和不同内容指纹视为冲突，不静默返回已存在。
- 高风险操作在最小审计无法持久化时 fail closed；普通日志 spool 不能替代业务原子性。
- 归档任务复用 Cron/Worker，按批次持久化 pending、running、completed、retry_wait、failed 状态及租约。
- 归档内容存入实例管理的私有存储，包含清单、计数、时间范围、指纹和签名；密钥与数据库访问权限分离并记录 keyVersion。
- 归档后先验证可读性和完整性，才按策略回收热存储；数据库中的 archive 行本身不等于独立长期归档副本。
- 审计只追加，纠错追加关联事件；归档读取、导出、冻结、解冻和到期清理均有审计。
- 自托管不默认外发审计，不引入外部日志服务作为必需依赖。

### 7.7 保留与保全边界

沿用 [LocalMind 日志系统设计](../localmind-logging-system-design.zh-CN.md) 的分类方向，初始参数见 1.2。实例管理员配置保留期限及保全策略；Project Owner 仅查看授权项目的业务证据，不因该身份读取所有运行日志和他人原始会话。

默认证据能够证明操作、授权与内容版本关系，不能还原已删除原文。若业务明确要求保留原文，应采用单独审批、访问控制、用途和到期时间的内容保全，不将其藏在普通日志中。保全内容不进入 AI 召回。

## 8. F05：Workspace AiContext 唯一性

### 8.1 数据库与调用约定

- 建立并验证 `AiContext.sessionId` 唯一约束；先核对在途迁移是否已覆盖，避免重复迁移或为撤销个人 Memory 而丢弃该修复。
- 以唯一查询替代 `findFirst`；创建改为事务内幂等创建/upsert，唯一键竞争时读取现有记录。
- 应用锁可以用于减小竞争，但不作为唯一性真相源。
- 服务端拒绝把原生 Project 会话误写入旧 Workspace AiContext 路径。

### 8.2 重复数据升级

1. 只读扫描重复 session，输出 ID/数量/版本等非正文报告。
2. 暂停相关创建和更新，依据最后有效配置及实际使用证据确定 canonical context。
3. 不盲目合并所有配置与附件，避免恢复用户已经移除的引用。
4. 无法可靠判定的冲突保留受控备份并要求重新选择，不随机选择一份假装完成。
5. 向量只迁移与最终有效配置一致的片段，其余清理或重新生成。
6. 必要时保留短期旧 ID 映射；映射必须重新做所有权检查，不直接返回目标数据。
7. 验证重复数为零后安装唯一约束，再开放写入。

该迁移不改变 ProjectChatContext 的独立存储和每会话选择语义。

## 9. F06：滚动上下文整理与长资料处理

### 9.1 产品语义与参考边界

目标是“同一会话持续工作、较早历史可整理、原始聊天仍可查看、用户知道发生了整理”。参考 Codex 的压缩生命周期，不复制其未公开的摘要算法或阈值。

官方 App Server 提供 `thread/compact/start`，并通过 `contextCompaction` 的开始/完成事件报告进度；本方案的状态机与提示方式据此设计，但 LocalMind 使用自己的持久模型及前端协议。[官方说明](https://learn.chatgpt.com/docs/app-server)

默认实现采用 provider-neutral 结构化摘要，复用现有 CapabilityRuntime 和 registry。OpenAI 原生压缩返回不透明状态，不能当作通用可读摘要，也不能未经验证跨 provider 使用。独立压缩输入仍需装入模型窗口；若未来接入该能力，必须按官方协议完整保留返回窗口，并在路由变化时从合法源数据重建。[官方压缩说明](https://developers.openai.com/api/docs/guides/compaction)

### 9.2 预算计算

在最终 provider/model 路由确定之后规划，使用模型注册表能力及可用 tokenizer，不建立另一套进程内模型规格表。

`可用输入预算 = min(上下文窗口 - 输出预留, 独立输入上限如有) - 安全余量`

实际输入成本包括系统/开发者约束、工具 schema、当前问题、近期消息、Memory、摘要、资料片段、图片以及 provider 的协议开销。推理/输出预留按 provider 的具体能力处理。

- 初始自动触发与目标值见 1.2，并在策略版本中固化。
- 中文、表格、JSON、多模态不能统一用字符数除以 4 当精确 token；无法准确计数时使用保守估计，UI 标注“估算”。
- 当前问题、权威策略和完整工具协议属于受保护内容，不通过截断它们来满足预算。
- 切换到较小窗口模型时重新规划；整理所用模型本身也要单独满足其输入预算。
- 单次超长输入先分块，超长工具结果先有界持久化并提供片段读取，不让其破坏下一轮协议。

### 9.3 结构化摘要

摘要至少包含 currentGoal、userConstraints、decisions、verifiedFacts、completedActions、pendingWork、openQuestions 和 sourceRefs。字段名可调整，但必须有严格 schema、长度上限和来源关联。

规则：

1. 只整理已完成的较早连续前缀；保留近期完整交互与当前用户输入。
2. 新摘要基于上次有效摘要与新增前缀生成；记录精确消息范围和输入指纹。
3. 用户最新纠正优先，冲突显式保留，不把旧摘要当权威覆盖新要求。
4. 完成动作绑定真实 receipt，不把意图、预览或模型声称当作已执行。
5. 摘要中不得记录或生成隐藏思维链；只记录任务状态、事实和必要的简要理由。
6. 总结器无写工具执行权，将原始文本作为材料而非指令，输出通过 schema 和来源检查。
7. 摘要是有损材料；精确金额、坐标、表格值或引文需要回读获授权原文。
8. 滚动摘要保持本人会话私有，不直接写入共享 Memory，不跨 session 或成员复用。需要贡献项目事实时走独立 Automatic Memory/主动保存路径及共享来源检查，不能把整个私人摘要发布。

### 9.4 持久状态和并发

演进现有 `AiContextCheckpoint`，由不可变摘要修订和一个当前有效指针表达历史；不再静默覆盖唯一 checkpoint 的内容。另以最小任务记录或现有运行实体承载可变执行状态，避免建立第二套完整 Agent Runtime。

建议状态：`queued → running → succeeded`；失败进入 `retry_wait` 或终态 `failed`；用户取消为 `cancelled`；输入/权限代次失效为 `stale`。重试复用任务身份并增加 attempt，不重复发布有效摘要。

任务应包含：session/actor/scope、contextEpoch、输入修订及指纹、覆盖前缀、上次 checkpoint、策略和路由版本、依赖来源、lease/attempt、前后预算、有限错误码和时间。

唯一执行身份至少绑定 session、contextEpoch、输入指纹和策略/模型预算版本。worker 最终发布时通过 CAS 检查这些字段以及实时授权；摘要与有效指针的提交必须一致。

- 同时发送、重试和手动整理合并同一有效请求，不产生重复整理或重复回答。
- 崩溃后从持久状态恢复；仅当前有效 lease 能发布结果。
- 完成前发生删除、撤权、资料刷新或模型配置失效，丢弃旧结果或重新规划。
- 来源依赖同时关联共享 Memory revision、projectMemoryRevision、resource sequence 和实时成员/来源授权；不能仅靠内容指纹判断可用。共享记忆变更应使所有相关成员的 checkpoint 失效或重建，不只处理贡献者自己的会话。
- Memory 删除不自动删除用户选择保留的原始会话，但不能从缓存、旧摘要或已标记的 assistant 派生内容重新注入被删除的记忆。若无法可靠剥离派生污染，应开启干净的上下文代次并提示用户；不得用旧全文重建来绕过失效。
- checkpoint 正文属于私密会话数据，应用现有受保护存储和访问控制；审计/trace 只保存计数和指纹。

### 9.5 接入运行时

现有同步 context planner 演进为“异步准备/整理 + 确定性装配”两部分。异步准备放在 ConversationHost/TurnOrchestrator 的模型调用前，工具循环在安全边界检查预算；原规划器保留可测试的预算与渲染职责。

先持久化整理状态并向前端发送事件，再调用总结模型。成功结果校验和提交后重新装配输入，只提交一次原用户请求。不要为了整理重跑已完成工具或重新执行外部操作。

无可整理历史时返回 no-op，不为短会话收费。整理失败允许有界重试；只有明确标注且仍满足完整性/预算的降级路径才可继续。否则保留用户输入并暂停本次提交，提供重试、减少资料或新建会话入口。

### 9.6 长资料独立处理

历史整理不能修复进入 planner 前已经丢掉的资料。Project 材料应改为：获授权冻结版本 → 全文提取/分块 → 有覆盖信息的资料摘要 → 与本轮问题相关的原文片段。

- 分块记录页码、sheet/slide、段落或字符区间，资源 ID 与 sequence 不丢失。
- 对大资料采用分层摘要；记录实际成功处理范围，不因达到预算就默认声称全文已读。
- 多份资源有基本覆盖预算，再按相关性补原文，避免只读取排序最前几项。
- 不支持格式、图片处理上限、解析失败、缺失页及成本上限都输出结构化覆盖状态。
- OCR/VLM 若需要模型调用，使用当前合法路由；不偷偷上传给额外服务。
- 后续精确问题通过有界读取工具回查同一冻结版本，并重新检查 ACL。
- 派生片段和摘要按其来源的访问规则隔离；私人附件不得通过共享缓存泄露。

现有资源选择数量上限不因此自动扩大；本次修复解决已选择资源的预算和覆盖语义，不承诺一次完整读取无限资料。

### 9.7 用户反馈与协议

新增或扩展既有 timeline/流事件，统一包含 eventId、sessionId、contextEpoch、单调序号、整理任务 ID、状态和无正文统计。具体事件名在共享协议中定义，不能仅在 React 本地模拟。

| 状态               | 建议提示                                               | 行为                                     |
| ------------------ | ------------------------------------------------------ | ---------------------------------------- |
| queued/running     | 正在整理较早的对话，以便继续当前任务……                 | 非阻断通知；模型提交在服务端等待安全输入 |
| succeeded          | 上下文已整理，已保留当前目标、约束和待办。             | 可查看摘要、范围和估算前后用量           |
| failed，尚未生成   | 上下文整理失败，本次消息尚未发送给模型。               | 保留草稿/待提交消息，提供重试和减少资料  |
| failed，工具循环中 | 上下文整理失败，任务已暂停；已完成的操作不会重复执行。 | 展示实际完成步骤，允许安全恢复           |
| stale/cancelled    | 根据实际原因说明已取消或正在重新准备                   | 不展示过期结果，不自动重发消息           |
| 部分资料未处理     | 本轮使用了资料摘要与相关片段；部分内容尚未处理。       | 列出实际缺失范围及处理方式               |

提供手动“整理上下文”入口；是否增加 `/compact` 别名不是交付前置条件。UI 可显示上下文估算占用，但必须与 Automatic Memory 开关分开。

断线重连从服务端查询/重放状态，按事件 ID 去重；切换项目不接收旧项目事件。摘要查看遵守同一会话权限，Owner 不能通过此入口查看其他成员会话。

- 管理、主动保存、项目设置、会话贡献控制、冲突解决、事件与撤销接口支持原生 Project；管理写入使用 expectedVersion/幂等键并检查当前贡献关系。项目设置仅允许有效 Owner 修改，AI 不得代替 Owner 改项目政策。
- 引用刷新接口使用 expectedContextVersion；整理接口返回持久任务身份；清理查询返回不含正文的进度。
- 错误复用已有类型；必要时补充明确的 scope mismatch、version conflict、context stale 和 compaction unavailable 映射，不泄露对象详情。
- 同步 resolver/schema、共享 `.gql`、生成类型和 Web/Electron/mobile 消费者；由生成命令维护产物。
- 老客户端不能表达共享资格、贡献权限或明确发布确认时提示升级；不能通过旧查询返回私人记录，不能把“忘记”兼容为无条件删除共享事实。安全的共享只读查询可保持兼容。
- 不改变公开 MCP 凭据能力上限，不新增 Owner Memory 管理的模型工具。

### 13.1 上线前硬关卡

- [ ] 所有正文载体和清理责任明确；在线清理时限、备份期限、保全策略已经记录。

- [ ] GraphQL、Prisma、i18n 生成与源 schema 一致。

### 13.2 切换顺序

1. 进入相关写入维护窗口，暂停记忆写入、受影响 AI 提交和 worker，停止旧任务领取。
2. 验证备份、实际迁移状态和数据契约，按 5.8 分支应用前向迁移；恢复合法共享资格，隔离私人/未知/非法来源，不盲目解除历史隔离。
3. 验证项目共享唯一键、贡献/版本约束、项目设置和独立 AiContext 唯一约束；修正账号删除的资产归属/作者处理，不改写历史作者。
4. 提升共享 Memory 合约及项目版本，失效受影响缓存/上下文，拒绝旧个人写入任务；未明确共享的私人数据始终排除。
5. 部署兼容版本，验证各入口拒绝路径；分批恢复 worker 和用户流量。
6. 仅在共享范围、会话私有和来源权限稳定后灰度启用整理策略；不能 A/B 测试是否公开私人内容或跨项目召回。
7. 检查同项目跨成员召回、非成员/跨项目拒绝、共享来源、项目/会话开关、冲突处理、清理与整理恢复后结束维护。

若实际实现改变了既有模型工具契约，额外遵循现有退休脚本及维护流程；本方案本身不要求恢复或扩展工具契约。

运行环境同步须单独获得部署任务授权，遵守仓库脚本与 Docker 约束。含 schema/migration/native 漂移时，先验证 Linux 源码容器及备份，再使用既有 `yarn localmind:sync:backend` / `web` / `all`；不得手工复制零散运行文件或默认重建镜像。

### 13.3 观察指标

仅收集有界、无正文的指标：拒绝原因计数、跨作用域候选拒绝、偏好版本冲突、Memory 写入/配额、清理最老积压及失败数、审计 outbox/归档滞后、整理成功/失败/stale 次数、前后 token、provider 成本、p50/p95 延迟和资料覆盖不足比例。

跨项目、非成员及未获共享资格的私人内容泄漏为零容忍；合法同项目跨成员召回是预期行为，不作为泄漏告警。发现越权即停止受影响召回与写入并保留脱敏调查证据。性能预算根据隔离环境基线制定上线阈值，不能凭空宣称生产 SLA 已达成。

### 13.4 回滚边界

- 可以关闭新摘要策略、暂停自动贡献或暂时停止共享召回；合法项目共享查询本身不是禁止的回滚目标。但不得回退到授权前加载、忽略成员/共享来源校验、将旧私人记录自动公开或伪造作者的实现。
- 回滚应用版本必须理解新 schema、共享资格、贡献权限和数据来源；不能恢复个人化任务后把其产物当共享数据。不兼容时维持维护状态并前向修复，已执行迁移不改写。
- 已完成的正文清理不可通过普通应用回滚恢复；备份恢复必须应用删除屏障。
- 已发生的外部副作用及其审计不能因回滚被撤销或改写。
- 历史隔离结果保留审查证据；旧方案仅因多作者而隔离的合法共享记录可在复核后恢复，但私人、未知、已删除或撤权记录不能随之批量启用。
- 回滚开关、操作者、原因、影响范围和恢复条件写入最小审计。
