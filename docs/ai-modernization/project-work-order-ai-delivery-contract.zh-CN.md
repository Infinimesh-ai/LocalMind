# Project 个人工单：统一模板、接单对话与 AI 辅助交付契约

日期：2026-09-29。状态：v2 工单核心流程已实现；语义内容条件仍按本文的“不可可靠判断则不放行”规则处理，运行环境同步与视觉验收另行执行。

本文是 Project 个人工单从草拟、发出、接单到完成发回的现行产品契约。它覆盖
[Project v9 工作台方案](project-workbench-v9-implementation.zh-CN.md)中“接单人必须在右侧表单
手工整理并提交交付”的交互约定；v9 的独立工单存储、私人会话、不可变回执、
完整返回门禁及权限边界继续有效。[Project Workbench Redesign](tracks/project-workbench-redesign.md)
负责页面壳与路由，[Project Native Resources](tracks/project-native-resources.md)
负责项目原生资源，本文不改变二者的资源归属。

## 1. 用户流程

1. **草拟工单**：发单人在自己的 Project 会话中说明需要谁提供什么。其 AI 根据统一
   模板形成结构化草稿，逐项写明应返回的文字或文件、格式、数量和可验证条件。
   发单人查看完整草稿与准确收件人后，显式确认发送。草稿阶段不通知收件人。
2. **收到工单**：发送成功后，收件人收到站内通知；“我的项目”的“待我行动”展示
   这张工单卡片。卡片显示标题、发单人、来源项目名称、需要返回的项目、缺失/待确认
   状态和最后活动时间，不展示发单人的私人会话。
3. **打开接单对话**：点击卡片进入该工单专属的私人 AI 对话。首次打开创建一次
   会话，此后点击返回同一会话。对话默认载入已确认的工单要求、明确交接的背景及
   后续双方显式发送的追问/答复；不继承发单人的私人聊天、Project 文件树或 Memory。
4. **协作补全**：收件人与 AI 对话，AI 可解释要求、追问发单人、起草文字、生成或
   整理文件。可交付的文字和文件必须逐项进入工单交付草稿，并与冻结的要求 ID
   绑定。聊天消息、仅有下载链接或未绑定要求的暂存文件不算已填写。
5. **就绪提示**：AI 发现各项必填要求已有候选内容时，调用受控检查得到逐项结果。
   仅全部通过时，在对话里展示“已备齐工单要求，是否确认完成并发回？”卡片，列出
   即将发回的文字摘要、文件名与对应要求，并提供预览及“确认完成并发回”按钮。
   AI 的文字判断本身不能把工单变成已完成。
6. **确认发回**：收件人点击确认后，服务端按当前工单版本和草稿版本重新验证全部
   必填项，原子生成不可变交付版本及回执，通知发单人，并将该工单和收件人对应
   会话归入“已完成”。发单人在自己的原会话查收；如一批工单尚未全部返回，仍只见
   约定的要求和进度。将回执采用到原会话上下文仍是发单人的独立操作。

收件人始终可打开交付清单检查缺项和手动发起就绪检查；AI 提示不是唯一入口。完成
确认与停止 Agent、拒绝工单、撤回工单、完成普通 Project 会话是不同动作。

## 2. 统一工单模板

统一模板固定**结构与校验语义**，不固定“写四段文字”之类业务内容。每张工单至少有：

| 区域         | 必要字段与规则                                                                |
| ------------ | ----------------------------------------------------------------------------- |
| 身份与来源   | 工单 ID、模板版本、发单人、精确收件人、来源会话、来源项目名称快照和创建时间   |
| 目标与背景   | 标题、目的、仅被明确允许交接的背景；发单人确认前完整预览                      |
| 返回要求清单 | 至少一项，稳定要求 ID/顺序、类型 `text` 或 `file`、标题、说明和必填标记       |
| 文字要求     | 明确需要回答的内容和可验证条件；不能靠 AI 从聊天里猜哪段话是最终答案          |
| 文件要求     | 允许的真实 MIME/容器格式、最少/最多数量和内容条件；文件与要求 ID 一一建立关联 |
| 交付规则     | 必填项全部合格方可发回；可选项可为空；发送后要求冻结，补充/替代创建新工单     |

例如“请返回一份 PPT”：模板中必须有一项必填 `file` 要求，允许真实 PPTX 格式，
最少一份。AI 可生成 PPTX 草稿，但只说“PPT 已做好”、贴文件名或提交与该要求无关的
文件都不能通过检查。发单人无法用模糊要求强迫系统验证它不具备的格式或内容能力；
确认发送前应说明限制并要求修正。

一个发单请求涉及多名收件人时，仍为每位收件人建立独立工单和私人接单会话；统一
模板不意味着多人共用一份可编辑交付草稿。发单人的确认绑定草稿指纹和收件人身份，
再次确认不得重复派单。

## 3. 交付草稿与完成判定

- AI 可按接单人的对话指示，把候选文字和生成的文件自动写入对应要求的交付草稿；
  用户上传文件也可直接关联所选要求，无须逐项复制到另一张表单。每项都必须保留
  稳定要求 ID，且收件人可编辑、替换、预览。草稿属于该收件人与该工单；发单人
  此时只能看到要求和进度。仅在聊天里提到的内容若未写入草稿，仍不算已填写。
- 每次就绪检查绑定工单 ID、要求指纹、工单版本、交付草稿版本、逐项候选的内容指纹
  与检查结果。检查失败只显示可操作的缺项/错误，不产生交付版本或成功通知。
- 服务端先验证本人接单身份、当前工单状态和冻结要求，再检查每项必填文字非空且
  符合明确条件；文件要有对应要求 ID、允许的 MIME、正确数量、仍可读取的 Blob、
  非空字节、真实容器格式和约定内容条件。扩展名、模型宣称或前端按钮状态都不能
  代替服务端验证。
- 内容条件需要语义判断时，AI 可提出有界逐项检查证据；无法可靠判断时保持
  “需补证/待确认”，说明原因，不虚构通过，也不临时增加发单时未约定的主观标准。
- 所有必填项通过后只产生**待用户确认**状态。确认卡片必须显示准确的交付快照和
  每项要求的映射。用户可以继续修改、取消确认或返回对话；未点击确认不得发回。
- 用户点击确认时再次检查身份、工单/草稿版本、要求指纹和每个文件的当前可用性。
  若在提示后新增追问、修改草稿、文件过期、工单取消或版本变化，旧确认失效，
  显示变化并重新检查。重复点击或网络重试以同一请求键只产生一个交付版本。
- 成功交付保存不可变的文字/文件快照、逐项证据、提交人、时间、版本和回执指纹；
  后续修改须显式提交新版，不覆盖旧回执。通知与状态变化随事务可靠投递。

## 4. 状态、权限与提示

| 情况                             | 收件人卡片 / 对话                              | 发单人侧                     |
| -------------------------------- | ---------------------------------------------- | ---------------------------- |
| 工单刚送达                       | 待我行动；显示冻结要求与缺项                   | 进行中，等待返回             |
| Agent 正在生成，或等待发单人答复 | 进行中，标注真实等待原因                       | 追问到达时待我行动           |
| 候选不完整或检查失败             | 待我行动；逐项指出缺少的文字、文件或可验证证据 | 不见私人草稿内容             |
| 全部通过、等待本人确认           | 待我行动；展示交付预览与确认按钮               | 尚未收到交付                 |
| 确认成功                         | 已完成；可查看自己的回执，继续聊天不重交付     | 收到通知；按完整返回门禁查收 |
| 拒绝、撤回或取消                 | 显示明确结果，不标为成功交付                   | 保留原因及后续处理入口       |

通知与卡片只指向收件人自己的工单会话；发单人只能回到自己的来源会话。Agent 不得
通过接单人的会话读取来源 Project 的文件树、共享 Memory、其他接单人的工单或私人
聊天。交付前的文字和文件仅对接单人可见；交付后仅在既有完整返回门禁允许时，
发单人才能取得对应不可变回执。交付不自动写入发单人的 Project 或 Workspace。

## 5. 与当前实现的差距及实施验收

新发出的工单使用模板版本 2。服务端保存接单人独有的版本化交付草稿；AI 文字工具、
私有文件生成和用户上传均可绑定冻结的要求 ID。逐项检查会读取候选文件并核对
存储元数据、字节指纹及暂存时验证过的真实容器；接单对话在全部通过时展示
交付预览与本人确认按钮。确认请求绑定工单/草稿版本和交付指纹，服务端再次读取
文件并在事务中生成不可变回执。旧模板版本 1 保留原提交 mutation；版本 2 只
接受草稿确认入口。通知、私人会话和完整返回门禁沿用既有领域逻辑。

目前没有可靠的通用语义内容判定器。新的 `bounded_model` 要求在草拟阶段被拒绝；
历史上已发出的此类要求保持“缺少语义验证证据”，不会以文字非空冒充通过。发单人
应把返回内容改成系统可验证的要求后重新发单；`non_empty_text` 只证明文字确实填入，
`mime_and_container` 只证明文件格式、字节和容器，不证明演示文稿的业务质量或
任意自然语言内容条件。实施与聚焦验证记录见
[执行记录](project-work-order-ai-delivery.execution.zh-CN.md)。

实施时至少验证：

1. AI 草拟的不同文字/PPTX 工单都使用同一模板；未获发单人确认时收件人无通知和工单。
2. 通知与“待我行动”卡片打开同一私人会话；要求和明确背景自动进入上下文，其他
   人的私聊、Project 树和 Memory 均不可见。
3. AI 或用户形成的文字/文件准确绑定要求 ID；仅在聊天里宣称完成不会改变状态。
4. 必填 PPTX 缺失、文件过期、伪装扩展名、容器损坏、数量不足或关联到错误要求时，
   均不出现可确认的就绪卡片，直接调用提交接口也被拒绝。
5. 全部要求通过后显示逐项预览；确认前发单人看不到交付；用户点击一次产生单一
   不可变回执、已完成状态和通知。
6. 确认卡片展示后若草稿、要求版本或工单状态变化，旧确认失效；并发确认、重试、
   取消和新版提交不重复交付、不覆盖旧版本。
7. 多收件人、补充工单与部分返回继续遵守完整返回门禁；发单人采用回执保持独立，
   不自动公开到 Project 或 Workspace。
