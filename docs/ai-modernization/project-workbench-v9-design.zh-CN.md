### D04：任务总览

状态：状态边界与“一会话一卡”已确认；多事项状态聚合等细节继续讨论。

用户明确提出将“最近完成”改为“已完成”，原型已调整。用户对以下边界明确回答
“可以，待处理表示轮到我行动”：

- 待处理：当前需要我审批、决策、回答问题、提交资料或查收返回结果。
- 进行中：会话中的工作仍在推进，包括等待其他人返回的阶段；等待原因作为状态标签。
- 正在等待别人并不自动进入自己的待处理。该规则替代此前把“等待他人”放在待处理列
  内的建议，仅用于本次新方案，不声称现行产品已切换。

用户确认的看板形态：每个人拥有独立总览，一张卡片对应当前用户的一个会话，点击进入
该 session；不把同一会话的每个工单或内部执行步骤重复铺成卡片。项目会话标明所属
项目；个人工单不强行绑定项目，点击进入接单方自己的独立会话。原型标注“个人工单”
及发起人，具体展示样式仍可调整。同一会话同时存在多个事项时，建议“待我行动”
优先，其余执行或等待状态以标签显示；这一聚合优先级尚未单独确认。

“进行中”是会话的工作状态，不等同于模型此刻正在生成或 worker 正在执行。正式实现
需要区分会话工作状态、待办原因与底层执行状态，不能只靠 AI 回复中的状态词判断。
具体持久化模型和判定证据尚未设计。

关系图已按 D13 改为来自个人条目关联工单的只读视图，随预览身份、项目筛选和交付
状态变化；不再使用与条目无关的静态关系示例。总体进度的含义和首期范围仍待讨论。

### D05：会话、执行任务与团队事项

状态：手动完成、接单方独立会话与未结工单约束已确认；交付完成原则见 D12。

用户提出：进行中会话的右上角提供类似归档的按钮，用户手动将会话放入已完成；
已完成仍可打开，继续对话时从已完成移回进行中。

原型暂用按钮名“标记完成”。单纯打开查看不改变状态，发送新的非空消息才重新进入
进行中；Agent 后续若提出必须由当前用户处理的问题，可再进入待处理。按钮最终名称、
误操作撤销、仍有本人的 Agent 执行任务时的完成行为尚未确认。协作工单尚未结束时，
先列出未结事项，完成交付或由发起人明确撤回后才能结束主会话，不能静默取消。

协作会话的“完成”还受明确交付要求约束。原型中的接收人按钮会引导提交必填资料，
不能只点完成却不返回资料。普通会话手动结束与协作请求交付完成需要分别说明。

用户确认 B 进入独立工单会话；A、B、C 各有自己的 session，关联工单和明确交接的
说明、答复与交付物。B/C 不必选项目或加入 A 的项目；A 不自动获得 B/C 的私人聊天。
追问、答复、拒绝与撤回说明会明确发送给对方，普通聊天不自动作为对外消息。

### D12：通用工单模板与完成回执

状态：通用模板、发布方 Agent 决定具体交付要求、给出所需信息即完成已确认；
字段布局、检查实现和异常交互仍可继续讨论。

用户明确要求：“类似工单”，使用通用模板发送任务和接收完成结果。具体要什么由
发布任务的 Agent 根据当前目标决定。例如发送时要求 PPT，返回时必须确认 PPT
实际交付，不能仅靠对方说“完成了”、提供文件名或一段说明替代约定文件。

核心规则：

1. Agent 先形成工单草稿，列明对象、任务目的、所需交付项与完成条件；A 确认后发送。
2. 接收方按同一份交付清单返回文件和信息。模板通用，内容不固定；某项任务要求 PPT，
   另一项可以只要求文字，不能给所有任务强加相同必填字段。
3. 完成判断依据发送时约定的要求。需要文件则检查对应文件确实交付，需要信息则检查
   所需信息齐备；满足后工单完成并返回回执，无需 A 再点击“通过验收”。
4. 仅选择文件、保存草稿或声称完成不等于已返回。缺项或格式不符时，向接收方明确指出
   缺什么、如何补齐，保留在轮到该接收方行动的待处理状态。
5. 按 A/B/C 示例，接收方完成和发起方主任务完成分开：B/C 已完成，A 在全部回执返回
   后进入待处理，查收返回内容并将其用于后续对话；A 的主会话仍由 A 决定何时完成。

建议使用以下同源模板字段；这些具体字段与命名属于原型方案，不是正式 API 设计：

| 部分     | 字段与呈现                                                                          |
| -------- | ----------------------------------------------------------------------------------- |
| 工单身份 | 工单标识、发起人、接收人、各自关联会话；来源项目/工作区仅为可选背景，不决定收发资格 |
| 任务说明 | 标题、目的与必要背景，由发布方 Agent 填写，用户确认发送                             |
| 交付清单 | 逐项名称、文件/文字类型、必交/选填、格式、数量或所需内容说明                        |
| 完成回执 | 对应交付项的文件/信息、逐项检查结果、完成结果；正式实现还需关联持久化证据           |

正式实现时的边界与未决细节：

- 文件需可访问、可读取并确为约定类型，内容项需按工单要求核对；检查应有证据，不能
  把扩展名正确或文字非空等同于信息齐备。检查能力不足时应明确说明，不能自动声称通过。
- 只按已约定的条件核对是否交付；不新增主观满意度或未约定的质量门槛。内容质量异议
  的处理交互仍待讨论；追加或改变要求须按 D17 新建工单，不能重新解释原完成标准。
- 原型将发送时的要求复制到接收方工单，避免交付时要求随草稿漂移。正式版本的补充/
  替代工单、并发与幂等实现尚待设计；需求变更原则见 D17，回执的固定版本规则见下文。
- 回执关联明确交付的内容，不自动共享接收方的私人聊天、附件或其他上下文。工单按
  D10 独立于 Project/Workspace 收发；来源资源授权和分享限制继续遵守所属资源契约，
  不能以工单关系替代来源项目的成员权限或泄露项目 Memory。

交付版本规则已确认：

1. 每次成功提交形成固定版本，文件、文字、约定要求与检查结果均对应这次提交。
   修改源文件、改本地草稿或继续聊天，不会改变 A 已收到的结果。
2. B 更新交付需要显式重新提交，生成新版本并通知 A；不原地覆盖旧回执，不把普通
   私人消息当作新的对外交付。准备或放弃新版草稿均不影响已经交付的版本。
3. A 已采用的上下文继续固定在原版本。新版到达后，在完整交付条件满足时进入待处理；
   A 查收并明确采用后再更新当前引用，旧版交付及采用历史保留。无需新增主观验收门槛。
4. 原型提供版本号、历史回执、准备/放弃新版、重新提交及通知的交互；要求缺项仍不能
   提交，已拒绝/取消的工单不能借重新提交恢复。正式实现应以持久化版本和不可变资源
   标识保证此规则，不能仅依赖文件名、可变链接或浏览器对象。

验收场景草案：要求 PPT 时，缺附件、只写文件名或返回其他格式不能完成；按要求交付
真实 PPT 与所需说明后，B 完成且 A 收到回执，不等待 A 批准。C 的纯文字工单不要求
额外附件，选填项留空不阻塞完成。正式实现还应覆盖伪装扩展名、损坏或无权限文件、
缺少约定内容以及重复提交；这些尚未通过 HTML 原型验证。

   交互仍需细化；正式发送时须重新校验，不以 HTML 中的 A/B/C 身份切换作为权限依据。

个人工单模型：

1. 个人工单会话与 Project 会话共用管理员配置的全局 AI 模型与凭据，不要求接单方
   为此加入来源项目或建立隐藏 Project/Workspace。
2. 共用模型配置不等于共享数据。只使用当前用户自己的工单会话上下文、明确交接的
   工单说明及获授权的资料，不继承来源项目 Memory、文件树、私人会话或工具权限。
3. 延续全局模型边界：配置缺失或停用时明确提示联系管理员，不回退到 Workspace、
   用户或设备私有凭据。密钥保留在服务端，不交给收件人或写入静态 HTML。
4. 现行 Project provider 路径包含项目成员校验；正式实现应建立独立工单会话的所有权
   与资源授权路径，再复用管理员全局配置，不能通过伪造项目归属或绕过校验实现。

发送后需求变更：

1. 已发工单的对象、目的、交付清单和完成条件固定。新增或改变要求时，Agent 在 A
   原会话生成补充或替代工单，说明与原工单的关系，经 A 再次确认后发送。
2. 新工单有独立身份和接单会话；A 仍从原发起会话跟进和收取结果，不另建接收会话。
   已有聊天、工单约定、交付版本与历史均保留。
3. 发送替代工单不自动取消原工单。需要废弃的未结原工单，仍由 A 明确撤回并通知
   对方，可解释原因；已成功交付的记录不改成取消，也不因新增要求被追溯判为未完成。
4. 原会话继续遵守完整返回与未结事项约束：补充或替代工单发送后纳入待返回范围；
   未明确撤回的原工单仍保留原有义务，不能静默从进度或完成检查中移除。
5. 区分“交付新版”和“需求变更”：按原要求更新资料使用 D12 的显式新版本提交；
   改变要求或收件人使用新工单，不能借新版交付入口改写原约定。

后续验收应至少覆盖：非同项目的站内账号接单、站外地址不投递、不继承项目上下文、
全局模型不可用时不回退，以及新增工单不覆盖原要求、不自动撤回或改变已交付结果。

## 7. 后续验收清单草案

以下仅为设计完备性检查，待决定确认后形成正式验收矩阵；当前均未验收。

- 全局总览 → 项目 → 会话 → 产物 → 返回，导航状态和浏览器历史一致。
- 首次使用、空项目、没有会话、没有运行任务时有明确入口。
- 多项目、多会话、多任务及大量文件不会挤占主要工作区域。
- 自己的会话与团队可见事项不会混淆，链接和预览不能扩大权限。
- 执行、审批、等待资料、等待编辑、失败和取消均展示真实状态与可执行动作。
- 产物打开到正确编辑器；保存、未保存提示、只读与版本变化可理解。
- 完整文件浏览与当前会话引用选择的范围清晰，切换会话不会混用引用。
- 深色主题、窄屏、中文长标题、键盘导航、焦点恢复与错误提示通过实际检查。
- 不以演示数字、静态进度、模拟发送或无持久化状态冒充已实现能力。
