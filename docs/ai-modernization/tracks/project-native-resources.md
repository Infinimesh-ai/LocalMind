## 2. 已确认的产品规则

| 编号 | 确定规则                                                                                                                                |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------- |
| D1   | Project 真正拥有内部文档、文件和文件夹。默认创建、编辑和保存不属于任何 Workspace。                                                      |
| D2   | 用户要求创建文档时，先把真实文档创建到当前 Project 的指定文件夹或项目根目录，不因缺少 Workspace 位置而停在待创建状态。                  |
| D3   | Project 支持持久化的多级文件树，人工界面与 AI 均能按用户意图创建文件夹和文档。                                                          |
| D4   | Project 内部内容、标题和目录变动只影响项目内部，不自动更新、移动或删除任何外部副本；外部修改也不自动回流。                              |
| D5   | 只有用户明确要求保存到、发布到或更新某个 Workspace 时，才进入对外操作。选择 Project、提供素材、普通保存和重试内部保存都不代表对外授权。 |
| D6   | Project 与 Workspace 文档具有独立 ID、编辑状态和版本历史。通过来源及发布记录关联，同名不是身份依据。                                    |

| D8   | 不设 Project 对外发布开关或 Owner 专属发布权。有效项目成员明确发起对外操作时，按目标 Workspace、目录、文档的实际权限判断。              |
| D9   | Workspace 新文档继承目标位置权限；更新已有文档保留其原有权限。两种操作都不自动改变 Project 成员或 Workspace 成员关系。                  |
| D10  | 从 Workspace 导入 Project 时，沿用来源文档的读取、复制和分享权限检查。不能把只能个人阅读的内容开放给整个 Project。                      |
| D12  | 对外位置选择器逐级选择 Workspace、根目录和子文件夹，并支持在当前层级新建文件夹；不能把全部后代目录塞入一个下拉框。                      |

## 3. 用户工作流

### 3.1 仅在 Project 内工作

用户在 `test` 中要求“创建 test1 文件夹，在里面创建文档a并写入内容”：

1. 验证当前 Project 和成员身份，定位 Project 内的父目录。
2. 通过项目目录模型创建 `test1`，通过对应资源引擎创建、保存 `文档a`。
3. 文件树立即显示真实资源，并可在 Project 内打开、编辑和重新打开。
4. 返回项目资源 ID、项目路径和实际保存结果；不出现 Workspace 保存位置选择器。

同级已有同名目录时须确认身份或按既有明确规则复用，不通过名称匹配到外部目录。
多步骤任务分别记录已完成步骤；后续失败时，已创建内容仍可见并可恢复，不能虚报整项完成。
普通保存、自动保存、关闭重开、重连以及 AI 重试均只更新项目资源。

Project 内部操作必须在用户没有任何 Workspace 成员资格时仍能成立。
不得暗中创建专用 Workspace、选取第一个可访问 Workspace，或用当前会话的
`workspaceId` 假装实现 Project 原生存储。技术性执行上下文不得成为资源的存储所有者。

### 3.2 创建后发布到 Workspace

用户明确要求“创建文档a，并保存到 Workspace1”：

1. 先在当前 Project 持久化文档及内容，展示内部创建成功。
2. 为这份项目文档单独建立发布请求，显示目标 Workspace 的逐级位置选择器。
3. 用户选择明确位置后，检查目标权限，按已有工具审批语义执行发布。
4. 在 Workspace1 创建独立文档，保存发布回执及对应的内外版本。
5. UI 分别显示“项目内已保存”和“已发布到 Workspace1 / 路径”。

取消位置选择、撤回发布、目标无权限或发布失败，都不能删除、隐藏或回滚项目内文档。
如果用户已经给出可唯一解析的位置，选择器可以预选该位置，但不能自行选取模糊匹配项。
根目录是可明确选择的目标，不与“未选择位置”混用。

后续发布到 Workspace2 会创建另一份独立外部文档。一个项目文档可以保留多个发布目标
记录，但任何发布记录都不代表自动同步授权。

### 3.3 更新已有外部文档

用户明确要求“把项目中的文档a更新到 Workspace1 中的文档A”：

- 绑定准确的目标 `(workspaceId, resourceId)`；存在多个候选或仅有同名时让用户选择。
- 展示本次使用的项目版本、目标文档和更新差异，不把“更新”偷偷改成“新建副本”。
- 目标已关联时复用映射；第一次指定更新某个已有文档，也可在准确选择后建立映射。
- 校验目标最新版本。若外部或项目源版本相对预览发生变化，旧确认失效，重新比较。
- 用户明确更新 Workspace1，只写 Workspace1 的目标；Workspace2 的其他副本保持不变。
- 完成后记录本次发布的项目版本与外部结果版本；失败或冲突不得记录成功版本。

已有可读权限不足时，不能把目标正文读出来做差异展示。不能为了显示差异而绕过目标 ACL。
外部文档已删除、目标类型不兼容或目录失效时明确失败，不按同名自动重建或换绑。

### 3.4 从 Workspace 导入 Project

“加入 Project”在新界面中表示复制一份项目内部资源，并明确显示该语义：

1. 在源 Workspace 中核对来源 ID、最新版本、读取、复制和向整个 Project 分享的权限。
2. 无权分享时复用现有访问申请流程，不提前复制正文、Blob、索引或预览。
3. 通过后创建独立项目资源，记录来源和导入时版本；源文档及源 ACL 不变。
4. 导入后的项目副本按 Project 成员权限编辑，不继承源文档的只读编辑状态。

来源复制审批人通过通知批准或拒绝，不因审批身份额外生成 Todo。申请人及目标项目
成员保留“等待他人”的待办；同时具有审批和项目成员身份的人仍只能从通知或来源文档
的申请记录处理审批，待办不提供审批按钮。申请方可撤回未决申请。批准后保留授权与
审计记录，不提供撤回已同意复制授权的接口或按钮，也不能借此使项目副本失效。

授权导入的是一个独立版本。源文档后续修改或访问权限变化不自动重写、删除这个已合法
导入的副本；后续读取新版或再次导入时，重新检查当时的来源权限。历史共享引用和未完成
导入仍按其有效授权处理，不能把失效引用当成已授权副本。

用户明确要求“读取源文档新版并更新项目副本”时才执行反向导入，也必须比较项目当前
版本以免覆盖内部修改。导入素材中的嵌入文档和附件分别检查授权，不递归扩大复制范围。

## 4. 权限边界

| 操作                           | 服务端条件                                          | 权限与副作用范围                   |
| ------------------------------ | --------------------------------------------------- | ---------------------------------- |
| 项目资源读取、编辑、创建目录   | 有效 Project 和当前有效成员身份                     | 仅当前 Project；默认所有成员可读写 |
| 项目树移动、重命名、移入回收站 | 当前有效成员身份及资源/父目录属于本项目             | 不改变外部目录、内容或 ACL         |
| Workspace 导入项目             | 有效项目成员；源读取、复制、向项目分享权限          | 创建独立项目副本，不改源文档       |
| 项目发布为 Workspace 新文档    | 有效项目成员；明确用户意图；目标创建及位置权限      | 新文档使用目标 ACL                 |
| 项目更新 Workspace 现有文档    | 有效项目成员；明确用户意图；目标读取/更新等所需权限 | 保留目标原 ACL                     |
| 在位置选择器新建文件夹         | 当前目标目录的新建文件夹权限                        | 只在该 Workspace 当前目录创建      |

Owner 继续承担项目成员和项目管理职责，但不是内容发布资格的唯一持有者。
不增加 Project 发布角色、Owner 审批或逐文件发布开关。旧 `aiPolicy=read_only`、
源文档的 Project write grant 或“目标所有读者必须也是项目成员”，不能变成上述
新流程的额外 Project 发布门槛。需要将旧校验分支与新资源归属正确区分。

新发布流程以明确的用户操作和目标实时 ACL 允许内容进入目标受众，并保留受众及权限
证据。不得简单删除共享权限校验，导致普通会话或旧工具获得无意的跨域写入能力。
来源权限检查仍在导入边界执行；未经授权的私密材料、Rule 或旧会话未知来源不能通过
AI 上下文混入项目共享内容。Project 原生内容使用本项目的来源证据，不要求伪造源
Workspace grant。

用户和 AI 调用同一资源授权模型。AI 仍不能创建 Project、管理成员、变更权限或批准
访问请求，但可代表有效成员操作 Project 内的真实文件和文件夹。保留平台级功能控制、
工具审批、委托凭据上限与审计，不把这些机制误实现为 Owner 专属发布许可。

排队、确认、执行、重试和持久化提交前都重新检查实时权限。成员移除、目标授权撤回、
Project 归档及租约交接必须在所有 API、下载、编辑同步、索引和 AI 路径生效。

## 5. 资源与目录模型

以下是必须满足的领域模型，不要求照抄表名；实现前按仓库现有模型确定最小结构。

| 领域记录     | 必需信息和不变量                                                             |
| ------------ | ---------------------------------------------------------------------------- |
| 资源所有者   | 明确的 `project` 或 `workspace` 归属和 ID；单份可变资源只有一个所有者        |
| 项目资源     | 项目 ID、稳定资源 ID、类型、标题、当前版本、创建者、时间、回收站状态         |
| 项目目录节点 | 项目 ID、节点 ID、父文件夹 ID、目录/资源类型、排序与并发版本                 |
| 内容与版本   | 项目命名空间内的编辑状态、不可变版本及 Blob 引用；不能读写外部副本的可变状态 |
| 导入来源     | 源 Workspace/资源 ID、被复制版本、授权证据、操作者和导入结果                 |
| 外部目标记录 | 项目资源 ID、目标 Workspace/资源 ID、最近成功发布版本、外部版本和历史操作    |
| 持久化操作   | 种类、源/目标、意图/确认、版本、状态、幂等键、租约、结果与失败证据           |
| 迁移记录     | 旧引用身份、内部新 ID、授权状态、内容校验、重试游标与完成凭据                |

### 5.1 存储与编辑边界

- 复用 BlockSuite/Yjs、现有存储接口和 Native Office 引擎，通过明确的资源归属适配访问。
- Project 的正文、增量、Blob、附件、预览、索引、搜索和版本均须有真实项目作用域。
- 不只在 UI 增加 Project 标签，底层继续读写旧 `(workspaceId, docId)`。
- 不把 `projectId` 填入假 `workspaceId`，不通过伪造 Workspace 成员或隐藏 Workspace 绕过边界。
- 可复用不可变内容去重，但每次访问必须按所有者授权；不共享可变 Yjs 文档或 Office 当前版本指针。
- 普通文档、画布和现有 Docs/Sheets/Slides/PDF 类型保持原类型；附件按 Blob 资源保存。
- OfficeArtifact/Revision 和 Blob 的归属约束需正式迁移，保留版本不可变、父版本及证据约束。
- 不新造编辑器、不扩展格式保真目标，也不把 Office/PDF 降级为普通 BlockSuite 页面。
- 前端使用项目内打开路径和 Project 作用域服务；点击内部文档不能跳到来源 Workspace 编辑。
- 协议采用明确的资源引用联合类型，旧 Workspace API 保持兼容，不在各入口复制另一套授权。

### 5.2 文件树

- 提供根目录、新建文档、新建文件夹、展开/折叠、重命名、移动、排序、回收站和恢复。
- 目录记录实际持久化；`groupId` 展示分组不能冒充具有父子关系的目录树。
- 同一父目录按既有名称规范处理重名并明确反馈；文档的内容身份不由名称或路径决定。
- 父节点只能属于当前 Project，且必须是有效文件夹；禁止自包含、祖先循环和跨项目直接换父。
- 路径深度、批量移动和子节点返回数量有服务端上限；建议深度 64、分页默认 50/最大 100。
- 树节点按展开层级按需加载，不能先加载全项目所有后代再前端过滤。
- 并发重命名、移动、删除和恢复使用版本检查或事务条件更新。
- 删除默认移入项目回收站，恢复也在项目内部；不永久清理业务数据或联动删除外部副本。

### 5.3 会话、AI 与执行归属

- All projects 只显示总览，不显示聊天入口。选定项目后，聊天和文件操作明确绑定该项目。
- 切换项目不能复用另一个项目的草稿附件、内容缓存、文件 ID 或检索权限。
- 全局 Project BYOK 保持独立于 Workspace；内部资源不要求执行用户先拥有 Workspace。
- 梳理 `AiSession`、Agent Runtime、队列、工具上下文和审计中强制依赖 Workspace 的路径，
  将实际资源归属与历史执行上下文分开；不得通过创建隐藏 Workspace 兼容旧接口。
- `doc_create` 在项目会话中的结果必须证明项目资源已提交，不能只准备 Markdown 并要求选外部位置。
- 发布、更新外部和导入是明确的独立命令；不能让普通 `doc_update` 或自动保存沿来源关系写回。
- UI 和模型回执分别表达内部创建、待发布、发布成功、冲突、撤回和失败，不能一律显示 `Created`。
- MCP 继续遵守凭据的既有作用域和能力上限；不能因引入 Project 资源就把 Workspace 凭据自动
  扩展成全项目凭据。无法表达 Project 授权的旧委托入口明确拒绝，不伪造确认或成员身份。

## 6. 外部操作与恢复

### 6.1 操作生命周期

Project 内部保存和对外发布使用独立状态，不能共用一个含糊的 `created` 状态。
内部资源提交成功后，即使外部操作仍等待位置，内部文档也必须可以打开。

```text
项目资源：creating -> saved -> 后续独立内部版本

外部操作：
prepared -> waiting_for_location / waiting_for_confirmation
         -> queued -> running -> complete
         -> conflict / failed / cancelled / expired
```

复用 Agent Runtime 的合法状态及批准机制，按需增加受迁移约束的业务状态。
所有等待、执行、取消、租约和重试记录都必须可跨进程恢复。状态名称可适配既有模型，
但不能仅存在于 UI、内存或日志。

### 6.2 幂等与并发

- 冻结项目源版本、目标资源/位置、目标预期版本、操作者、确认版本、期限及操作指纹。
- 外部副作用和成功回执在可靠事务/幂等边界内衔接；崩溃重试不会重复创建文件、文件夹或内容版本。
- 同一确认重复提交只执行一次；后续明确再次发布属于新的操作。
- 用户新增同名文档可以是新的合法意图，不能靠标题把不同请求合并。
- 有明确替代关系的请求通过操作 ID 标记取代/撤回；“不要文件夹了”应优先修订当前请求，
  不静默丢失已有项目内容，也不再凭同名创建多个无法区分的待发布请求。
- 目标版本、路径、受众或权限变化使旧确认失效。冲突不自动覆盖，也不扇出更新全部目标。
- 已成功外部创建但结果回传中断，恢复时返回原回执；已完成副作用不以“取消”名义静默删除。
- 单纯关闭位置选择器不得撤销项目内部保存；过期与失败的外部请求可重新选择位置后重试。

## 7. 逐级位置选择器

选择器服务于显式外部发布，不作为 Project 内部创建的前置步骤。
优先从对应发布任务或聊天工具结果打开，与那次操作及项目资源绑定，避免在聊天顶部堆叠
多个同名而缺少目标说明的独立表单。

### 7.1 浏览与搜索

1. 先选择可访问且适用于本次操作的 Workspace。
2. 显示该 Workspace 根目录的直接子文件夹，支持选择“保存到当前目录”。
3. 点击文件夹进入下一层，显示面包屑和返回上级；选择与进入两个动作明确区分。
4. 使用 `(workspaceId, parentFolderId, cursor)` 查询，按父目录和排序分页。
5. 搜索采用服务端有界查询，结果附带可见的路径；选择结果后定位到相应目录，仍可逐级调整。

不默认读取全部后代、不把 10,000 个目录放进一个 select，不枚举不可见祖先名称。
跨父目录、跨 Workspace 的游标不得误用；切换目录清空旧分页，丢弃迟到响应。
列表可见性与可写性分别校验；能浏览某目录不意味着能保存或建子目录。

### 7.2 当前层级新建文件夹

- 在当前 Workspace/父目录提供“新建文件夹”，输入名称后调用已授权的目录创建 API。
- 提交前后检查当前目录 ID、版本与创建权限；重复点击使用幂等键，重名明确处理。
- 成功后刷新当前列表并可进入新目录，再确认外部文档的保存位置。
- 新建文件夹是独立且真实的外部副作用，有单独权限、确认结果与审计。
- 用户后来取消发布时，已明确创建的文件夹保留，不自动删除；失败时不显示不存在的目录。
- 目标没有建文件夹权限时提供准确的禁用/错误状态，不笼统隐藏整个位置选择流程。

### 7.3 必须覆盖的界面状态

沿用现有组件、图标、主题和 i18n。覆盖加载、空目录、无 Workspace、只读目录、错误重试、
重名、目标已删除、权限变化、离线、处理中、重复提交、成功、冲突、撤回和过期。
窄屏下可以完整浏览路径、进入/返回目录和创建文件夹。可用键盘操作且焦点不会丢失。
用户看到的状态只描述真实业务结果，不暴露内部 ID、租约或后端协议。

完成情况逐阶段记录；单个阶段完成不等于整个功能已交付。

## 11. Docker、运行同步与交付

执行遵守 [Docker Development Constraints](../../localmind-docker-development-constraints.md)
和 [Validation](../validation.md)。优先复用 `localmind-affine:test` 与已有容器做聚焦检查。
只在工具链、native 或打包等实际需要时构建固定 tag，不创建专项 tag、不常规重建整镜像。
重建前检查 `docker system df`，预计新增超过 30 GB 时停止并报告。

运行更新前完成数据库备份、同平台 Linux 验证与升级演练，再通过现有
`yarn localmind:sync:backend`、`yarn localmind:sync:web` 或 `yarn localmind:sync:all`
同步，按脚本要求提供 `LOCALMIND_RUNTIME_SOURCE_CONTAINER` 和
`LOCALMIND_DATABASE_BACKUP`。不手工复制散落文件，不删除业务数据、volume 或无关镜像。

验收使用隔离测试 Project/Workspace，既有业务文档和本次页面上的等待请求按迁移规则
处理，不拿它们做破坏性演示。测试数据与失败样本的保留/清理由已授权规则决定。

交付报告列明变更文件、真实命令与结果、迁移/回填数量和例外、备份路径、浏览器证据、
是否重建固定镜像、磁盘状态和剩余风险。同步更新本文状态、`current-state.md`、
`next-goals.md`、相关权限/Office 文档和用户指南，区分产品契约、实现和实测结果。
未经用户明确要求不 commit、push、创建 PR 或发布远端。

### Workspace 导入选择器与后台执行（2026-09-08）

Project 文件区提供“从工作区导入”，在当前目录接入工作区/文件两步选择器。
工作区按 `Workspace.Read` 过滤；文件发现、提交、执行和重试使用显式个人 ACL
（`projectScope(null)`），不能将已有 Project grant 当成个人读取权限。来源复制及
分享权限仍由 `ProjectImportService` 和授权模型实时校验。

提交复用 `AiAgentRun` / step / execution result 持久化来源、目标目录、幂等键和
复制申请关联，不新增只存在于浏览器中的等待任务。审批人由通知处理；申请人及
Project 成员保留单条访问申请 Todo，等待中的导入 run 不再重复投影，也不能通过
普通任务确认接口自批。既有分钟 worker 从数据库恢复已批准请求并创建独立副本，
拒绝、过期、撤回转为未导入。关闭页面或队列即时投递失败不丢失任务。

工作区导入失败保留执行回执；显式重试重新检查实时权限，以同一个 run 的导入键
继续执行，防止重复副本。文件区和导入记录展示真实执行状态，与审批状态分开。
本次复用已有 runtime 表及约束，没有新增数据库迁移。
